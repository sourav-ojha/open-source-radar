# Open Source Radar — 2026-11-25
_Rotation slot 1 — AI agents, MCP, coding productivity_

## Executive Summary
Today's slot (AI agents, MCP, coding productivity) produced an unusually strong, well-documented crop: a Microsoft Research/UC Berkeley plugin with a published arXiv paper that measurably cuts Claude Code/Codex spend, two MCP servers that take a real-world action (mobile device control, browser control) with a deliberate human-in-the-loop safety gate for anything sensitive, a local SSD-streamed inference runtime for running huge open-weight models without workstation-class hardware, and a validated text-to-SQL/personal-knowledge-base MCP server built atop NVIDIA's published Auto Ontology research. Two already-catalogued projects (Bernstein, ctx) crossed real major-version boundaries with substantive new capability, not just version-number churn. The dominant noise pattern today was a wave of GitHub repos with wildly inflated star counts relative to forks/issues/subscribers — repeatedly flagged in prior runs and reconfirmed here — which kept several otherwise-plausible mobile-agent and local-inference entrants out of the main catalog pending organic traction.

## Today's Best Discoveries

### 1. TokenEconomizer — 8.6/10
**Decision:** USE NOW

**What it is** — A plugin for Claude Code, Codex, GitHub Copilot CLI and Pi that cuts coding-agent token cost in repositories worked in repeatedly, without touching the agent's model or code. Three mechanisms: micro-skills (remembers confirmed repo-specific facts), tool pruning (stops sending definitions for tools that go unused), and a failure-loop guard (nudges, never stops, a stuck turn). From Microsoft Research, Microsoft Security and UC Berkeley, with a published arXiv paper.
**Why I should care** — It wraps Claude Code, the exact agent this radar itself runs on, and the 18.4-30.9% measured cost reduction across five agent/model combinations on SWE-Bench (cheaper in all 30 repository×combination cells, Pass@1 up in 4 of 5) is backed by a real benchmark methodology rather than a marketing number.
**What it could replace** — Hand-written CLAUDE.md/AGENTS.md repo notes that require manual upkeep and don't prune unused tools or catch stuck loops.
**Ways I could use it** — Install in a frequently-used Claude Code repo and let it learn test/build commands; use the tool-pruning mechanism on repos where only a few tools are ever invoked; rely on the loop guard during long autonomous runs; compare measured cost before/after to judge whether a model is worth its spend.
**Agent opportunity** — Directly applicable to this very radar's own Claude Code run.
**Integration effort** — Low: a plugin install into an existing agent, fails open if any part errors.
**Maturity** — Emerging (v0.1.0, six weeks old) but backed by a published, benchmarked paper.
**License** — MIT, no restrictions.
**Alternatives** — Hand-written repo notes; prompt-cache-aware harnesses like Dao Code (STUDY, catalogued); vendor usage dashboards that report spend after the fact.
**Why this one** — Rare combination of a rigorous published benchmark and direct Claude Code applicability.
**Recommendation** — Install on a repo used daily with Claude Code.

### 2. phonedriver — 7.9/10
**Decision:** PROTOTYPE

**What it is** — An MCP server and CLI giving a coding agent control of a real or virtual Android phone/iPhone: reads the screen as a numbered text list (not a screenshot), taps/types by reference, and pauses for human approval before any action that pays. Claims 6.9x fewer tokens than mobile-mcp.
**Why I should care** — Turns manual mobile QA (navigate three screens deep to toggle a setting, walk a signup flow by hand) into something an agent can do in the same Claude Code session already used for backend/web work, with a concrete safety pattern for real-money actions.
**What it could replace** — Manual mobile QA passes; heavier Appium/Maestro-plus-vision-model setups for agent-driven mobile testing.
**Ways I could use it** — Agent-driven signup/checkout flow testing; mobile regression checks in a PTaaS/MSSP engagement; exploratory bug-finding on an emulator from a single prompt.
**Agent opportunity** — Ships as a standard MCP server plus installable Claude Code/Codex plugin bundles.
**Integration effort** — Low to install (`npx phonedriver init`); requires local adb/Xcode device setup.
**Maturity** — Emerging (17 days old at review, but with docs, CI and published benchmarks).
**License** — AGPL-3.0 — fine for local/personal use; flag before embedding in a hosted multi-tenant product.
**Alternatives** — mobile-mcp (slower per its own benchmark); Appium/Maestro with a vision wrapper; manual QA.
**Why this one** — The text-based screen-reading architecture and the explicit payment-approval guard are both concrete, checkable design choices rather than marketing claims.
**Recommendation** — Prototype against one real app's signup or checkout flow.

### 3. browse (Anomaly) — 7.7/10
**Decision:** PROTOTYPE

**What it is** — An MCP server plus Chromium extension letting an agent drive the user's own real browser — actual tabs, logins, extensions — instead of an isolated automation profile, handing control back to the human for logins, 2FA or payment. From Anomaly, the company behind OpenCode.
**Why I should care** — Most browser-automation-for-agents tools already in this catalog operate a disposable logged-out profile; this removes the recurring "the agent needs me logged in somewhere" friction entirely.
**What it could replace** — Playwright-MCP-style wrappers and browser-use/Stagehand-class tools that require re-establishing logins for every agent task.
**Ways I could use it** — Fill/submit forms or scrape authenticated internal dashboards using an already-logged-in session; automate a no-public-API SaaS tool's web UI; visual QA with the developer's actual extensions installed.
**Agent opportunity** — One install flow wires native MCP config for 10+ agent clients at once.
**Integration effort** — Medium — a native binary plus a browser extension, more setup than a pure CLI tool.
**Maturity** — Emerging (about a month old) but with a real signed-release pipeline and company backing.
**License** — MIT, no restrictions.
**Alternatives** — Playwright MCP wrappers, browser-use, Stagehand (already evaluated, saturated niche) — all use an isolated profile rather than the user's real browser.
**Why this one** — The real-browser architecture is a genuinely different, well-executed answer to the login/2FA friction the saturated browser-automation niche hasn't solved.
**Recommendation** — Set up for one workflow that currently needs manual browser use because of an existing login.

### 4. Auto Ontology MCP — 7.6/10
**Decision:** PROTOTYPE

**What it is** — An MCP server bringing NVIDIA's published Auto Ontology semantic-layer research to any MCP client for validated text-to-SQL (checks generated SQL against reviewed join paths and real data before running it) and a personal knowledge base (typed facts/concepts from documents, exportable as an Obsidian vault). Runs entirely through the connected MCP client's own model — no separate endpoint or API key.
**Why I should care** — Text-to-SQL's real failure mode is a plausible-looking wrong number, not a crash; this project's validate-before-run step directly targets that, with a worked table of concrete failure cases (wrong joins, case-mismatched filters, fan-out double-counting) applicable to any reporting feature on the existing Postgres/MongoDB stack.
**What it could replace** — Hand-rolled "send the schema in the prompt" text-to-SQL that fails silently.
**Ways I could use it** — Add a validated query layer in front of a reporting database; build a personal knowledge base from receipts/statements/notes queryable with exact numbers; export the ontology as a browsable Obsidian vault.
**Agent opportunity** — No model hosting or API key — cost and capability simply track the MCP client already in use.
**Integration effort** — Low — local MCP server, local SQLite storage, a demo command to try before pointing at real data.
**Maturity** — Experimental (19 days old, no tagged release yet).
**License** — Apache-2.0, no restrictions.
**Alternatives** — WrenAI, Chat2DB-style text-to-SQL (already evaluated) lack the explicit validate-before-run step; claude-self-reflect/ClickHouse-loom (catalogued) overlap only the knowledge-base half.
**Why this one** — The validate-before-run ontology check is a concrete, checkable safety mechanism, not a generic "AI-powered SQL" pitch.
**Recommendation** — Try the bundled demo against a real reporting use case; re-evaluate once it ships a tagged release.

### 5. InferSSD — 7.4/10
**Decision:** PROTOTYPE

**What it is** — A local inference runtime built on llama.cpp that runs mixture-of-experts GGUF models larger than available RAM/VRAM by streaming experts from SSD, with a browser chat UI and an OpenAI-compatible API. Tested against named models up to 763B total parameters.
**Why I should care** — Makes large open-weight models usable on commodity hardware without buying workstation-class GPU memory — useful for cost-free experimentation or benchmarking before committing to a paid hosted model.
**What it could replace** — Recurring per-token API cost during iterative prompt/tooling development, via a local model behind an OpenAI-compatible endpoint.
**Ways I could use it** — Evaluate a new open-weight model release before paying for hosted inference; point an agent harness's OpenAI-compatible client at it for free local dev-time testing.
**Agent opportunity** — OpenAI-compatible API drops into any harness already wired for that interface via a base-URL change.
**Integration effort** — Medium — desktop app download, needs SSD I/O headroom and a supported GPU; Windows/Linux GPU backends still in progress.
**Maturity** — Emerging (about a month old, date-based pre-1.0 release tagging).
**License** — Apache-2.0, no restrictions.
**Alternatives** — llama.cpp directly (no SSD-streaming layer); Ollama/LM Studio (mainstream, excluded); cloud inference (no hardware constraint, ongoing cost).
**Why this one** — A specific, benchmarked technical capability (SSD-streamed MoE experts) rather than a generic "run models locally" wrapper.
**Recommendation** — Try on macOS (the only complete platform today) with a real large model before relying on it.
