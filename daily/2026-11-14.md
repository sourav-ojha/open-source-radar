# Open Source Radar — 2026-11-14
_Rotation slot 4 — data, search, documents, RAG_

## Executive Summary
Today's slot surfaced a genuine Postgres-as-search-engine option (ParadeDB), a
security-conscious agentic-PDF-RAG MCP server that treats hidden PDF text as a threat
rather than free context (pdf-mcp), a cross-language Office-document parsing library built
for exactly the Node/TS binding a MERN stack needs, a fast local PDF parser backed by the
official LlamaIndex org, and a lighter alternative to Debezium's Kafka weight for data
replication. Separately, a sweep of the catalog's 64 existing data/search/documents/RAG
entries against the GitHub API turned up four real meaningful updates — most notably
RushDB dropping its Neo4j dependency and split license for a native Rust engine under a
single Apache-2.0 license. A same-org pair (Zleap-AI's SAG/SAG-Wiki) showed the clearest
star-inflation signature seen in several runs and was rejected despite real-sounding
architecture behind it.

## Today's Best Discoveries

### 1. ParadeDB — 8.4/10
**Decision:** PROTOTYPE

**What it is** — A Postgres extension suite that adds BM25-scored full-text search,
vector retrieval, aggregations, and facets inside Postgres itself, so application data and
search live in one database instead of Postgres plus a bolted-on Elasticsearch/OpenSearch
cluster.
**Why I should care** — Most hybrid-search RAG setups end up running two systems kept in
sync by hand; this collapses that into one database with real BM25 ranking (Block-Max
WAND, top-k) rather than Postgres's weaker built-in `tsvector` search.
**What it could replace** — A standalone Elasticsearch/OpenSearch/Typesense/Algolia
cluster for any product where Postgres is already the system of record.
**Ways I could use it** — Add BM25 + vector hybrid search to an existing Postgres database;
run RAG retrieval entirely in Postgres against the same tables as the application data;
self-host on an existing EKS cluster via the CloudNativePG operator; replace a bolted-on
search SaaS integration.
**Agent opportunity** — None beyond standard SQL access — any agent or tool that already
talks to Postgres can use it with no new interface.
**Integration effort** — Medium: it's a Postgres extension, so it means managing a custom
Postgres build or extension loading, not dropping in a sidecar service.
**Maturity** — Mature (created 2023-06-30, ~3.3 years; 9,511 stars, 512 forks, 43
subscribers; active Slack; latest v0.26.6, 2026-11-08).
**License** — **AGPL-3.0 — flagged loudly.** Self-hosting or internal use is unaffected,
but offering it as a hosted service to third parties triggers AGPL's source-disclosure
requirement without a commercial license from ParadeDB.
**Alternatives** — pg_textsearch (catalogued, lighter/BM25-only/permissive); pgvector
(vector-only); Elasticsearch/OpenSearch/Typesense/Algolia (separate infra); Infino
(catalogued, embedded library rather than a database extension).
**Why this one** — It's the only option here that keeps search *inside* Postgres's own
transaction model rather than syncing a second system, with three years of production
history behind it.
**Recommendation** — Stand it up against a non-production Postgres database with a real
hybrid-search workload and compare ranking quality against the current setup before any
production decision — and price in the AGPL question up front if hosting is on the table.

### 2. pdf-mcp — 8.2/10
**Decision:** PROTOTYPE

**What it is** — An MCP server giving coding agents agentic RAG over one PDF or a folder
of PDFs: hybrid BM25+semantic search, selective page reads instead of whole-document
ingestion, table/chart/scanned-text extraction, and page-level evidence so an agent can
render a page and check extracted text against what's actually printed. Hidden text,
including prompt-injection attempts, is flagged rather than silently passed through.
**Why I should care** — Most document-RAG tooling optimizes purely for recall and trusts
extracted text blindly. This treats a PDF's text as untrusted input by default — a
genuinely novel safety property for any agent workflow that reads documents from outside
sources.
**What it could replace** — Dumping a whole PDF into an agent's context window to answer
one question about it, and the blind trust most pipelines place in extracted text.
**Ways I could use it** — Let Claude Code search/read a folder of PDFs without burning
context on every page; verify an agent's extracted answer against the rendered page before
trusting it for anything finance- or compliance-adjacent; flag PDFs carrying hidden/
injected text before an agent acts on them.
**Agent opportunity** — Native MCP server, install and use as-is inside Claude Code or any
MCP client with no custom glue.
**Integration effort** — Low: `pip install pdf-mcp`, runs as an MCP server over stdio.
**Maturity** — Emerging (created 2026-01-28, ~10 months; 171 stars, 17 forks, 2
subscribers; PyPI package, CI, codecov; latest v3.8.0, 2026-11-14).
**License** — MIT, no restrictions.
**Alternatives** — unpdf/undoc, Dedoc, oxidize-pdf (all catalogued) — parsing-focused, no
MCP server or evidence-check loop; manually dumping PDF text into context.
**Why this one** — The injected-text flagging plus page-evidence verification loop is a
distinct safety property, not just another extraction pipeline.
**Recommendation** — Wire it into a real Claude Code session against a folder that includes
at least one PDF with embedded/hidden text, and confirm the flagging and evidence loop
behave as advertised before relying on either.

### 3. Office Oxide — 8.0/10
**Decision:** PROTOTYPE

**What it is** — A memory-safe Rust library for text extraction from Office documents
(DOCX, XLSX, PPTX, DOC, XLS, PPT) with first-class native bindings for Python, Go, C#/.NET,
Node.js (native and WASM), and a stable C FFI. Claims 5-10x the speed of python-docx/
openpyxl/python-pptx/xlrd and a 97.3% open rate across a 10,386-file test corpus.
**Why I should care** — Office-document parsing in a Node/TS stack usually means a
format-limited JS library or shelling out to Python. This gives a real native Node package
(not just WASM) with benchmarked performance across six formats, from one codebase.
**What it could replace** — A separate Python microservice or LibreOffice-headless step
just to extract text from uploaded Office documents.
**Ways I could use it** — Parse user-uploaded DOCX/XLSX/PPTX in a Node backend directly;
handle legacy DOC/XLS/PPT from the same library; run the WASM build client-side for a
privacy-preserving document preview with no server round-trip.
**Agent opportunity** — None built in; a library, so an agent tool would need a thin CLI/
API wrapper.
**Integration effort** — Low: native npm package or WASM, embeddable directly.
**Maturity** — Emerging (created 2026-03-01, ~8 months; 167 stars, 27 forks, 1 subscriber;
CI configured, docs.rs documentation; latest v0.1.17, 2026-11-11).
**License** — Dual MIT/Apache-2.0, no restrictions.
**Alternatives** — python-docx/openpyxl/python-pptx/xlrd (Python-only, slower per its own
benchmarks); Apache POI/Tika (JVM-dependent); mammoth.js/docx4js (narrower coverage).
**Why this one** — One Rust core bound natively into six language ecosystems, rather than
six independent reimplementations of the same parsing logic.
**Recommendation** — Try the Node native binding against a real sample of user-uploaded
Office documents, including a few legacy formats, before replacing an existing
Python-based parsing step.

### 4. LiteParse — 7.9/10
**Decision:** PROTOTYPE

**What it is** — A standalone, local-only PDF parsing library from the official LlamaIndex
org, focused on fast and light spatial text extraction (PDFium-based, ~2-5ms/page) with a
pluggable OCR system and complexity detection that flags documents needing heavier
processing before a full parse. No cloud dependency in the open-source core; explicitly
escalates only the hard documents to the paid LlamaParse cloud product.
**Why I should care** — Backed by the official run-llama org rather than a solo
maintainer, honestly scoped (fast local parsing, not a RAG framework), with real bindings
across four language ecosystems from one codebase.
**What it could replace** — Paying for cloud document parsing on the simple majority of
PDFs, by pre-filtering locally and only escalating genuinely hard documents.
**Ways I could use it** — Fast first-pass extraction in a document pipeline with
complexity-based routing; generate page screenshots for an agent's own verification loop
(similar in spirit to pdf-mcp, above); plug in an existing OCR server instead of being
locked into one engine.
**Agent opportunity** — None built in; page-screenshot generation is a useful primitive
for an agent verification loop but would need to be wired up.
**Integration effort** — Low: crates.io, npm (native + WASM), or PyPI package.
**Maturity** — Emerging but well-backed (created 2026-02-09, ~9 months; 13,043 stars, 900
forks, 37 subscribers; latest node-v2.19.0, 2026-11-13).
**License** — Apache-2.0, no restrictions.
**Alternatives** — OpenDataLoader PDF, Dedoc, oxidize-pdf, unpdf (all catalogued, broader
structure-aware focus); LlamaParse (same org's paid cloud escalation path); unstructured.io/
docling (heavier).
**Why this one** — Official LlamaIndex backing plus an honest "fast parsing only, cloud for
the hard cases" scope, rather than another all-in-one document framework.
**Recommendation** — Benchmark it against a representative sample of real (not just clean)
documents to see how often the complexity detector escalates before deciding whether it
replaces an existing parsing step.

### 5. Filament — 7.7/10
**Decision:** PROTOTYPE

**What it is** — A pluggable data-replication engine (full, incremental, or CDC) with
durable checkpointing, two-sided batch integrity verification, and safe pause/resume.
Sources, sinks, state storage, and event transport are all replaceable interfaces; runs as
a standalone service with an API/web UI or embeds in a Go application.
**Why I should care** — Sits between a hand-rolled sync script (easy to get subtly wrong on
a crash mid-sync) and Debezium's full Java/Kafka stack, as a single Go binary with real
checkpoint/integrity guarantees.
**What it could replace** — A hand-rolled sync script, or a Debezium/Kafka deployment that
is heavier than the actual job needs.
**Ways I could use it** — Replicate Postgres/MySQL data to a search index or warehouse
without Kafka; use where the already-catalogued go-pq-cdc's Postgres-only scope is too
narrow; embed the engine directly inside a Go service.
**Agent opportunity** — REST API is straightforward for an agent to drive replication jobs
via HTTP calls if wired up; no MCP server.
**Integration effort** — Medium: production is a single binary, but local development
needs Go, Docker, Node.js, pnpm, and NATS.
**Maturity** — Emerging (created 2026-06-30, ~5 months; 309 stars, 42 forks, 2
subscribers; CI configured, Slack community; latest v0.43.0, 2026-11-14).
**License** — Apache-2.0, no restrictions.
**Alternatives** — Debezium (mainstream, heavier); go-pq-cdc (catalogued, Postgres-only);
Airbyte (mainstream, much larger connector catalog).
**Why this one** — Pluggable source/sink model plus real checkpoint/integrity guarantees in
a single binary, filling a real gap between a sync script and a full CDC stack.
**Recommendation** — Run a real replication job through a deliberate crash-and-resume test
before trusting its checkpoint guarantees with anything production-critical.

## Meaningful Updates
**RushDB** — PROTOTYPE (Neo4j-backed, split Elastic License 2.0/Apache-2.0) → PROTOTYPE
(native Rust engine, single Apache-2.0 license). v3.0 (2026-10-28, "RushDB 3.0 — Rust
engine (LMPG)") replaced the Neo4j-backed core with a native Rust storage engine exposing
Postgres-wire, Bolt, and gRPC protocols plus TLS and tenant-bound capability tokens, and
simultaneously retired the split Elastic License 2.0 (`platform/core`/`platform/dashboard`)
for a single Apache-2.0 license across the repo. This resolves both limitations ("hard
dependency on Neo4j" and the ELv2 hosted-service caveat) the original 2026-09-12 review
flagged. Why it matters: the project went from "API layer over someone else's graph
database with a commercial-use caveat" to "its own storage engine, plainly licensed" in one
release. Does this change the recommendation: score raised 7.4 → 7.9, still PROTOTYPE given
the Rust engine is three weeks old. Catalog updated: Yes.

**PipesHub AI** — PROTOTYPE (pre-1.0) → PROTOTYPE (1.0, maturity jump). v1.0.0
(2026-10-27) adds code graphs, more capable retrieval/agent tools, and stronger permission
enforcement, with a breaking change (SAML and generic OAuth sign-in removed). Why it
matters: clears the "pre-1.0, young for a permission-sensitive system" risk the original
review flagged, while strengthening the project's core differentiator (permission-aware
retrieval). Does this change the recommendation: score raised 7.8 → 8.0, still PROTOTYPE —
audit the ACL-inheritance logic and auth-provider compatibility before upgrading. Catalog
updated: Yes.

**LibreDB Studio** — USE NOW → USE NOW (expanded scope). 1.2.0 (2026-10-31) added
OpenShift/Rancher support (operator, console plugin, cluster-account sign-in); 1.3.0
(2026-11-10) opened MCP/the read-only agent to most connected engines, gave each MCP token
its own tool list, and added per-engine write-permission recording so "read-only" means the
same thing in the form, the seed file, and the agent. Why it matters: extends both the
Kubernetes-native deployment story (relevant to EKS) and the agent-facing permission
granularity this project was already differentiated on. Does this change the
recommendation: score raised 8.6 → 8.7, recommendation unchanged. Catalog updated: Yes.

**Markdown Vault MCP** — PROTOTYPE → PROTOTYPE (architecture improvement). v6.0.0
(2026-11-01) moved embeddings from in-memory numpy files into an incrementally-written
SQLite database, keeping semantic search usable as a vault grows. v6.1.0 (2026-11-02) added
a terminal client that searches/reads/explores a server-published vault over MCP with a
bearer token and no local vault copy. Does this change the recommendation: score raised
7.1 → 7.3, recommendation unchanged. Catalog updated: Yes.

## Small but High-Leverage Utility
**Bank Statement Parser** — parses bank statements across eight structured formats (CAMT,
PAIN.001, MT940, MT942, OFX/QFX, BAI2, CSV) plus digital and scanned PDFs into one unified,
auditable Transaction model, with treasury analytics, two-way reconciliation, and
Parquet/ledger (hledger, beancount) exports. Maintained since 2023 with real test coverage,
dual Apache-2.0/MIT licensed (the GitHub API misreported NOASSERTION — confirmed by reading
LICENSE-APACHE and LICENSE-MIT directly). Narrow (only useful for a finance/billing-
reconciliation feature), but it replaces exactly the kind of multi-week, format-by-format
integration slog that this kind of feature otherwise burns real time on.
