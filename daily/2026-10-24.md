# Open Source Radar — 2026-10-24
_Rotation slot 4 — data, search, documents, RAG_

## Executive Summary
Today's discovery search was dominated by noise — a generic GitHub search for "RAG"/"vector
search"/"document parsing" today returns almost entirely zero-star same-hour student projects and
a new recurring pattern of "API Evangelist" third-party profile repos (not actual tools, just
descriptions of other companies' APIs). The signal that did surface clustered around agent-facing
document/knowledge infrastructure that goes beyond flat vector search: a markdown-native knowledge
graph agents and humans build together (sage-wiki), an embedded Parquet-backed hybrid-search
library (Infino), a pure-Rust PDF toolkit with built-in RAG chunking (oxidize-pdf), and a
document-intelligence platform with a genuinely newer dual vision+text architecture whose
self-hosted path turns out to depend on a third-party parsing API (Knowhere). Two already-
catalogued projects in this slot's niche — schemagate and Tela — shipped real feature work worth
recording as updates.

## Today's Best Discoveries

### 1. sage-wiki — 8.2/10
**Decision:** PROTOTYPE

**What it is** — A graph memory and knowledge base that AI agents and humans build and query
together. Drop in documents; an LLM compiler extracts entities/relations into an interlinked wiki
with a knowledge graph. Agents query it over MCP (19 tools); humans browse the same data as
Obsidian-native markdown. An opt-in "evidenced graph" mode adds typed relations, provenance,
confidence scores, and per-fact citations. One Go binary scales from a personal vault to a
Postgres/pgvector-backed team or company hub.
**Why I should care** — Most agent-memory tools are either a vector store with no relational
structure, or a graph database with no human-readable surface. sage-wiki is both: markdown I can
read in Obsidian and a compiled knowledge graph an agent can traverse and cite through MCP.
**What it could replace** — Re-explaining project context to an agent every session; hand-building
entity resolution and citation tracking for an internal "ask your docs" feature.
**Ways I could use it** — Overlay an existing Obsidian vault and run on local models for a
zero-cost personal knowledge base; ask multi-hop relational questions through `wiki_graph_query`;
share one wiki via git as a lightweight, agent-writable team knowledge hub; turn on evidenced-graph
mode when an answer needs to cite its source; scale storage to Postgres/pgvector for team use.
**Agent opportunity** — 19 MCP tools plus generated agent-skill files; review-gated entity
resolution is a concrete pattern for safe agent-driven data cleanup.
**Integration effort** — Low for personal use (single binary); medium once moving to a shared
server with a Postgres backend.
**Maturity** — Emerging (created 2026-04-04, v0.2.12, 637 stars, 105 forks, 10 contributors).
**License** — MIT, unrestricted commercial use.
**Alternatives** — Graphiti (32k stars, mainstream real-time agent knowledge-graph library, more
of a general SDK than a human-browsable wiki); plain vector-store RAG (no multi-hop or citations).
**Why this one** — The dual human/agent interface over the same data, not a bolted-on chat layer.
**Recommendation** — Prototype on a real personal vault before trusting it as a team knowledge
hub; stars:watchers ratio (159:1) is elevated enough to re-check on the next review even though
contributor count and release cadence argue against it being inflated.

### 2. Infino — 7.8/10
**Decision:** PROTOTYPE

**What it is** — An embedded retrieval library (Rust core, Python/Node/Rust bindings) doing
full-text (BM25), vector, hybrid, and SQL query over one Parquet-backed table, on local disk or
object storage, with published warm-latency benchmarks at 1M/10M documents.
**Why I should care** — Adding search or RAG retrieval to a small product feature usually means
standing up a separate service; Infino folds BM25 + vector + SQL into one embeddable, npm-installable
table.
**What it could replace** — A hand-wired Postgres-FTS-plus-pgvector combo, or a separate search
cluster, for a feature that doesn't need that much infrastructure.
**Ways I could use it** — `npm install @infino-ai/infino` for hybrid search in a small
Node/Express service with no search infra; store the index as Parquet on S3/R2 for a serverless
deployment; prototype locally (`memory://`) then move to object storage unchanged; embed inside
an MCP server as the retrieval backend.
**Agent opportunity** — Light enough to embed directly inside an MCP server or custom agent tool.
**Integration effort** — Low — `npm install`/`pip install`/`cargo add`, runs in-process.
**Maturity** — Emerging (created 2026-05-19, pre-1.0 at v0.11.11, 139 stars, 14 contributors).
**License** — Apache-2.0, unrestricted commercial use.
**Alternatives** — pgvector+Postgres FTS (free if Postgres is already there, but you run it);
Qdrant/Weaviate/Milvus (heavier, more capable at scale); turbopuffer/Marqo (similar design, cloud-first).
**Why this one** — One embeddable table instead of operating a separate search service.
**Recommendation** — Prototype on a small service that currently has no real search, or fakes it
with a SQL `LIKE` query.

### 3. oxidize-pdf — 7.6/10
**Decision:** PROTOTYPE

**What it is** — A pure-Rust PDF toolkit (no C bindings, no native crypto library) for generating,
parsing, modifying, extracting from, and validating PDFs — including PDF/A validation and
signature verification — with a built-in `rag_chunks()` method returning structure-aware chunks
(text, page numbers, bounding boxes, element types, heading context, token estimates).
**Why I should care** — One dependency-free crate instead of juggling separate libraries for
generation, parsing, and validation, each potentially pulling in native C dependencies that
complicate container builds.
**What it could replace** — pdfium/poppler/LibreOffice-headless where deployment simplicity
matters more than feature parity; hand-built chunk metadata after parsing with a text-only library.
**Ways I could use it** — Swap in for a native-dependency PDF library in a Docker image that
should stay dependency-light; generate RAG chunks directly from parsing; run as a small sidecar
service from a Node/Express backend; validate PDF/A compliance or signatures without a Java tool.
**Agent opportunity** — Wrap as a small MCP server/CLI for an agent that needs PDF read/generate/
chunk without a heavyweight Python/C stack.
**Integration effort** — Medium for a MERN stack — no official Node/WASM bindings yet, so it runs
as a Rust binary or sidecar rather than a direct `npm install`.
**Maturity** — Emerging but longer-lived than most new entries (created 2025-07-07, v5.5.1, 7,993
tests, 192 stars, 12 contributors).
**License** — MIT, unrestricted commercial use.
**Alternatives** — pdf-parse/pdf.js (Node-native, text-only, no PDF/A validation); PyMuPDF/
pdfplumber (Python + native deps); unpdf/undoc (already catalogued, has npm/WASM bindings but no
generation/PDF-A/signature support).
**Why this one** — Covers generate/parse/modify/extract/validate in one crate, plus a
`docs/CLAIMS.md` claims inventory — an unusually rigorous practice for a small project.
**Recommendation** — Prototype as a sidecar for a document-ingestion pipeline needing
structure-aware PDF chunks; the missing Node bindings are the main adoption blocker.

### 4. Knowhere — 6.8/10
**Decision:** STUDY

**What it is** — A document parsing and retrieval system turning unstructured files (including
long/complex PDFs and PowerPoint) into hierarchy-aware agent memory, with dual Vision + Text
parsing tracks converging into one cited schema, and an "agent-native retrieval" MCP mode where
the agent chooses how to search/traverse/cite rather than running a fixed RAG pipeline.
**Why I should care** — The dual-track parsing and agent-native retrieval design is a genuinely
more current take on document RAG than most catalogued parsers — but the documented self-hosted
path requires a MinerU API key for PDF parsing and a DeepSeek/Alibaba LLM key by default, which
undercuts the "self-hosted" framing for anyone who wants it without a third-party dependency.
**What it could replace** — In principle, a from-scratch hierarchy-aware document memory system;
in practice, adopting it also means adopting its external API dependencies.
**Ways I could use it** — Study the vision/text parsing split for mixed scanned+text documents;
reference implementation for agent-native (rather than fixed-pipeline) MCP retrieval.
**Agent opportunity** — MCP-native hierarchy-aware navigation tools (not just flat chunk search)
is a pattern worth copying independent of adopting Knowhere itself.
**Integration effort** — High — the self-hosted path's default dependency on MinerU/DeepSeek/
Alibaba APIs needs to be worked around for a fully local deployment, and that path isn't fully
documented.
**Maturity** — Emerging (created 2026-04-30, v1.2.30, 3,756 stars, 338 forks, 9 contributors,
company-backed with a managed-cloud free-credits offer).
**License** — Core repo Apache-2.0; the self-hosted deployment repo has no separate license.
**Alternatives** — OpenDataLoader PDF, Dedoc, unpdf/undoc (already catalogued, fully
self-contained, no mandatory third-party API); LlamaParse, Mindee, Unstructured (comparable
managed APIs, similarly cloud-first).
**Why this one** — The agent-native retrieval idea is worth reading even though direct adoption
is blocked by the API dependency today.
**Recommendation** — Study the architecture; don't adopt until a fully local parser/LLM
substitution path is proven out, per AGENT.md's standing penalty for "open-source" tools
functionally unusable without proprietary infrastructure.

## Small but High-Leverage Utility
**chunklet-py** (speedyk-005/chunklet-py, MIT, 88 stars) — a Python text-splitter for RAG
pipelines that chunks by sentence/paragraph/code boundaries rather than character counts, with
automatic language detection across 60+ languages and chunk-overlap/metadata support. Text
chunking is a small job every RAG pipeline reinvents badly — splitting mid-sentence, ignoring
language boundaries, losing context between chunks — and a focused, CI-tested library for exactly
this one job is worth dropping into any Python-side document-ingestion script immediately rather
than hand-rolling it again.

## Worth Watching
- **tokensave** (aovestdipaperino/tokensave, MIT, 676 stars, 41 contributors) — a Rust/libSQL
  code-intelligence MCP server (semantic search, call-graph traversal, impact analysis across 50+
  languages). Genuinely strong traction, but it's another entrant in an already-saturated
  code-search-for-agents niche (jevgrep, Semble, ripwire, Sourcebot, CocoIndex ccc are all already
  catalogued). Its call-graph "impact radius before you change code" angle would need to prove out
  as clearly distinct from ripwire's code-graph focus before it earns a full catalog slot.
- **searchlite** (davidkelley/searchlite, 0 stars) — an embedded Rust search engine (BM25 with
  phrase matching, filters, highlighting, optional vectors) exposing a CLI, Rust API, and
  C/WASM bindings in a small footprint. Interesting architecture choice (WASM bindings would solve
  exactly the gap oxidize-pdf and Infino don't), but zero independent traction yet — would need
  real users or a release history to take seriously.
- **rampart** (aflin/rampart, 28 stars) — an "old-school JavaScript" runtime with fast C-backed
  full-text/vector search, SQL, LMDB, Redis, HTTPS, WebSockets, and crypto bundled into one
  engine. Unusual kitchen-sink scope makes it hard to place; would need a clearer "this is what you
  use it for" story to move past Worth Watching.
