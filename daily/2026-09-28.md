# Open Source Radar — 2026-09-28
_Rotation slot 6 — infrastructure, observability, deployment_

## Executive Summary
Today's slot 6 pass turned up a genuine eBPF cluster: two independent tools (AgentSight, Qtap) use kernel-level tracing to get visibility that would otherwise require SDKs, proxies, or certificate trust — one aimed at AI coding agents specifically, the other at general egress traffic. Alongside that, two developer-productivity finds attack the same underlying problem from different angles — making third-party API mocking and failure simulation genuinely good instead of an afterthought — with mockd betting on protocol breadth plus an MCP server, and Pikopod betting on spec-derived, production-fidelity failure scenarios. The mainstream corners of this slot (Terraform drift detection, blue-green/canary deployment, service mesh) were dominated by same-week hackathon-grade repos and tutorial/lab projects with no independent value, filed under Rejected rather than reviewed individually.

## Today's Best Discoveries

### 1. AgentSight — 8.6/10
**Decision:** PROTOTYPE

**What it is** — A local-first, eBPF-based `top`/`strace` for AI coding agents: it observes prompts, model calls, tool decisions, and their real file/network/process effects for any running agent (Claude Code, Codex, Gemini CLI, OpenCode, OpenClaw, or an arbitrary command), with no SDK, proxy, or vendor integration.
**Why I should care** — Application-level agent observability tools (LangSmith, Langfuse, Phoenix) require owning the agent's source; gateway tools (Helicone) require routing its LLM traffic through a proxy. AgentSight watches OS-level effects instead, which is the only approach that works against a closed-source CLI agent binary.
**What it could replace** — Manually correlating an agent's self-reported logs with what it actually touched on disk/network when a run stalls or misbehaves.
**Ways I could use it** — Auditing what a coding agent actually did during a session; diagnosing retry loops or runaway tool-call spend; security review of agent-initiated network/file activity before granting more autonomy; flamegraph profiling of where a session's time went.
**Agent opportunity** — It *is* the observability layer for agent tools — pairs directly with any coding-agent workflow already in use.
**Integration effort** — Low (single `cargo install` or prebuilt binary), but Linux-only and requires eBPF support and elevated privileges.
**Maturity** — Emerging. Created 2025-07-07, 710 stars, 106 forks, latest release v1.0.31 (2026-09-05). Backed by a published paper (arXiv:2508.02736, also an ACM venue, DOI:10.1145/3766882.3767169).
**License** — MIT. No restrictions.
**Alternatives** — LangSmith, Langfuse, Arize Phoenix (app-level), Helicone (gateway-level) — all require owning or routing the agent's traffic, unlike AgentSight.
**Why this one** — The only entrant that treats a closed-source coding-agent binary as a black box and still gets full visibility, via kernel-level tracing rather than instrumentation.
**Recommendation** — Prototype it against an existing Claude Code / Codex workflow before relying on it for anything beyond local debugging.

### 2. Qtap — 8.0/10
**Decision:** PROTOTYPE

**What it is** — An eBPF agent that attaches to TLS/SSL functions in the kernel to show the unencrypted contents of all egress traffic on a host — full request/response bodies with process/container/user/protocol context — without a proxy, cert management, or app changes.
**Why I should care** — Most traffic-inspection tools need either a proxy with cert trust configured, or access to TLS keys. Qtap decrypts at the kernel boundary, so it works against any process on a host, including ones I don't control.
**What it could replace** — Adding temporary logging to a service just to see what it sends to a third-party API, or standing up mitmproxy with cert trust for one debugging session.
**Ways I could use it** — Debugging a misbehaving third-party integration without touching app code; security auditing outbound traffic from an EC2/ECS/EB workload; reverse-engineering an undocumented internal service; confirming a deploy didn't change wire behavior.
**Agent opportunity** — None built in, but the CLI output is scriptable enough to hand a coding agent as a live debugging tool.
**Integration effort** — Medium. Requires Linux kernel 5.10+ with BTF, and privileged/CAP_BPF host or container access.
**Maturity** — Emerging. Created 2025-04-16, 1,460 stars, 55 forks, active multi-contributor team (Qpoint.io). No tagged GitHub releases at all — always tracks `main`.
**License** — Apache-2.0. The agent is the free/open core of Qpoint's commercial hosted product; standalone use is explicitly supported.
**Alternatives** — mitmproxy (needs proxy + cert trust), tcpdump/Wireshark (no TLS decryption without keys), application-level API gateway logging.
**Why this one** — Kernel-boundary TLS decryption is a fundamentally different (and lower-friction) approach than every proxy-based alternative.
**Recommendation** — Prototype in a controlled/non-production environment given the privileged-access requirement and complete absence of release versioning.

### 3. mockd — 8.1/10
**Decision:** PROTOTYPE

**What it is** — A single Go binary that mocks HTTP, gRPC, GraphQL, WebSocket, MQTT, SSE, and SOAP from one CLI, with OpenAPI/Postman/HAR/WSDL import, stateful CRUD mocks, chaos-injection profiles, circuit breakers, and a local MCP server so a coding agent can create or mutate mocks itself.
**Why I should care** — Every mainstream mock tool forces a trade-off: one protocol, a JVM/Electron runtime, or a paid cloud tier for chaos/circuit-breaker features. mockd bundles nine protocols and fault injection into one dependency-free Apache-2.0 binary.
**What it could replace** — Standing up WireMock or MockServer (both JVM) to mock one HTTP endpoint; separate ad hoc tools per protocol when an integration spans HTTP + WebSocket + MQTT.
**Ways I could use it** — Mocking a third-party payment/messaging API before real credentials exist; integration tests against WebSocket/MQTT/gRPC without real infrastructure; chaos-testing client resilience pre-production; letting a coding agent generate a mock backend for a frontend task via its MCP server.
**Agent opportunity** — Ships a local MCP server specifically so an agent can generate/modify mocks — explicit, first-class agent integration, not an afterthought.
**Integration effort** — Low. `go install`, Homebrew, Docker, or a prebuilt binary; zero runtime dependencies.
**Maturity** — Emerging. Created 2026-02-04, 147 stars. Solo-maintainer project (one contributor accounts for the overwhelming majority of commits); latest tagged release (v0.7.1, 2026-06-21) trails the last `main` push (2026-09-17) by roughly three months.
**License** — Apache-2.0, unrestricted. Managed SaaS tier listed as roadmap, not live.
**Alternatives** — WireMock, Mockoon, Prism, MockServer, Beeceptor, json-server — mockd's own README compares against all six (treat those specific claims as marketing, not verified independently).
**Why this one** — The MCP server plus 9-protocol breadth in one binary is a combination none of the incumbents offer together.
**Recommendation** — Prototype on a real integration; watch for the bus-factor risk and the release/main-branch lag before depending on it.

### 4. Pikopod — 7.8/10
**Decision:** PROTOTYPE (young — treat as an experiment)

**What it is** — A Go binary that builds a deterministic failure-injection sandbox from a third-party API's own OpenAPI spec (declines, timeouts, retry storms, duplicate webhooks) with no fixtures authored by hand, a fail-open recording proxy that fingerprints real production failures into replayable scenarios, and a spec-diff CI gate that fails a build on a breaking provider API change.
**Why I should care** — A provider's own sandbox can't be asked to return a specific failure at a specific point in a state machine. Pikopod derives failure archetypes from the provider's spec and can replay an exact production failure on demand.
**What it could replace** — Hand-authored mock fixtures for every failure mode of a third-party integration; discovering a breaking API change only after a deploy fails; manually reconstructing a production incident to write a regression test.
**Ways I could use it** — Testing payment/webhook retry and idempotency logic against realistic failures; catching breaking provider spec changes in CI; turning a real incident into a permanent regression test; building a Stripe/Razorpay-style resilience suite beyond what the provider's sandbox supports.
**Agent opportunity** — CLI is fully scriptable; could be wrapped as an MCP tool for a coding agent to generate resilience scenarios for a newly integrated API.
**Integration effort** — Low. `go install` or a signed release binary; documented GitHub Actions integration.
**Maturity** — Experimental. Created 2026-09-11 (~2.5 weeks old), 66 stars, pre-1.0 at v0.1.2. Some listed "contributors" are dependabot.
**License** — Apache-2.0, unrestricted.
**Alternatives** — Hand-rolled fixtures; mockd/WireMock-style general fault injection (not spec-derived); the provider's own sandbox.
**Why this one** — Unusually mature supply-chain practices (cosign-signed releases, SLSA provenance) for a 2.5-week-old project, and a genuinely novel spec-to-failure-archetype approach.
**Recommendation** — Watch closely and try it on one low-stakes integration; too young to lean on for anything critical yet.
