# Open Source Radar — 2026-11-26
_Rotation slot 2 — product infrastructure, APIs, backend components_

## Executive Summary
Today's strongest finds cluster around a theme: serious engineering teams open-sourcing narrow
building blocks they built to solve their own production problem, rather than speculative
"platform" plays. A production cloud operator open-sourced the S3 client-side encryption proxy
it needed after discovering its own Postgres backups were landing on S3 unencrypted; Gusto's
engineering org published a genuinely novel serverless document database that runs entirely
inside a request handler with no resident server; and a small Czech company shipped a
disciplined, well-tested single-binary replacement for cron+supervisord. Separately, a very
small but unusually rigorously documented open-source form engine (arc42 architecture docs,
numbered ADRs, regulatory SOUP declarations) turned up with native MCP tooling for agent-driven
form authoring — a reminder that star count is a poor proxy for engineering quality in this
corner of GitHub.

## Today's Best Discoveries

### 1. formancy.ai — 8.3/10
**Decision:** PROTOTYPE

**What it is** — A self-hostable, fully open-source (Apache-2.0) visual form builder and
rendering engine for Angular and React, sharing one compiled validation/condition/calculation
engine across browser and server, with an optional Fastify+Postgres backend for submissions.
**Why I should care** — Forms-with-logic recur in nearly every product; this is the rare fully
open option with a real visual builder (not just a headless library) where client and server
rules literally cannot drift, since both run the same compiled engine.
**What it could replace** — Typeform/Tally/Feathery subscriptions for anything beyond a trivial
intake form, plus the usual hand-maintained duplicate of form-validation logic between frontend
and backend.
**Ways I could use it** — Multi-step intake/application forms with conditional fields and
calculated totals; a self-hosted submissions backend (drafts, file uploads, CSV export, webhooks,
audit log) instead of a form SaaS; embedding a themeable headless renderer into an existing
design system; letting a coding agent draft and validate a form definition via MCP before
deploying it.
**Agent opportunity** — MCP server ships 9 tools; 5 need no server or credentials
(`describe_spec`, `validate_form`, `diff_forms`, `check_scenarios`, the checking half of
`publish_form`), so an agent can write and validate a whole form offline. CEL-based type-checking
catches a model's logic mistakes before they ship.
**Integration effort** — Low for the renderer/library (`npm install @formancy/react`, Node
>= 22.12); Low-Medium for the self-hosted backend, which the project's own docs say is "not ready
for a public deployment" yet.
**Maturity** — Emerging/beta (v0.14.0). Unusually deep CI/SBOM/provenance tooling for a 56-star,
0-subscriber repo.
**License** — Apache-2.0 for the spec/engine/renderers/builder/backend. Three adjacent paid
modules (Data, Report, Health) live in separate repos under a source-available license — flagged,
but they're optional add-ons, not the core.
**Alternatives** — SurveyJS (dual-licensed, not fully open), Feathery (hosted-first),
react-hook-form (headless library only, no builder or backend), Typeform/Tally (closed SaaS).
**Why this one** — The only fully-open, dual-framework option with a shared engine, an MCP-native
authoring path, and documentation rigor (ADRs, accessibility conformance, regulatory SOUP
declarations) well beyond what its star count would suggest.
**Recommendation** — Prototype the renderer/builder on a real form now; treat the self-hosted
backend as an evaluation target, not production, until its own documented gaps close.

### 2. S3 Encryption Gateway — 8.0/10
**Decision:** PROTOTYPE

**What it is** — A transparent HTTP proxy that sits in front of any S3-compatible backend (AWS,
MinIO, SeaweedFS, Hetzner) and client-side encrypts objects on write / decrypts on read, with no
application code changes.
**Why I should care** — The realistic S3 exposure risk is a misconfigured IAM policy or a leaked
key, not a compromised cloud provider; this holds even when the first line of defense fails, in
one place, for every application.
**What it could replace** — Having to individually retrofit client-side encryption into every
tool that writes to S3 (backup tooling, log shippers, Terraform state, CI/CD artifacts), including
closed-source tools that can't be modified at all.
**Ways I could use it** — Encrypt CNPG/Postgres WAL backups and dumps before they land on S3;
add a crypto layer in front of Velero/Restic backups or Loki/Thanos logs; protect Terraform state
files (which often contain secrets); a sellable "client-side encrypted everywhere" compliance
answer for the MSSP admin-portal SaaS.
**Agent opportunity** — None directly; it's infrastructure a backup/ops agent would sit behind,
not a tool an agent calls.
**Integration effort** — Low — point the S3 endpoint URL at the gateway instead of the real
backend. Check the published S3 API compatibility matrix against the specific operations in use
first.
**Maturity** — Emerging. Created November 2025, 39 stars/3 subscribers, already running in the
authors' own production per their README, but the current release candidate (v0.13.0-rc3) is
explicitly flagged "for isolated non-production validation only."
**License** — MIT, unrestricted.
**Alternatives** — Intrinsec/s3proxy (AGPL-3.0, older, less active), guided-traffic/
s3-encryption-proxy (5 stars, much smaller).
**Why this one** — Most stars and most mature documentation (compatibility matrix, KMS modes,
benchmarks) among the S3-encryption-proxy entrants, MIT rather than AGPL, and born from a real
production incident rather than a speculative build.
**Recommendation** — Trial against a non-critical backup/log bucket before trusting it with
anything production-critical, given both the pre-1.0 status and the blast radius of getting
encryption wrong.

### 3. baerly-storage — 7.8/10
**Decision:** PROTOTYPE

**What it is** — A document database with no server or daemon: the execution layer runs as
library code inside your request handler, and the data lives directly in an S3/R2 bucket, using
S3's strong consistency plus a conditional-create as the sole commit primitive.
**Why I should care** — Removes a whole category of infrastructure (connection pool, migrations,
pager rotation) for exactly the class of small, single-collection internal tools and MVPs that
make up a large share of micro-SaaS experiments.
**What it could replace** — A throwaway managed Postgres/Mongo instance stood up for a small
internal tool (a kanban board, an RSVP list, one channel's chat) that only ever needs one
collection.
**Ways I could use it** — Zero-infra internal admin tools; micro-SaaS MVPs that graduate to
Postgres (`baerly export --target=postgres`) only once they actually need it; an LLM-friendly
backend where the whole API fits in ~12k tokens of context.
**Agent opportunity** — The deliberately tiny API surface (8 verbs, no SQL) is explicitly
designed to be "small enough to hold in context" for an LLM or non-engineer writing against it.
**Integration effort** — Low — `pnpm create @gusto/baerly-storage@latest`; runs on Cloudflare
Workers+R2 or AWS Lambda+S3. The fit is narrow by design: not for anything needing cross-
collection queries.
**Maturity** — Experimental. Created May 2026, v0.7.0, 25 stars, 0 subscribers — low given it's
published by Gusto's own engineering org, with an accompanying blog post explaining the
rationale.
**License** — Apache-2.0, unrestricted.
**Alternatives** — Firebase/Supabase/Convex (all need a running backend), Cloudflare D1 (a real
SQL database, heavier setup) — the project's own docs compare itself against all three directly.
**Why this one** — None of the alternatives let the "database" disappear entirely between
requests; this is a genuinely different commit architecture (S3-conditional-write log, not a
wrapped SQLite or a hosted service), not a repackaging of an existing idea.
**Recommendation** — Trial on the next small internal tool that would otherwise get its own
throwaway database instance.

### 4. RunWisp — 7.6/10
**Decision:** PROTOTYPE

**What it is** — A self-hosted cron job manager and process supervisor as a single Go binary
(~30MB RAM) with a web dashboard, terminal UI, and REST API — replacing both `crond` and
`supervisord` at once.
**Why I should care** — Removes the recurring "write a tiny dashboard to see why last night's
cron job failed" task on any self-managed server, with run history, live log streaming, and
multi-channel failure alerts built in from the start.
**What it could replace** — A scattered mix of crontab entries plus a hand-rolled process-restart
script with no shared history, dashboard, or alerting.
**Ways I could use it** — Scheduled backup/report jobs and long-running worker services side by
side on an EC2/VPS box; a client-facing ops dashboard for an MSSP/PTaaS delivery box without
standing up a monitoring stack; migrating an existing crontab or docker-compose service list via
the project's documented import paths.
**Agent opportunity** — REST API lets an agent inspect/trigger/stop tasks; task definitions
themselves stay file-based only, by design — no remote mutation.
**Integration effort** — Low — curl installer, Homebrew, apt/rpm, Docker, or tarball; `runwisp.
toml` replaces crontab/supervisord config directly.
**Maturity** — Emerging. Created March 2026, 108 stars/4 subscribers, mentioned in Awesome Go,
with current Codecov coverage and a green SonarCloud security-rating badge.
**License** — GPL-3.0-or-later for the daemon/web UI; Apache-2.0 for shared libraries. Flagged:
fine for self-hosted internal use, review before redistributing a modified binary.
**Alternatives** — crond/systemd timers/supervisord (no dashboard or alerting), Dagu (already
catalogued — broader DAG orchestration, heavier for a straight cron+supervisor swap),
healthchecks.io (hosted monitoring only, doesn't run the job itself).
**Why this one** — The only entrant combining both halves (scheduling *and* process supervision)
in one dependency-free binary with a built-in dashboard, TUI, and REST API, backed by visible
test/coverage discipline from day one.
**Recommendation** — Trial as the cron+supervisor layer on the next self-managed VPS/EC2
deployment before replacing an established crontab/supervisord setup wholesale.

## Small but High-Leverage Utility
**token-throttle** (Elijas/token-throttle, Apache-2.0, Python) implements precise multi-resource
rate limiting for LLM APIs: reserve the declared maximum tokens/requests before a call, then
refund the unused delta once the actual usage is known, coordinated across workers via SQLite (one
host) or Redis (multiple machines). The problem it solves is specific and real — a generic rate
limiter either reserves worst-case tokens and wastes throughput, or undercounts and produces 429s
— and the reserve-then-refund pattern, plus the Redis sorted-locking approach to avoiding
deadlocks across multiple simultaneous resource buckets, is a reusable architecture even outside
Python. Being Python-only (not Node) is the one real friction point for this stack; it's most
useful today either as a sidecar rate-limiting service fronting Node callers, or as a reference
implementation to port the reserve/refund pattern into a TypeScript agent pipeline.
