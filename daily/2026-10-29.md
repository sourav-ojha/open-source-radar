# Open Source Radar — 2026-10-29
_Rotation slot 2 — product infrastructure, APIs, backend components_

## Executive Summary
Today's strongest find sits at the intersection of two usually-separate worlds: identity/IAM and AI-agent safety. Issuerd is a from-scratch, OpenID-Certified IAM server built to be a lighter Keycloak replacement, but its real pitch is DPoP/token-exchange/CIBA support aimed specifically at the problem of an AI agent holding a bearer token for hours and calling downstream services on a user's behalf. That theme — making the IAM/secrets/analytics layer agent-aware rather than agent-agnostic — showed up three more times today: a self-hosted analytics platform shipping its own MCP server with Stripe revenue attribution (OpenAnalytics), and a KeePass-compatible secrets manager built entirely around a per-field MCP approval gate (keypaste), which also stood out as the one credible entrant in a same-week wave of near-identical "secrets for agents" repos. A git-server-as-a-database architecture (Enroute) rounds out the day as a pure study entry, and a production-hardened BullMQ dashboard (Bullpane) was today's small utility pick.

## Today's Best Discoveries

### 1. Issuerd — 8.7/10
**Decision:** PROTOTYPE

**What it is** — A single-binary, OpenID Certified Identity and Access Management server in Rust, deliberately API- and data-model-compatible with Keycloak (realms, clients, roles, Admin REST API), continuously diff-tested against a live Keycloak 24.0 instance.
**Why I should care** — Keycloak's JVM/Quarkus footprint is heavy for a small product team to operate; Issuerd gives the same operational knowledge transfer with a stateless Rust binary. More importantly, it's one of the only self-hosted IAM servers implementing DPoP (RFC 9449), token exchange (RFC 8693), and CIBA specifically for the AI-agent threat model — an agent holding a bearer token for hours, calling many downstream services, reading untrusted input all day.
**What it could replace** — A self-hosted Keycloak deployment; hand-rolled scope-attenuation/step-up-approval logic for agent tool calls touching sensitive data.
**Ways I could use it** — Self-hosted OIDC/SSO for a product's customer and admin-portal auth; DPoP-bound, scope-narrowed tokens for MCP server access; CIBA-gated human approval before a privileged agent action (a refund, a destructive admin operation) executes; LDAP/AD federation for an internal admin panel; migrating an existing Keycloak realm directly given the compatible model.
**Agent opportunity** — This is the authorization layer an MCP server or agent fleet sits behind. Documented demo: a scripted chat agent calling a real MCP server backed by Postgres row-level security, with a stolen token replayed via raw curl rejected (401) and an unapproved refund rejected (403).
**Integration effort** — Low. One binary, Docker image, crates.io package; Postgres + Redis for cluster state; horizontally scalable, no sticky sessions.
**Maturity** — Experimental. Created 2026-09-23 (~5 weeks old), v0.1.24, 70 stars/7 forks/14 open issues (healthy ratio). The OpenID Certified claim was independently verified against the OpenID Foundation's own certification registry — confirmed, not just self-reported.
**License** — Apache-2.0, unrestricted for commercial use and embedding.
**Alternatives** — Keycloak (heavier JVM footprint); Ory Hydra (delegates login/consent elsewhere); Authelia (OIDC provider still beta); ArkGravity/burrow (simpler, no DPoP/CIBA — see Worth Watching).
**Why this one** — Verified certification plus genuinely novel first-class agentic-auth primitives, not just "another Keycloak clone."
**Recommendation** — Prototype it in front of an MCP server or agent-tool integration that currently forwards a user's standing token; too young (one month) to replace a production Keycloak deployment outright yet.

### 2. OpenAnalytics — 7.4/10
**Decision:** PROTOTYPE

**What it is** — A self-hostable, privacy-first, cookieless web analytics platform (Plausible/Fathom/Umami niche) built as a real multi-service architecture (tracker, collector, ClickHouse-backed worker, signed query gateway, realtime SSE, Next.js dashboard, CLI) rather than a single container.
**Why I should care** — Replaces an analytics subscription with something self-hostable, and it's one of the few tools that ties pageview/funnel data directly to revenue pulled from the operator's own Stripe account — useful for judging which referrer/campaign actually produces paying customers on a micro-SaaS product, not just traffic.
**What it could replace** — A Plausible/Fathom/GA4 subscription; hand-built Stripe-to-traffic revenue attribution.
**Ways I could use it** — Self-hosted analytics for a product's marketing site and app; revenue-attributed funnels; embeddable public stats widgets; MCP-driven "what happened to signups this week" queries from a coding agent instead of a dashboard login; CSV/JSON export.
**Agent opportunity** — Ships its own MCP server as a first-class interface for querying site stats, funnels, and revenue data directly — fits an automated weekly-report or anomaly-detection agent workflow.
**Integration effort** — Medium. Not a single container: ~8-11 services, Postgres + ClickHouse + 2x Valkey. Third-party Railway templates document ~4GB RAM / 25GB disk for self-hosting.
**Maturity** — Emerging. v0.8.0 (2026-09-19), created 2026-08-11, 643 stars/53 forks (healthy ratio)/5 open issues. Backed by named Vercel OSS Program and Neon Open Source Program sponsorships; independently corroborated via third-party Railway deploy templates and an MCP marketplace listing.
**License** — AGPL-3.0 — **flagged loudly.** Self-hosting internally is unrestricted; reselling a modified instance as a hosted service to third parties triggers source-disclosure. The authors run exactly that hosted model themselves at getopen.so, so the license is clearly deliberate.
**Alternatives** — Plausible, Fathom, Umami (none tie into the operator's own Stripe account or ship an MCP server); PostHog (broader, heavier).
**Why this one** — CI-enforced architecture discipline (signed query envelopes, single-seam OpenAPI contract, byte-budgeted tracker) is more rigorous than most tools in this niche, plus the revenue-attribution and MCP angle.
**Recommendation** — Worth standing up for a real product's analytics, budgeting for the multi-service ops overhead; treat the AGPL implication as a real constraint if a hosted-resale plan is ever considered.

### 3. keypaste — 6.9/10
**Decision:** PROTOTYPE

**What it is** — A KeePass-compatible (KDBX4) local secrets manager purpose-built for AI coding agents: every agent request for a credential goes through a per-field, reason-logged approval prompt (Deny / Allow once / Allow for 1 hour / Always-for-project), recorded in a hash-chained audit log.
**Why I should care** — "Give the agent a `.env` file" is a common default that breaks down the moment an agent is compromised or just makes a mistake with a prod credential. keypaste's scoped, logged, revocable approval model is a clean pattern to adopt directly in his own coding-agent workflows, with no cloud vault required.
**What it could replace** — Ad hoc `.env` files fully readable by any process an agent can spawn; manually tracking which secret an agent session touched.
**Ways I could use it** — `.env.keypaste` references committed to a repo instead of real values; per-project dev/staging/prod profiles with prod always requiring a live approval; scoped, expiring CI tokens; an MCP approval gate in front of Claude Code; one-time encrypted share links for handing a credential to a teammate.
**Agent opportunity** — It *is* an agent-safety tool: MCP-native approval flow with hash-chained audit logging of every grant and denial.
**Integration effort** — Low. CLI/MCP server, single KDBX4 file on disk, no account, no network; CI-verified round-trip compatibility with `keepassxc-cli`.
**Maturity** — Experimental, pre-1.0 (CLI v0.3.0), created 2026-09-05. 598 stars but only 8 forks and 4 subscribers — an engagement-ratio anomaly this review could not fully resolve. Weighed against that: the README is unusually candid about its own historical defects per version and keeps a numbered threat model (`THREATS.md`), which is not typical of engagement-farmed repos.
**License** — AGPL-3.0; unrestricted for personal/internal use, source-disclosure triggered if embedded into a distributed product.
**Alternatives** — sallyport, OpenKeylet, vahta, jitpass — a same-week wave of similar tools, all noticeably thinner on documentation (see Rejected).
**Why this one** — The most substantively documented and self-critical of this week's "secrets for agents" wave.
**Recommendation** — Try it as a drop-in credential gate for an existing coding-agent workflow; don't depend on it for anything irreplaceable yet, and recheck the star/fork anomaly in a future run.

### 4. Enroute — 6.2/10
**Decision:** STUDY

**What it is** — A Git server rebuilt in Rust on modern-database design principles: repositories as immutable, log-structured layers in object storage (S3/GCS/Azure Blob), a Raft-replicated per-repository ledger for refs/ordering, and stateless compute nodes that hold only rebuildable caches.
**Why I should care** — Not something to adopt directly, but a concretely documented answer to "what would Git hosting look like designed today instead of in 2005." The compute/storage separation and optimistic-write/log-structured-layer model is the same pattern worth recognizing whenever something is being designed to scale past a single disk.
**What it could replace** — Nothing directly in his current stack; this is an architecture-study entry.
**Ways I could use it** — Reference architecture for any "cheap append-mostly storage with strong per-shard ordering" design problem; the gRPC API + opt-in hooks (deciding who can read, what they see, which pushes land) are a plausible substrate for a policy-gated Git backend if a PTaaS engagement ever needs an isolated, audited code-review environment.
**Agent opportunity** — Speculative — no agent-specific tooling exists yet, but the hook model is a reasonable starting point for one.
**Integration effort** — Medium. Single binary or replicated cluster; requires an S3-compatible object store and a persistent disk per ledger node.
**Maturity** — Emerging/experimental. Created 2026-08-24, v0.3.0 (2026-10-14), 326 stars/14 forks/3 open issues — no red flags, just young.
**License** — Apache-2.0, unrestricted.
**Alternatives** — Traditional single-disk Git hosting (GitHub/GitLab/Gitea); Pierre (code.storage); Cloudflare Artifacts — both of which Enroute explicitly positions itself against.
**Why this one** — Genuinely novel application of Raft-replicated metadata + object-storage log-structured layers to a problem (Git hosting) almost nothing else in the space has rethought this way.
**Recommendation** — Study the architecture (compute/ledger separation, optimistic writes, LSM-style layer merging); not a deployment candidate today.

## Meaningful Updates
**Pikopod** (Pikopod/pikopod) — v0.1.2 → v0.2.0 (2026-10-04). Added **divergence detection**: every production exchange is now replayed through a fork of the linked sandbox, and a `behaviour_divergence` event (categorized `spec_drift`, `undocumented_rule`, or `provider_failure`) fires on the first difference, with `rule promote <fingerprint>` turning a divergence into a permanent sandbox rule after confirmation. Also added an inbound webhook tap (duplicate/out-of-order delivery detection), `agent incidents import <bundle>` for installing a recorded production incident locally, and a cosign-verified GitHub Action for CI. This is a real architecture step — from "spec-derived failure sandbox" toward a sandbox that self-corrects against live production traffic — not just a patch release. Catalog updated: Yes.

## Small but High-Leverage Utility
**Bullpane** — a self-hosted BullMQ/BullMQ Pro dashboard engineered specifically to be safe against a production Redis: bounded `SCAN` instead of `KEYS`, Lua-script reads (one round trip, pipelined across queues), in-Redis payload truncation, and cluster-safe hash-tagged scripts, plus support for BullMQ 6's newer PostgreSQL backend. It fills the exact gap `bull-board` leaves — no search inside job payloads, no roles, no alerts — without routing job data through a third-party hosted service like Taskforce.sh. Free core is MIT (open-core, Pro tier adds auth/roles/audit log for $39/month), but the free edition ships with **no authentication at all**, so it needs to stay on a private network. For anyone running BullMQ in a Node backend, this is a one-command (`npx bullpane`) upgrade over `bull-board`.
