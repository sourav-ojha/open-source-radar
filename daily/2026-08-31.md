# Open Source Radar — 2026-08-31
_Rotation slot 6 — infrastructure, observability, deployment_

## Executive Summary
Today's research turned up an unusually coherent observability cluster: two very different
architectures (S3-backed platform vs. ClickHouse-backed protocol gateway) for cutting the
cost of a self-hosted observability stack, plus two AI-agent-specific tools that treat
coding-agent activity and codebase context as first-class observability/infrastructure
problems rather than afterthoughts. The GitHub Search API's "self-hosted deployment
platform" query also surfaced a striking wave of near-identical "Coolify/Dokploy
alternative" repos launched in the last 24–48 hours — noted under Rejected rather than
covered individually, since none differentiate enough yet to recommend over the
already-known incumbents.

## Today's Best Discoveries

### 1. Monoscope — 8.6/10
**Decision:** USE NOW

**What it is** — A self-hosted, OpenTelemetry-native observability platform that stores
logs, traces, and metrics in S3-compatible buckets, with natural-language querying via
LLMs and scheduled AI agents that detect anomalies and email reports.
**Why I should care** — S3-backed storage removes the usual "trim retention because
storage is expensive" tradeoff, and NL query removes the LogQL/PromQL learning curve.
**What it could replace** — A self-hosted Grafana Loki/Tempo/Mimir stack, or a Datadog/
Better Stack subscription, for internal service observability.
**Ways I could use it** — Monitor the MSSP admin portal's backend services affordably at
long retention; let non-observability-fluent teammates query logs in plain English;
schedule an anomaly digest email instead of hand-building alert rules; correlate logs,
traces, metrics, and session replay in one place.
**Agent opportunity** — Scheduled AI agents for anomaly detection are a built-in feature.
**Integration effort** — Medium: `docker-compose up` is trivial, but routing all existing
services' telemetry into it and provisioning S3 buckets is real work.
**Maturity** — Mature: created 2022, 1,679 stars, weekly-ish releases, active, not archived.
**License** — AGPL-3.0 — **flagged loudly.** Safe for internal self-hosted use; only
triggers network-copyleft obligations if modified and re-offered as a hosted,
customer-facing service (use the managed cloud tier instead in that case).
**Alternatives** — Grafana Loki/Tempo/Mimir, SigNoz, Better Stack, Datadog, Axiom.
**Why this one** — Cheap, S3-native long-retention storage plus first-class AI agents
distinguishes it from the standard self-hosted observability stack.
**Recommendation** — Install and point it at one non-critical service's telemetry first.

### 2. LoongSuite Pilot — 8.2/10
**Decision:** PROTOTYPE

**What it is** — A local-first telemetry collector purpose-built for AI coding agents
(Claude Code, Codex, Cursor, and others), normalizing their activity into a shared
GenAI event schema with a local dashboard.
**Why I should care** — No mainstream tool normalizes coding-agent activity across
vendors; this fills that specific gap and gives real usage data instead of guesswork.
**What it could replace** — Manually digging through each agent's own native session logs.
**Ways I could use it** — See aggregate token spend across Claude Code/Cursor/Codex;
audit exactly what tools an agent ran in a session; feed normalized activity into an
existing OTel backend (e.g. Monoscope or Cerberus, both below) for one unified view; use
real usage data to justify or budget agent tooling spend as engineering responsibilities
grow toward CTO-level scope.
**Agent opportunity** — The entire tool is agent-observability infrastructure across 12+
coding agents via hooks, normalized to one schema.
**Integration effort** — Low: single install-script per platform, auto-detects agents.
**Maturity** — Emerging: created 2026-06-04 (~3 months old), backed by Alibaba, active,
Apache-2.0, weekly releases.
**License** — Apache-2.0, no restrictions.
**Alternatives** — Native per-agent logs (status quo); Langfuse/OpenLLMetry (LLM-app
tracing, not coding-agent-specific); Laminar (same gap, already catalogued 2026-08-29).
**Why this one** — Purpose-built normalization across multiple coding-agent vendors,
which nothing else in the catalog attempts.
**Recommendation** — Install locally for a week and see whether the visibility is worth
keeping before wiring it into shared infrastructure. Note: installer is a curl|sh script
from an Aliyun OSS CDN — review it before running.

### 3. Gortex — 8.0/10
**Decision:** PROTOTYPE

**What it is** — A single-binary, fully local code-intelligence engine that indexes
codebases (257 languages via tree-sitter) into a persistent graph exposed to coding agents
via CLI, MCP server, and web UI.
**Why I should care** — Large MERN monorepos and multi-repo microservice setups are
exactly where agents burn tokens re-reading files for context every session; the
cross-repo API-contract detection (matching HTTP/GraphQL/gRPC/message-topic
providers to consumers) is a genuinely useful check for an AWS/EKS microservices setup.
**What it could replace** — Grep-based or re-read-everything agent context strategies.
**Ways I could use it** — Persistent call-graph for large-repo agent sessions; detect
orphaned API providers/consumers across separate service repos before they cause an
incident; reduce token spend on agent-driven refactors.
**Agent opportunity** — 175 configurable MCP tools; auto-configures across 19 supported
coding agents in one install step.
**Integration effort** — Low: single-binary curl installer, no server component.
**Maturity** — Emerging by age (created 2026-04-06, still pre-1.0 at v0.63.9) but unusually
mature supply-chain practice for that age — Sigstore-signed, SLSA Level 3, OpenSSF
Scorecard, VirusTotal-clean, 10+ distinct contributors.
**License** — Apache-2.0, no restrictions.
**Alternatives** — Sourcegraph (heavier, hosted-first), LSP/ctags-only context, plain
grep-based context (status quo).
**Why this one** — Purpose-built for agent token-efficiency on large codebases rather
than a general code-search tool retrofitted for it.
**Recommendation** — Pilot against one real large repo and measure actual token savings
on representative tasks before trusting the "50x fewer tokens" headline claim, which is
the maintainer's own benchmark rather than independently reproduced.

### 4. AnythingMCP — 7.8/10
**Decision:** PROTOTYPE

**What it is** — A self-hosted MCP gateway that converts REST, SOAP/WSDL, GraphQL, and
SQL/NoSQL databases into MCP tools automatically, with OAuth2, RBAC, and audit logging.
**Why I should care** — Wrapping an API as an MCP tool is normally bespoke, hand-written
work; RBAC and audit logging out of the box is the piece most hand-rolled wrappers skip,
and that matters the moment an agent touches anything customer-facing.
**What it could replace** — Writing a one-off MCP server per API integration.
**Ways I could use it** — Expose the MERN admin-portal's REST API to agents as MCP tools
without a custom wrapper server; wrap a Postgres/Mongo read replica as queryable MCP
tools; give agents controlled, audited access to third-party SaaS APIs already in use.
**Agent opportunity** — This is the core product: any existing infrastructure becomes an
MCP tool with auth and audit built in, usable from Claude, ChatGPT, Gemini, Copilot, Cursor.
**Integration effort** — Medium: Docker Compose gets it running quickly; the "no-code"
spec-import claim needs hands-on verification against a real-world API with non-trivial
auth before trusting it further.
**Maturity** — Emerging: created 2026-02-28, active, v0.4.4, 185 stars, 14 open issues.
**License** — AGPL-3.0 — **flagged loudly**, same considerations as Monoscope above:
fine for internal tooling, but re-offering it as a hosted customer-facing feature would
trigger network-copyleft obligations.
**Alternatives** — Hand-rolled MCP servers (status quo), aws/mcp-proxy-for-aws (narrower,
AWS/IAM-only — see Worth Watching), Composio/Pipedream-style commercial platforms,
OpenConnector (Worth Watching, 2026-08-30).
**Why this one** — RBAC and audit log by default, plus 175+ pre-built adapters.
**Recommendation** — Prototype by wrapping one existing internal API and testing an
agent-driven call end-to-end, including the RBAC/audit path.

### 5. Cerberus (ClickHouse observability gateway) — 7.5/10
**Decision:** STUDY

**What it is** — A read-only HTTP gateway that speaks the Prometheus/Loki/Tempo wire
protocols but translates queries into ClickHouse SQL, so Grafana keeps working unchanged
while the storage/query backend becomes ClickHouse.
**Why I should care** — Collapses "run Prometheus + Loki + Tempo + Mimir" into "run
ClickHouse + cerberus" for any future self-hosted observability stack, with zero
migration cost to existing Grafana dashboards/alerts.
**What it could replace** — A native Loki+Tempo+Mimir stack, if self-hosting observability
for personal infra or the MSSP admin portal's internal monitoring.
**Ways I could use it** — Cheaper long-retention metrics/logs/traces storage; study the
protocol-translation-gateway pattern itself, which generalizes well beyond observability.
**Agent opportunity** — None identified.
**Integration effort** — Low to bolt on (three Grafana datasources), but requires an
existing OTel Collector → ClickHouse pipeline; not a turnkey full stack.
**Maturity** — Experimental: created 2026-05-05 (~4 months old), 64 stars. The
maintainer's own README states: "young project... try it against your own data before you
rely on it in production" — an honest maturity signal worth taking at face value.
**License** — Apache-2.0, no restrictions.
**Alternatives** — Native Loki+Tempo+Mimir (status quo), Grafana's own ClickHouse
data-source plugin (per-datasource, not full protocol translation), SigNoz, Monoscope
(above — a different approach, S3-backed rather than ClickHouse-backed).
**Why this one** — Publishes live compatibility-percentage badges per protocol instead of
just claiming compatibility, and the architecture pattern is reusable beyond observability.
**Recommendation** — Study the architecture and pilot against non-critical data; not yet
a production swap given the maintainer's own caveat and single-primary-maintainer profile.

## Small but High-Leverage Utility
**inspeximus** ([DanceNitra/inspeximus](https://github.com/DanceNitra/inspeximus)) — a
zero-dependency, single-file Python library (plus an MCP server) that gives AI agents the
ability to correct a remembered fact and later undo that correction on command, with a
verifiable "receipt" of what changed. Most agent-memory libraries (mem0, Graphiti) can
apply a correction but have no clean channel to take it back; inspeximus's own benchmark
(published, reproducible via its `audit.yml` CI workflow) reports the old value resurfacing
0% of the time after a correction, versus 13.3% for Graphiti and 46.7% for mem0 in the same
test. Extremely early (6 stars, created 2026-07-13) and narrow in scope, but the
"confidently remembering the wrong answer" problem it targets is real for any agent
workflow that accumulates long-term memory — worth a 10-minute `pip install` trial rather
than production dependence today. Not added to the catalog as a full entry given its very
early stage; logged in `evaluated_repos` to avoid rediscovery.

## Worth Watching
- **AWS MCP Proxy** ([aws/mcp-proxy-for-aws](https://github.com/aws/mcp-proxy-for-aws)) —
  an official AWS package that bridges MCP clients (Claude Desktop, Kiro CLI) and
  frameworks (LangChain, Strands, LlamaIndex) to MCP servers on AWS using IAM/SigV4 auth
  instead of OAuth. Solid and official (347 stars, Apache-2.0, active), but only relevant
  if/when MCP servers get deployed on AWS (e.g. via Bedrock AgentCore) with IAM-based auth
  — not an immediate need today.
- **OpenRun** ([openrundev/openrun](https://github.com/openrundev/openrun)) — a
  self-hosted, Apache-2.0 GitOps deployment platform specifically for teams deploying
  internal tools, with OIDC/SAML auth and RBAC baked in (single-node or Kubernetes). Would
  need a closer look at how it differs in practice from standing up Coolify/Dokploy plus a
  reverse proxy with SSO in front, given today's GitHub search also surfaced a wave of
  near-identical "self-hosted PaaS" launches (see Rejected below) that make this crowded
  category hard to evaluate by README alone.
- **ServiceRadar** ([carverauto/serviceradar](https://github.com/carverauto/serviceradar))
  — an Apache-2.0 network monitoring/ITOM/security-analytics platform (917 stars, CNCF
  landscape listed) that could be relevant to the MSSP secondary context. Flagged rather
  than fully catalogued because its README states active development has moved to a
  self-hosted Forgejo instance (`code.carverauto.dev`) with GitHub now a mirror — worth
  revisiting once it's clear the mirror stays current and the primary repo's health
  signals (releases, issues) remain trustworthy from GitHub alone.
