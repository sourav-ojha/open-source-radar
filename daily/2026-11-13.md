## Executive Summary
Today's slot leaned toward review and CI-reliability tooling rather than new frameworks: a
multi-forge code-review TUI, a cross-agent plan/diff annotation surface, a self-hosted
Playwright flaky-test dashboard, a pnpm/Turborepo monorepo CLI, and a content-aware diff

## Today's Best Discoveries

### 1. Plannotator — 8.2/10
**Decision:** PROTOTYPE

**What it is** — A local-first surface for reviewing and annotating coding-agent output
— plans, specs, markdown/HTML artifacts, diffs/PRs — with one-click feedback sent back
into the agent session. Wires into Claude Code, Codex, Copilot CLI, Gemini CLI, OpenCode,
Droid, Kiro, Pi, and Amp via each harness's own hooks.
**Why I should care** — This is a review layer for exactly the kind of long Claude Code
session this radar itself runs on: instead of reading a plan in scrollback and typing
corrections, it opens a dedicated annotate surface and sends structured feedback straight
back to the agent.
**What it could replace** — Manually typing feedback paragraphs into an agent's prompt
after reading its plan or diff in raw terminal output.
**Ways I could use it** — Review a plan before implementation starts; review a GitHub
PR/GitLab MR/local diff/GitButler workspace from one surface regardless of which agent
produced it; keep a local, non-telemetry archive of past plan decisions.
**Agent opportunity** — Native hooks for eight-plus agent harnesses, usable as-is inside
an existing Claude Code workflow with no custom glue.
**Integration effort** — Low: local CLI/app install, no server required for the
open-source workflow.
**Maturity** — Emerging (created 2025-12-28, ~11 months old; 776 forks, 194 open issues —
real engagement despite a 465:1 star:subscriber ratio).
**License** — Apache-2.0 for the local app; team sharing ("Workspaces") is a separate
hosted product (open-core).
**Alternatives** — Planning with Files (already catalogued — persists agent task state,
not a review surface); reading plans/diffs directly in the terminal or GitHub's UI.
**Why this one** — Differentiated from Planning with Files: PWF is the agent's own
state-persistence layer, Plannotator is the human review/annotate layer on top of what
the agent produces, across every major CLI agent, not just one.
**Recommendation** — Wire it into one real Claude Code planning session and see if the
annotate-and-send-back loop actually beats typing feedback directly.

### 2. tuicr — 8.1/10
**Decision:** USE NOW

**What it is** — A terminal UI for code review with vim keybindings: one continuous
scrolling diff instead of GitHub's per-file tabs, persistent comments, and real push-back
to GitHub, GitLab, Gitea, Bitbucket, Azure DevOps, or Gerrit. Also reviews git, jj, and
Mercurial working copies.
**Why I should care** — Collapses the terminal/browser tab-switch of code review into one
tool that still produces a real review on whichever forge the repo lives on.
**What it could replace** — GitHub/GitLab's web PR review UI for day-to-day review work.
**Ways I could use it** — Review a PR or an agent's diff without leaving the terminal;
review uncommitted changes before pushing; work the same way across GitHub and a
self-hosted Gitea/GitLab instance; pipe a review to clipboard for an agent follow-up
prompt.
**Agent opportunity** — Clipboard/stdout markdown export is a ready-made bridge into an
agent's next prompt; no MCP server yet.
**Integration effort** — Low: install via script, Homebrew, pacman, Cargo, or Nix — no
server, no account.
**Maturity** — Emerging (created 2026-01-08, v0.28.0; 339 forks, 96 open issues despite an
elevated 450:1 star:subscriber ratio, which looks like a following-size anomaly rather
than fabricated engagement given the fork/issue volume).
**License** — MIT, no restrictions.
**Alternatives** — `gh pr diff`/`glab mr diff` piped to a pager; difftastic/delta (diff
rendering only, no review tracking).
**Why this one** — The multi-forge export (6 platforms) plus jj/Mercurial support is
integration breadth not worth re-implementing personally.
**Recommendation** — Install the binary and use it on the next real PR review instead of
the browser.

### 3. Piwi — 7.6/10
**Decision:** PROTOTYPE

**What it is** — A self-hosted dashboard for Playwright test results: keeps every CI run,
clusters failures by root cause, scores tests by flakiness, and suggests the locator you
should have used. Ships as an npm reporter, a self-hosted server/dashboard (Docker image),
a browser extension, and a desktop companion.
**Why I should care** — Flaky E2E tests are a recurring, silently-accepted tax in any
Playwright CI setup; this is a self-hosted, zero-telemetry alternative to paid
test-analytics SaaS (BuildPulse, Currents).
**What it could replace** — Re-investigating the same flaky test from scratch every time
it fails; re-debugging broken locators by hand; a paid test-analytics subscription.
**Ways I could use it** — Track flaky-test trends over time; triage failing E2E tests by
root-cause cluster; get locator-healing suggestions; decide what to quarantine using a
flakiness score.
**Agent opportunity** — Structured failure-cluster output is a plausible input for an
agent tasked with fixing a batch of flaky tests; no MCP server yet.
**Integration effort** — Medium: needs the npm reporter wired into an existing Playwright
config plus a self-hosted server.
**Maturity** — Emerging (created 2025-12-07; 50 stars/4 forks/1 subscriber — thin
traction, but latest npm release (0.69.0) published 2026-11-12, so actively maintained).
**License** — MIT for the embedded reporter/core/picker-dom packages; **FSL-1.1-MIT**
(converts to MIT after a future date) for the dashboard, server, desktop app, browser
extension, and IDE plugins — flagged per AGENT.md §14 since the pieces actually
self-hosted here are the FSL ones.
**Alternatives** — Playwright's own HTML reporter (no history/clustering); paid
test-analytics add-ons; manually grepping CI logs.
**Why this one** — Failure-clustering and locator-healing in one self-hosted, zero-telemetry
package is genuinely novel for this niche.
**Recommendation** — Self-host it against an existing Playwright suite with a known flaky
test and see whether triage actually gets faster.

### 4. repoctl — 7.4/10
**Decision:** PROTOTYPE

**What it is** — A task-first CLI for initializing, maintaining, validating, and
releasing pnpm + Turborepo monorepos: workspace health checks, scaffolding, repeatable
local verification, and change-intent-based publishing, with machine-readable
JSON/Markdown output.
**Why I should care** — Turborepo itself only orchestrates tasks; it has no opinion on
workspace health, scaffolding, or release publishing. This fills exactly that gap for his
actual pnpm+Turborepo stack without pulling in Nx's much larger surface area.
**What it could replace** — Bespoke workspace-health scripts; hand-rolled
changesets-plus-custom-scripts release flows.
**Ways I could use it** — `repo doctor` as a one-command health check; `repo new` for
scaffolding with house conventions; `repo verify` to gate CI with machine-readable output;
publishing from pnpm change intents.
**Agent opportunity** — JSON output from `repo check`/`repo verify` is directly
consumable by an agent deciding whether a monorepo change is safe to merge.
**Integration effort** — Low: `pnpm add -D repoctl`, no migration required.
**Maturity** — Mature for a niche tool (created 2022-11-02, ~3 years; codecov-tracked;
latest npm release 6.6.1 published 2026-11-12), despite only 49 stars/1 subscriber.
**License** — MIT, no restrictions.
**Alternatives** — Turborepo's own CLI (orchestration only); Nx (heavier); hand-rolled
scripts.
**Why this one** — Scoped precisely to pnpm+Turborepo rather than trying to be a universal
monorepo tool.
**Recommendation** — Run `repo doctor` against an existing workspace to see what it flags
before adopting it for releases.

### 5. OmniDiff — 7.2/10
**Decision:** STUDY

**What it is** — A diffing engine that selects a format-specific algorithm per file type
(code, images, cursors, fonts, archives, message catalogs, PDFs) instead of running
textual diff on everything, with published per-content-type speed/accuracy figures and an
in-browser showcase.
**Why I should care** — Most diff tooling is textual-only (git diff) or code-only
syntax-aware (difftastic, delta). This dispatches by content type and publishes an
accuracy table covering assets a product repo accumulates that git treats as opaque.
**What it could replace** — "Binary files differ" on image/font/PDF changes in a PR, with
no diff at all.
**Ways I could use it** — Wire it in as a custom `git diff`/`difftool` driver; study the
content-type dispatch design as a reference for format-aware diffing elsewhere.
**Agent opportunity** — A format-aware diff is a materially better review input than raw
textual diff for an agent reviewing a PR touching non-code assets.
**Integration effort** — Medium: Rust crate/CLI, no Node/JS bindings found.
**Maturity** — Emerging (created 2025-10-17; v0.4.0; 1,355 stars/36 forks/3 subscribers —
elevated ratio, but CI/coverage/fork/issue activity and a public showcase site look
organic).
**License** — **AGPL-3.0-only**, with a separate commercial license available — flagged
loudly: embedding this in a hosted/commercial product under AGPL terms triggers its
network-use source-disclosure requirement unless the commercial license is purchased.
Local CLI/git-diff-driver use for personal/internal work is unaffected.
**Alternatives** — GNU diff/git diff (textual only); difftastic/delta (code-only);
specialized per-format tools used piecemeal.
**Why this one** — The published per-content-type accuracy table and architecture are
worth understanding even without adopting the tool directly.
**Recommendation** — Try it as a git diff driver on a repo with real image/font assets
before deciding whether it earns a PROTOTYPE upgrade.

## Small but High-Leverage Utility
**dsr (Doodlestein Self-Releaser)** — a fallback release tool for when GitHub Actions is
throttled: it watches a repo's Actions queue time, and once past a threshold, builds the
release locally by running the existing `.github/workflows/release.yml` through `nektos/act`
(Linux) or natively over SSH (macOS, Windows), signs artifacts with Minisign, generates an
SBOM, and uploads to GitHub Releases — same artifacts, no queue wait, and no second build
pipeline to maintain. Narrow (only useful if you ship CLI binaries via Actions and have
actually hit queue throttling), and its MIT license carries an unusual rider voiding any
grant to OpenAI, Anthropic, or anyone acting on their behalf — flagged in the project file
as worth knowing about rather than a practical blocker for ordinary use.
