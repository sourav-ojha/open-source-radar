# Open Source Radar — 2026-10-31
_Rotation slot 4 — data, search, documents, RAG_

## Executive Summary
Today's generic GitHub keyword search (`semantic cache`, `reranker`, `document chunking`,
`data lineage`) was almost entirely drowned out by hackathon noise and same-second
0-star repos — the signal came instead from stars/pushed-date-filtered searches and
direct lookups. The standout is Antfly, a Zig-core "one engine for search, vectors,
graph, and inference" database with genuinely useful TypeScript embedding — a rare case
of infra that collapses a multi-service stack (search + vector DB + graph DB + RAG glue)
without forcing a Python-first ecosystem. The agent-memory niche produced its most
mature entrant yet (mcp-memory-service, ~2 years old vs. the usual weeks-old
competitors), and a rigorously engineered but Rust-first unified RDF/text/geo/vector
engine (PurRDF) was filed as an architecture study rather than something to adopt
directly.

## Today's Best Discoveries

### 1. Antfly — 8.3/10
**Decision:** PROTOTYPE

**What it is** — A search-and-inference database (Zig core) combining full-text (BM25),
dense + sparse vector search, graph traversal, and in-process embedding/reranking/
OCR/transcription models over one table, with built-in RAG agents, MCP/A2A protocol
adapters, and a Postgres CDC mirror.
**Why I should care** — It collapses the usual three-to-four-service stack behind a
search or RAG feature (full-text engine, vector DB, graph DB, embedding/reranking glue)
into one Apache-2.0 engine with a real embeddable TypeScript SDK, unusually convenient
for a Node/React stack.
**What it could replace** — A hand-assembled Elasticsearch/OpenSearch + Pinecone/Qdrant
+ Neo4j stack, plus the glue code tying them together for a RAG feature.
**Ways I could use it** — Embed it (`@antfly/embedded`) directly in a Node service or
browser for local-first search; stand up a support-answer or site-search RAG agent from
its documented end-to-end guides; mirror a Postgres table into it via CDC for hybrid
search with no separate ETL job; query it from Postgres via the `antfly_postgres`
extension; expose it to a coding agent over its native MCP/A2A adapters.
**Agent opportunity** — Native MCP and A2A protocol adapters, plus a built-in
query-builder agent that turns natural language into a structured query with its own
retrieval-quality eval metrics.
**Integration effort** — Low for the embedded/TypeScript path; Medium for operating the
full distributed server (multi-Raft).
**Maturity** — Emerging / pre-1.0 (latest tag v0.2.5, created 2026-03-15, ~7.5 months
old). SQL/Postgres-wire and serverless-over-object-storage are explicitly in progress.
**License** — Apache-2.0, no commercial restrictions. A hosted Antfly Cloud option
exists alongside self-hosting.
**Alternatives** — ParadeDB (already catalogued, narrower Postgres-only scope); WhoDB
and similar self-hosted DB workspaces (a client over existing DBs, not a storage engine).
**Why this one** — It's the only entrant found with a genuinely embeddable TypeScript
surface for this scope of functionality, rather than assuming a Python ML pipeline.
**Recommendation** — Prototype: try Antfly Lite embedded in a side project before
betting production search/RAG infra on a pre-1.0 engine.

### 2. mcp-memory-service — 8.0/10
**Decision:** USE NOW

**What it is** — A self-hosted, framework-agnostic persistent memory backend for AI
agents — REST API, MCP (local and remote with OAuth 2.0 + Dynamic Client Registration),
CLI, and a dashboard — with a typed causal knowledge graph and local ONNX embeddings.
**Why I should care** — It's the most mature entrant seen so far in the fast-saturating
agent-memory niche: ~2 years old (created 2024-12-26) against a wave of weeks-old
competitors, with 2,056 stars / 369 forks and production features (real OAuth-gated
remote MCP, SSE events, per-agent scoping) the newer entrants don't have yet.
**What it could replace** — Re-explaining architecture context to a coding agent every
session; a hand-wired Redis + vector-DB memory store across multiple agent frameworks.
**Ways I could use it** — Give Claude Code/Desktop cross-session memory; share one
memory backend across LangGraph/CrewAI/AutoGen and Claude; scope memories per agent via
`X-Agent-ID`; query typed causal edges (causes/fixes/contradicts) between past
decisions; expose remote MCP access to teammates behind real OAuth.
**Agent opportunity** — Native MCP server with OAuth2+DCR-gated remote access and SSE
real-time memory events for coordinating multiple agents sharing one memory space.
**Integration effort** — Low — `pip install mcp-memory-service`, working in under 60
seconds per the project's own setup guide; embeddings run locally via ONNX.
**Maturity** — Mature relative to the niche (latest release v12.4.0, 2026-10-26).
**License** — Apache-2.0, no commercial restrictions.
**Alternatives** — Hippo, CortexDB, deja-vu, MuninnDB (already catalogued, all
weeks-to-months old).
**Why this one** — Two years of track record and a materially larger community than
every other catalogued agent-memory tool, plus features none of them currently ship.
**Recommendation** — Use now as the first stop in the agent-memory niche; don't adopt it
alongside the other catalogued memory tools without a clear reason.

### 3. PurRDF — 6.8/10
**Decision:** STUDY

**What it is** — A single Rust RDF 1.2 engine (shared across Rust/Python/JS-WASM/C)
that answers BM25 full-text search, exact GeoSPARQL 1.1 topology, and exact/approximate
embedding kNN inside one SPARQL evaluator over one dataset, plus SHACL/ShEx validation
and Datalog/OWL reasoning, with deterministic fixed-point arithmetic.
**Why I should care** — It's a rare, academically rigorous (DOI-citable) example of
solving text, geo, and vector retrieval together inside one typed query evaluator
instead of running Postgres + pgvector + PostGIS as three subsystems.
**What it could replace** — A Postgres + pgvector + PostGIS combination for text +
vector + spatial retrieval, in a Rust-hosted application.
**Ways I could use it** — Study its fused SPARQL retrieval model as a design reference;
build a Rust knowledge-graph app needing RDF + validation + reasoning + retrieval in one
dependency; use the thinner npm/Python packages for RDF data-shape work alone.
**Agent opportunity** — The browser WASM build could back an in-browser,
no-server knowledge-graph explorer or agent-memory demo.
**Integration effort** — Medium — the npm/Python packages deliberately expose only
data-shaped property functions and path witnesses, not the full retrieval fusion that
makes the Rust core interesting.
**Maturity** — Experimental (created 2026-07-01, ~4 months old, 52 stars / 2 forks), but
unusually polished engineering for its age (DOI release, docs book, browser playground).
**License** — Triple-licensed, MIT OR Apache-2.0 OR MulanPSL-2.0 — all permissive.
**Alternatives** — RDFLib/Apache Jena (RDF-only, no built-in retrieval fusion); Postgres
+ pgvector + PostGIS run as three subsystems.
**Why this one** — The architecture genuinely does something novel; most "unified
database" pitches don't carry formal correctness guarantees like this one does.
**Recommendation** — Study the design; not a fit for direct adoption on a Node-first
stack given the narrower non-Rust bindings.

## Small but High-Leverage Utility
**PII-Shield** (pii-shield/pii-shield, Apache-2.0, 7.0/10, PROTOTYPE) — a zero-code
Kubernetes sidecar (also usable as a CLI or in-process WASM module) that redacts PII and
detects secrets in logs via entropy analysis before they leave the pod, preserving JSON
structure. Directly relevant to the EKS side of the AWS stack and to the MSSP/PTaaS
secondary context: dropping this in front of application logs on an EKS cluster is a
lower-effort GDPR/SOC2 compliance control than building log redaction into every service
by hand, and the in-process WASM SDK gives sub-millisecond redaction without a sidecar
network hop for cases that need it. The Kubernetes operator deployment mode is still in
a "stabilization phase" per the project's own status table, so the CLI/WASM path is the
better-tested option for now.
