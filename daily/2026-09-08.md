# Open Source Radar — 2026-09-08
_Rotation slot 7 — experimental projects and hidden gems_

## Executive Summary
Today's discovery skewed heavily toward MCP tooling — not agent frameworks themselves, but
the debugging and efficiency layer underneath them: a transparent MCP traffic inspector
(mcpsnoop), an Atlassian-backed tool-schema compressor (mcp-compressor), and an ambitious
(and not yet independently verified) codebase-graph MCP server (trace-mcp). All three are
complementary, not redundant — inspect traffic, shrink tool schemas, and cut repeated
codebase exploration are three different costs of running agents against real MCP servers
and real repos. Rounded out with Quackback, a genuinely full-featured self-hosted
Canny/Productboard alternative that needs its AGPL license taken seriously before any
resale plan.

## Today's Best Discoveries

### 1. mcpsnoop — 8.2/10
**Decision:** USE NOW

**What it is** — "Wireshark for MCP": a transparent proxy that sits in the real data path
between an MCP client (Cursor, Claude Code, Codex, Claude Desktop) and an MCP server,
showing every JSON-RPC frame live in a terminal UI.
**Why I should care** — The official MCP Inspector connects as its own client, so it never
sees what a real client actually sent — mcpsnoop sees the real conversation, including
calls the model never made or made with the wrong arguments.
**What it could replace** — Ad hoc console logging inside an MCP server; guesswork when a
tool silently isn't called.
**Ways I could use it** — Wrap any MCP server command with zero config while developing it;
auto-wrap/unwrap a specific server in Claude Desktop's config for one debugging session;
run as a reverse proxy in front of a streamable-HTTP server; gate CI on a captured session
via the bundled GitHub Action.
**Agent opportunity** — Directly supports building and debugging MCP servers, which is
core to this profile's AI-agent-leverage axis.
**Integration effort** — Low. Single Go binary; wrap an existing launch command.
**Maturity** — Emerging. Created 2026-06-27, 347 stars, 10 contributors, v0.21.0.
**License** — MIT. No restrictions.
**Alternatives** — Official MCP Inspector (structurally blind to real client traffic).
**Why this one** — Sits in the actual data path instead of emulating a client, which is
the only architecture that can see what really happened.
**Recommendation** — Install and use as the default debugging step for any new MCP server.

### 2. mcp-compressor — 8.0/10
**Decision:** USE NOW

**What it is** — An MCP server wrapper (CLI proxy or embeddable Python/TypeScript/Rust SDK)
from Atlassian Labs that shrinks the token cost of large MCP tool surfaces: the model sees
a compact tool list first, then fetches a full schema only for the tool it selects.
**Why I should care** — Large MCP servers can spend thousands to tens of thousands of
tokens on tool descriptions before an agent does anything useful; this compounds every time
another MCP server is added to an agent's toolset.
**What it could replace** — Hand-rolled tool filtering or bespoke progressive-disclosure
logic in front of a large MCP server.
**Ways I could use it** — Front any large third-party MCP server to cut fixed per-request
overhead; compress a self-built server's tool surface as it grows; embed compression
directly into a TypeScript/Python app's in-process tool definitions; use CLI/Code Mode to
get shell or function equivalents of MCP tools.
**Agent opportunity** — Directly lowers token cost and dollar cost for any agent workflow
built on MCP.
**Integration effort** — Low. CLI proxy in front of an existing server, or import the SDK.
**Maturity** — Emerging repo (created 2026-03-04) but backed by Atlassian Labs, which
meaningfully lowers abandonment risk. 118 stars, v0.31.10.
**License** — Apache-2.0. No restrictions.
**Alternatives** — Hand-rolled tool filtering; bespoke progressive disclosure per server.
**Why this one** — Reputable backing plus aligned SDKs across three languages make this a
safer bet than a typical solo tool-bloat fix.
**Recommendation** — Adopt when building or consuming any MCP server with a non-trivial
tool count.

### 3. trace-mcp — 7.4/10
**Decision:** PROTOTYPE

**What it is** — An MCP server plus desktop app that builds a framework-aware dependency
graph of a codebase once, then serves change-impact analysis, code-linked decision memory,
and cross-session recall through MCP tools — claiming 81 languages / 87 framework
integrations, and now also indexing Markdown knowledge vaults (Obsidian/Logseq).
**Why I should care** — The core thesis — that agent-session cost mostly comes from
repeatedly re-deriving the same repo structure, not from task complexity — matches real
experience running coding agents against non-trivial repos.
**What it could replace** — The "80 Grep calls and 190 file reads" pattern that dominates
long agent sessions when an agent has to rediscover structure every turn.
**Ways I could use it** — Ask "what breaks if I change this model?" and get a precomputed
blast radius; recover the reasoning behind a past decision instead of digging through git
blame; orient a new agent session in ~300 tokens; index a personal notes vault the same way.
**Agent opportunity** — Purpose-built MCP server for Claude Code, Codex, Cursor, Windsurf,
Zed.
**Integration effort** — Low on paper: `npm install -g trace-mcp`, `trace init`, `trace add`.
**Maturity** — Emerging, effectively single-author (created 2026-04-03). 170 stars,
v3.23.2.
**License** — MIT. No restrictions.
**Alternatives** — Plain grep/glob-based agent exploration; Sourcegraph-style code
intelligence (heavier, not agent-native); text-only decision-memory tools.
**Why this one** — Links decisions directly to the dependency graph rather than storing
them as unlinked text, which the closest comparable tools do not do.
**Recommendation** — Trial on a real repo before relying on it — the headline 72.7%
token-reduction and comprehension-parity numbers are self-reported over 60 PRs in repos the
author does not own, and the project is effectively a single maintainer.

### 4. Quackback — 6.7/10
**Decision:** PROTOTYPE

**What it is** — Open-source support-and-feedback suite: feedback boards with voting, a
shared inbox, help center, changelog/roadmap pages, and an embeddable widget — the
open-source alternative to Canny, UserVoice, and Productboard.
**Why I should care** — Feedback/roadmap/changelog infrastructure is exactly the
undifferentiated product-building work that otherwise eats weeks out of a micro-SaaS build.
**What it could replace** — A paid Canny/UserVoice/Productboard subscription, or a
hand-built feedback board.
**Ways I could use it** — Self-host as the feedback/roadmap layer for a new product; let an
internal agent triage feedback via the built-in MCP server; embed the feedback widget
directly in a product UI; route feedback into Slack/Linear/Jira/GitHub via 25 built-in
integrations.
**Agent opportunity** — Ships an MCP server for AI agents to search, triage, and act on
feedback, plus an in-product AI copilot with per-tool write permissions.
**Integration effort** — Medium. Requires PostgreSQL and its own ops; Docker or one-click
Railway deploy.
**Maturity** — Emerging. Created 2025-12-02, 263 stars, 39 open issues (active), v0.13.2.
**License** — **AGPL-3.0 — flagged loudly.** Self-hosting as-is for internal/own use is
fine; modifying and reselling it as a hosted service, or embedding it in a redistributed
commercial product, would trigger the obligation to release the modified source. The
repo's own commercial "cloud" hooks are the vendor's own dual-licensing path, not a
template for a competing fork.
**Alternatives** — Canny, UserVoice, Productboard, Fider (older, narrower OSS alternative).
**Why this one** — Feature breadth (25 integrations, mobile SDKs, MCP server, embeddable
widget) well beyond a typical "OSS Canny clone."
**Recommendation** — Prototype as a self-hosted internal tool as-is; treat any resale or
redistribution plan as an AGPL compliance question first.

## Small but High-Leverage Utility
**mnemonic** (danielmarbach/mnemonic) — a local MCP memory server backed by plain Markdown
files with YAML frontmatter, synced via git, with hybrid semantic/exact-match/relationship
recall. No database, no always-on service: memories are just files a coding agent can
`remember`, `update`, and `consolidate`, each creating its own git commit, so a project's
decision log travels in the same history as the code. Explicitly scoped to hundreds-to-low-
thousands of notes rather than trying to be a full vector database. Apache-2.0, 29 stars,
essentially a solo project by an established maintainer (danielmarbach, known for
NServiceBus/Particle). Not catalogued — narrower and smaller than dedicated agent-memory
options already tracked (e.g. mex), but worth knowing about for the specific case of
wanting agent memory that is nothing more than readable, diffable git-tracked files.

## Worth Watching
- **Skrun** (skrun-dev/skrun) — turns any `SKILL.md`/`AGENTS.md`-declared agent skill into a
  `POST /run` API endpoint, positioned as an open, multi-model, self-hostable alternative to
  Claude Managed Agents and similar vendor runtimes. MIT, 209 stars, genuinely useful
  micro-SaaS-shaped idea (closes the gap between "I published a skill" and "someone can
  actually call it from CI"), but contributor data shows it is effectively a one-person
  project (2 human-attributed contributors, one with a single commit) barely a week past its
  first tagged release. Revisit once a second maintainer or real production users show up.
- **OpenTaint** (seqra/opentaint) — a formal taint-analysis engine positioned as an
  AI-agent-driven, self-hostable alternative to Semgrep Pro and CodeQL, directly relevant to
  the MSSP/PTaaS secondary context. Apache-2.0, 156 stars, real multi-contributor team (not
  a solo project) — but current language support is Java/Kotlin/Spring only; Python, Go, C#,
  JavaScript, and TypeScript are roadmap items, not shipped. Becomes directly useful for this
  stack once JS/TS support lands.
- **QuickStack** (biersoeckli/QuickStack) — a self-hosted PaaS alternative to
  Vercel/Netlify/Railway/Heroku, notable because it takes a genuinely different architecture
  (installs and manages K3s + Longhorn under the hood) than the Docker-Compose-based
  Coolify/Dokploy incumbents already known in this space. GPL-3.0, 354 stars, started as a
  student project. The Kubernetes-native approach is an interesting STUDY item, but the
  self-hosted-PaaS niche is already saturated (a ~15-repo wave was rejected here on
  2026-08-31) and Coolify/Dokploy remain the lower-complexity default. Revisit if the K3s
  approach demonstrates a concrete operational advantage over the Compose-based incumbents.
