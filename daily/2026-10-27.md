## Today's Best Discoveries

### 1. GuardianWAF — 7.5/10
**Decision:** PROTOTYPE

**What it is** — A zero-dependency Web Application Firewall written in pure Go, shipped as a single binary. Runs standalone, as a Go library middleware, or as a Docker/Kubernetes sidecar with label-based auto-discovery.
**Why I should care** — Directly relevant to the MSSP security admin-portal SaaS and PTaaS partnership: a self-hostable WAF with SIEM export and agent tooling is something that could sit in front of client apps without a CDN-vendor WAF subscription or an nginx+ModSecurity build.
**What it could replace** — ModSecurity/OWASP CRS setup effort, or a recurring Cloudflare/AWS WAF subscription for self-hosted deployments.
**Ways I could use it** — Front a client app for an MSSP engagement; embed as Go middleware directly in a backend; export WAF events as CEF/syslog into a client SIEM; auto-protect Docker Compose services via labels.
**Agent opportunity** — Bundled MCP server with 44 tools for agent-driven configuration and threat analysis.
**Integration effort** — Low: single binary, Go library import, or sidecar, no module compilation required.
**Maturity** — Emerging: 35 stars, 9 forks, 0 subscribers, 20 open issues; single named maintainer; 79% test coverage with cross-browser E2E tests.
**License** — MIT core; cluster mode and commercial support are explicitly planned as a future separate commercial tier — not a blocker today.
**Alternatives** — ModSecurity+OWASP CRS, Cloudflare WAF, AWS WAF.
**Why this one** — Tokenizer-based cumulative threat scoring is a more nuanced middle ground between brittle regex rules and a full ML pipeline, and three deployment modes from one codebase removes typical WAF adoption friction.
**Recommendation** — Trial in front of a non-critical service to validate detection quality before a client-facing deployment.

### 2. Rostam — 7.4/10
**Decision:** PROTOTYPE

**What it is** — An embeddable Go engine combining a vector database (HNSW/IVF/Vamana, quantization, hybrid dense+sparse+BM25) and a sub-microsecond key-value store behind one `Store` interface — usable as a library, standalone server, or Raft-replicated cluster.
**Why I should care** — Collapses "vector DB + cache" into one embeddable dependency instead of running Qdrant/pgvector plus Redis separately for a self-hosted AI feature.
**What it could replace** — A two-service vector-search + KV/cache stack for a RAG or agent-memory feature.
**Ways I could use it** — Embed as a Go library for vector search + caching with zero extra infra; use the bundled MCP server for coding-agent memory; run the OpenAI-compatible semantic caching proxy to cut LLM spend; use the RAG CLI for cited document Q&A.
**Agent opportunity** — MCP stdio server purpose-built for agent memory.
**Integration effort** — Medium: library embed is simple; cluster/WASM-stored-procedure modes need more setup (Docker image for WASM, since pure-Go release binaries exclude cgo).
**Maturity** — Beta, 37 stars, 1 subscriber, 3 forks — small team for an ambitious scope. The project's own benchmark page explicitly flags its Milvus/pgvector/Qdrant comparison numbers as non-reproduced, same-session results.
**License** — Apache-2.0, no commercial restrictions.
**Alternatives** — Milvus, Qdrant, pgvector (vector only); Redis/Memcached (KV only) — both already mainstream/excluded individually.
**Why this one** — The single-engine, no-separate-server embedding model is the differentiator; throughput claims are secondary and unverified.
**Recommendation** — Prototype as an embedded library for one specific RAG/agent-memory feature; don't lean on the cluster/WASM feature set until tried directly.

### 3. Shopnex — 7.3/10
**Decision:** PROTOTYPE

**What it is** — A self-hosted, open-source e-commerce platform on Node.js/pnpm/PostgreSQL with an Astro storefront, a Shopify-aligned typed Storefront API, Liquid themes, multi-tenancy, and an out-of-process app-marketplace SDK.
**Why I should care** — Squarely in-stack (Node/Postgres), and the Shopify-aligned API/Liquid themes lower migration friction for porting a Shopify storefront to a self-hosted base.
**What it could replace** — A multi-month from-scratch build of catalog/checkout/admin/theme infrastructure, or a recurring Shopify subscription for a self-hosted use case.
**Ways I could use it** — White-label storefront for a client; custom headless storefront against the Storefront API; package a vertical extension via the app SDK; run multiple shops via `TENANCY_MODE` for agency use.
**Agent opportunity** — None documented specifically for agents; typed API and webhooks are generically automatable.
**Integration effort** — Medium: Node 22.22+/pnpm/PostgreSQL, migrations, then a setup wizard — no documented production-deployment guide yet.
**Maturity** — Experimental: 362 stars, 49 forks, 13 subscribers, 2 open issues; CI, tagged releases, roadmap doc; no stated production-readiness claim.
**License** — MIT, no commercial restrictions.
**Alternatives** — Medusa.js (mainstream, larger ecosystem), Saleor (Python/GraphQL), Shopify itself.
**Why this one** — The out-of-process app SDK ("no third-party code in the core," scoped tokens, signed webhooks) is a cleaner extensibility pattern than bolted-on plugins, and is worth studying independent of the e-commerce use case.
**Recommendation** — Local trial of the app SDK and Storefront API before considering it as a client-project base; not production-ready yet.

### 4. detest — 7.0/10
**Decision:** STUDY

**What it is** — An in-process Deterministic Simulation Testing (DST) framework for Go, built on `testing/synctest`, that systematically explores goroutine interleavings via stateless model checking to find and deterministically reproduce concurrency bugs.
**Why I should care** — DST is proven inside FoundationDB and TigerBeetle but almost never available as a drop-in library — most teams build a bespoke harness. detest packages the technique for ordinary Go code (GORM, sqlx, sqlc run unchanged above simulated client boundaries).
**What it could replace** — Ad hoc `-race -count=1000` stress loops and manual reproduction scripts for found concurrency bugs.
**Ways I could use it** — Reproduce a race before fixing it; pin a found bug as a permanent regression test via `s.ExpectViolation`; exercise Postgres/MySQL locking edge cases without a live database in CI; deterministically test retry logic against simulated flaky HTTP/queue delivery.
**Agent opportunity** — Ships an AI-agent skill as the primary intended entry point — the agent proposes targets and writes the simulation scenario.
**Integration effort** — Low for a Go codebase (`go get` + build tag); zero direct applicability to Node/Mongo.
**Maturity** — Experimental: created 2026-10-02, 0 stars, 2 forks, 0 subscribers — essentially no adoption signal; catalogued on the author's track record (k1LoW: tbls, runn, octocov) and architectural novelty rather than traction.
**License** — MIT.
**Alternatives** — `go test -race` (non-systematic), Jepsen (heavier, cluster-level, different ecosystem).
**Why this one** — The boundary-level simulation approach (simulate the client library, run real production code above it) is the reusable idea, independent of Go specifically.
**Recommendation** — Study the architecture now; revisit for direct adoption only if a Go service with real concurrency risk is in play.

## Small but High-Leverage Utility
**vertti/preflight** — A single-binary, zero-dependency validation toolkit for containers and CI: checks that a command exists and meets a version range, that env vars are set and well-formed, that files/directories exist and are writable/executable, that an HTTP endpoint or TCP port is reachable, and that a file matches a SHA256 checksum — all exiting 0/1 for direct use in `set -e` shell scripts or Docker `RUN` steps. This replaces the usual pile of hand-rolled `wait-for-it.sh`/`curl`-based health-check snippets scattered across Dockerfiles and CI configs with one documented, tested binary (gosec/govulncheck scanning, 20+ linters, Apache-2.0).
