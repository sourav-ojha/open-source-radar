# Open Source Radar — 2026-11-17
_Rotation slot 7 — experimental projects and hidden gems_

## Executive Summary
Today's slot surfaced three independent takes on the same underlying problem —
giving an AI agent real credentials and real system access without giving up
control of what it actually does with them — at three different layers: Coral
gates individual agent-generated tool calls against a per-tool policy, Tego
enforces a file/network contract outside the agent at the Linux kernel level,
and db-branch gives an agent a disposable, copy-on-write database branch to
act against instead of production. None of the three is mature; all three are
worth knowing about now rather than after adopting an agent workflow that
needs them. Separately, a small CLI daemon (speedrunner) turned up genuinely
useful, benchmarked speedups for everyday tools like the AWS CLI and eslint —
exactly the kind of "hidden gem" this slot exists to find. Two previously
catalogued projects, Reticle and Meteroid, both shipped real architecture
changes since last review.

## Today's Best Discoveries

### 1. Coral — 8.2/10
**Decision:** PROTOTYPE

**What it is** — A self-hosted gateway between AI agents and the systems they
work on. Agents call tools by writing short TypeScript programs against a
provider catalog (GitHub, Slack, Linear, or any OpenAPI/MCP server you add);
Coral checks every underlying call against a per-tool Allow/Ask/Block policy
before injecting credentials and forwarding it. A working program can be
saved as a reusable, policy-gated custom tool.
**Why I should care** — Most MCP gateways only decide which tools an agent
can see — once it can call `update_record`, it can call it however that tool
allows. Coral's unit of control is a custom tool, which is code, so a rule
like "only close tickets inactive 30+ days" is enforceable at the tool level,
not just the provider level — directly useful for the constrained,
auditable third-party-system access the MSSP/PTaaS context actually needs.
**What it could replace** — A hand-built MCP tool-permission layer in front
of internal or customer systems an agent needs to touch.
**Ways I could use it** — Gate an agent's GitHub/Slack/Linear access behind
Allow/Ask/Block; let an agent compose a one-off integration as code and
promote it to a shared tool once proven; bring an internal system's OpenAPI
spec as a provider for the same policy/audit layer; cut repeated agent token
spend by reusing saved tools instead of re-deriving API choreography each run.
**Agent opportunity** — Native MCP server — add a workspace's MCP URL to
Claude Code, Codex, or any MCP client.
**Integration effort** — Medium — solo trial via the desktop app is trivial;
team rollout needs Docker Compose/Kubernetes, an OIDC identity provider, a
reverse proxy, and Postgres.
**Maturity** — Emerging but well-backed: created 2026-04-03, 5,003 stars, 224
forks, 143 open issues, latest tag v1.8.0 (2026-11-13), pushed the same day
as this review.
**License** — Apache-2.0, confirmed directly from the LICENSE file.
**Alternatives** — ThinkWatch, Midplane, Octelium, DatI (all already
catalogued MCP/agent gateways, each scoped to one system — an AI API, a
database, a network layer).
**Why this one** — Code-as-custom-tool gives finer-grained, reusable control
than a flat tool-visibility list, and it's general-purpose rather than tied
to one backing system.
**Recommendation** — Stand up the desktop app solo against one real provider
(GitHub or Slack) to see whether the saved-tool mechanism actually reduces
repeated agent work before considering a team server rollout.

### 2. db-branch — 7.3/10
**Decision:** PROTOTYPE

**What it is** — Instant, copy-on-write database branches for self-hosted
MySQL and PostgreSQL, built on ZFS clones (sub-second for Postgres, ~3s for
MySQL, zero bytes copied at creation), with one API surface — CLI, REST, web
console, MCP server — over a single node or a Raft-replicated cluster.
**Why I should care** — This is the Neon/PlanetScale instant-branching
pattern, self-hosted and engine-native to Postgres/MySQL, for a team running
its own database on EC2/EKS rather than a managed branching vendor.
**What it could replace** — Hand-scripted pg_dump/restore or logical-
replication copies for CI, PR review, or agent-driven migration testing.
**Ways I could use it** — A database-per-PR torn down automatically via
`--ttl`; let a coding agent create a branch over MCP, run a risky migration,
inspect the result, then delete it — production never touched; test a major-
version upgrade against one branch with `--check-only` before touching the
base; instant checkpoint-and-restore before a risky manual change.
**Agent opportunity** — Built-in MCP server; the README's first listed use
case is literally "AI agent sandboxes."
**Integration effort** — Medium — needs Linux and a real ZFS pool, which is
not the default on most cloud instances including standard EC2/EBS setups.
**Maturity** — Very early: created 2026-11-13 (4 days before this review), 61
stars, self-labeled Beta, latest tag v0.2.5. Documentation depth (bilingual
docs, OpenAPI spec, live console demo, cluster benchmarks) is unusually high
for a 4-day-old public repo, suggesting private development predates the
public release.
**License** — Apache-2.0 for the core project. Separate closed-source paid
modules (auth/SSO, audit, point-in-time history, diff, FSx storage) are
gated by a license key — flagged, but they sit alongside the open core
rather than gating it, and there is no hosted/cloud offering.
**Alternatives** — Neon, PlanetScale (managed, proprietary — the model this
clones self-hosted). No other self-hosted ZFS-clone branching tool found
already catalogued.
**Why this one** — No existing catalog entry covers self-hosted database
branching at all; this fills that gap with a technically sound mechanism,
even though the public track record is four days long.
**Recommendation** — Worth testing the branching mechanism and MCP
integration against a real Postgres database on a ZFS-backed dev box, with
the explicit expectation that this is a brand-new public repo, not yet
battle-tested.

### 3. Tego — 7.0/10
**Decision:** PROTOTYPE

**What it is** — Runs any AI agent that's a Linux process (an MCP server, a
Claude Code/Codex session, a 24/7 assistant) under a written YAML contract of
allowed files, programs and network hosts, enforced outside the agent by
Tego's supervisor and, at higher tiers, the Linux kernel itself. Held actions
need human approval; every run gets a hash-chained, tamper-evident record.
**Why I should care** — An agent runs as you, next to your keys and your
network; a prompt injection or a plain mistake can reach both. Policy that
lives inside the agent only holds while the agent follows it. Tego's bet —
enforcement has to sit outside the agent's control, in the kernel — is the
only version of this that a convinced or compromised agent genuinely can't
talk its way past.
**What it could replace** — A hand-rolled seccomp/landlock sandbox plus an
audit trail around an agent process given real credentials.
**Ways I could use it** — Wrap a coding agent in a contract limited to a repo
directory and named hosts before granting it write access; black-box record
any agent command via `tego watch` with no contract written first; gate
individual MCP server tools live via the MCP relay; set hard run limits
(tokens, cost, time, stall, repeats) so a runaway session hits a stop instead
of an open-ended bill.
**Agent opportunity** — Ships ready-made contracts for Claude Code, OpenAI
Codex, the Claude Agent SDK, and the Anthropic Python SDK.
**Integration effort** — Low for a first trial (single Go binary, no root
needed at tier 1); Medium if adopting kernel-level tiers, which need root.
**Maturity** — Experimental: created 2026-11-02 (2 weeks old at review), 25
stars, latest tag v0.1.3. The project's own README and a dedicated
`docs/GAPS.md` explicitly list known limits before asking anyone to rely on
it — an unusually candid self-assessment.
**License** — Apache-2.0.
**Alternatives** — Coral (this run) enforces at the agent-to-provider call
boundary rather than the OS process boundary — complementary, not a
substitute. Destructive Command Guard blocks specific dangerous shell
commands rather than a full contract.
**Why this one** — It's the only project seen here enforcing agent
constraints at the kernel level rather than inside an SDK, gateway, or MCP
layer.
**Recommendation** — Try tier 1 (no root) around one real agent session with
file/network access, with the explicit expectation that the maintainers'
own documented gaps mean it is not yet a complete safety net.

## Meaningful Updates

**Reticle** — PROTOTYPE, 7.7→7.9/10. v2.13.1 (2026-09-02) → v3.10.7
(2026-11-17). Real architecture change, not a patch bump: every agent
"drive" of the app is now kept automatically as a replayable test with no AI
in the loop and no token cost on reruns, and a saved recording only becomes
a real assertion once the original observation stops reproducing — so a
replay can't trivially pass by checking a recording against itself. Also
collapsed the agent-facing tool surface from seventeen tools to nine. Stars
465→1,287, forks →254, open issues 100→276. Recommendation unchanged
(PROTOTYPE, same FSL caveat on the server package), but the self-writing-test
mechanism is a stronger reason to actually trial it. Catalog updated: Yes.

**Meteroid** — STUDY, 7.2→7.4/10. v1.0.0-rc7 (2026-08-24) → v2.2.3
(2026-11-13) — out of release-candidate status into a GA v2.x line, plus two
real correctness features: "billing determinism" (a movable clock,
charge-keyed line IDs, one totals function) and a "billing safety net"
(billing-core, rule registry, invariants, a document corpus, an invoice
model). Stars 1,231→1,362, forks →87. Does not change the recommendation —
Lago remains the safer immediate adopt — but strengthens the architecture-
study case. Catalog updated: Yes.

## Small but High-Leverage Utility
**speedrunner** (anthonyGosme/speedrunner, 7.6/10, USE NOW) speeds up
everyday CLI tools — aws, az, gcloud, ansible, eslint, rubocop, composer,
and hundreds more written in Python, Ruby, PHP, or Node — by loading each
one once in a background daemon and forking a ready process for every
subsequent call, falling back to a native run whenever it can't serve a call
faithfully. The project's own benchmarks: a multi-tool checks script 24.0s →
5.3s warm (4.5x), eslint on one file 328ms → 43ms, mypy 213ms → 50ms, a
pre-commit hook run 1.11s → 0.31s — all byte-identical to native output. It's
only 18 stars and under three weeks old, but it ships a real reproducible
benchmark suite (96 commands, VPS/Docker results checked into the repo)
rather than unverified claims, and the `--native` escape hatch makes it a
low-risk, reversible install. Worth enrolling the AWS CLI and eslint
specifically given Sourav's stack.
