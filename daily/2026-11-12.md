## Today's Best Discoveries

### 1. PgQue — 7.8/10
**Decision:** PROTOTYPE

**What it is** — A pure PL/pgSQL revival of Skype's 2006-era PgQ: a durable, fan-out event log inside Postgres using snapshot-based batching and table-rotation instead of per-row `UPDATE`+`DELETE`, installable as plain SQL on any Postgres 14+ including fully managed providers (RDS, Aurora, Supabase, Neon) — no C extension, no external daemon.
**Why I should care** — Most of the stack already runs on managed Postgres. This gives Kafka-topic-style fan-out (independent consumer cursors on one shared log) without adding a broker and without the dead-tuple bloat that SKIP LOCKED queues (PGMQ, pg-boss, River, Oban) are documented to hit under sustained load.
**What it could replace** — Standing up Kafka/Redis Streams/SQS purely for internal event distribution; hand-rolled outbox tables.
**Ways I could use it** — Internal event fan-out for an admin-portal SaaS; an audit/event trail with full Postgres ACID guarantees; multiple services independently consuming the same event stream from an existing RDS/Aurora instance; a lightweight webhook-distribution backbone.
**Agent opportunity** — None directly; this is backend plumbing.
**Integration effort** — Low — a SQL file plus a `pg_cron` schedule call on an existing database.
**Maturity** — Emerging (created April 2026, v0.2.2, 1,874 stars, 102 open issues).
**License** — Apache-2.0, unrestricted.
**Alternatives** — PGMQ, River, Que, pg-boss, Oban (job-queue frameworks, not true fan-out logs); Kafka/Redis Streams/SQS (external infra).
**Why this one** — The only option in its own comparison table that is both zero-bloat under load and requires no C extension — meaning it actually runs on RDS/Aurora rather than just self-managed Postgres. Author is Postgres.ai's founder; independently reviewed by Postgres consultant Christophe Pettus.
**Recommendation** — Prototype against a real internal event-distribution need on an existing managed-Postgres instance.

### 2. OpenRun — 7.6/10
**Decision:** PROTOTYPE

**What it is** — A self-hosted, declarative GitOps deployment platform: apps are a few lines of Git config, deployed to a single Docker/Podman node or a Kubernetes cluster from the same spec, with OIDC/SAML auth, RBAC, audit logs, and auto-provisioned per-app database service bindings.
**Why I should care** — Most self-hosted deploy platforms in this niche are imperative Heroku clones. OpenRun is declarative by default (every change is a reviewable Git diff) and targets both a single box and Kubernetes from one spec — directly relevant for moving an internal tool from EC2 to EKS without a rewrite.
**What it could replace** — Hand-rolled OIDC/SAML/RBAC/audit middleware per internal dashboard; manual per-app database credential provisioning; a separate Nginx/Traefik reverse-proxy layer.
**Ways I could use it** — Deploy internal MSSP admin dashboards with auth/RBAC/audit built in; managed SQLite with Litestream-to-S3 backups for small tools; scale idle internal tools to zero.
**Agent opportunity** — None identified.
**Integration effort** — Medium — single binary for Docker, or the same config against Kubernetes; non-AppSpec frameworks (including Node/Next.js) need a Dockerfile.
**Maturity** — Emerging despite a 3-year history (997 stars, single dominant maintainer, CNCF Landscape-listed, OpenSSF Best Practices badge).
**License** — Apache-2.0, unrestricted.
**Alternatives** — Coolify, Dokku, CapRover (imperative, no native Kubernetes path); Retool (hosted UI builder, different problem); raw Kubernetes+Helm+identity-proxy (far more manual setup).
**Why this one** — Structural differentiators, not cosmetic ones: declarative-by-default, dual single-node/Kubernetes targets, and automatic per-app database isolation — the three things the saturated self-hosted-PaaS wave (compartment, miabi, hakopod, cubeship, ninedeploy) hasn't combined.
**Recommendation** — Prototype by deploying one internal admin tool through it.

### 3. Ruvio — 7.5/10
**Decision:** PROTOTYPE

**What it is** — A single-process, Rust-built, RESP-compatible key-value server (`redis-cli` connects unmodified) that folds a distributed lock service, conditional writes, a change feed, and a delay queue into native commands (`LEASE`, `SETV`, `CHANGES`, `ZMOVEDUE`) instead of requiring separate bolted-on systems.
**Why I should care** — A small Node/Postgres service that needs caching, a distributed lock, a delay queue, and simple change notification today usually means Redis plus Redlock plus a scheduler library plus ad-hoc CDC. Ruvio is a genuine attempt to collapse that into one binary speaking a protocol everything already knows.
**What it could replace** — Redis + Redlock + a job-queue library + bespoke CDC, for services that don't need each at full scale independently.
**Ways I could use it** — Fencing-token distributed locks for a cron job that must not double-run across instances; a due-job delay queue without BullMQ/pg-boss; a lightweight change feed for cache-invalidation fan-out.
**Agent opportunity** — None identified.
**Integration effort** — Low — Docker image or prebuilt binary, drop-in RESP protocol, six first-party clients including Node.js.
**Maturity** — Experimental — about one month old (ruvio-0.4.0, 219 stars) but unusually complete packaging (crates.io/NuGet/npm/PyPI/AUR all published) for the stage.
**License** — AGPL-3.0 on the server (flagged — fine for plain self-hosted internal use, a real consideration for any redistribution/hosting scenario), MIT on client libraries.
**Alternatives** — Redis/Valkey + Redlock + BullMQ/pg-boss + custom CDC (the stack this replaces); KeyDB/DragonflyDB (faster RESP servers without the native lock/queue/CDC primitives).
**Why this one** — Bakes correct fencing-token lock semantics directly into a command instead of leaving Redlock-style correctness to the caller, with a documented per-feature memory cost.
**Recommendation** — Try as a Redis replacement for one low-stakes internal service to kick the tires on the lock/delay-queue primitives before depending on it for anything load-bearing.

### 4. Keeper.sh — 7.4/10
**Decision:** PROTOTYPE

**What it is** — A self-hosted calendar-syncing engine pulling from Google Calendar, Outlook, iCloud, Fastmail, CalDAV, or read-only iCal/ICS feeds and pushing aggregated events to one or more destinations to avoid cross-calendar double-booking, with a REST API and a global MCP server for agent-driven calendar management.
**Why I should care** — Directly solves the real problem of juggling a business calendar, work calendar, and personal calendar — and it's a clean case study in AGPL-as-trust-signal monetization: self-hosting unlocks every "Pro" feature for free, and the hosted tier is priced purely on convenience, not withheld features.
**What it could replace** — Manual cross-calendar copy-pasting to avoid conflicts; hand-rolled per-provider OAuth and incremental-sync code for any calendar-aware tool.
**Ways I could use it** — Personal multi-calendar conflict prevention; a ready-made MCP surface to give an agent calendar read/write authority instead of writing per-provider OAuth/polling from scratch; privacy-filtered calendar publishing.
**Agent opportunity** — MCP server (`trigger_sync`, `pause_sync`) — usable as-is as a "give an agent calendar authority" building block.
**Integration effort** — Medium — Docker Compose, either a convenience bundled image or five granular services behind Postgres/Redis/Caddy.
**Maturity** — Emerging — 1,465 stars, v2.31.0 (actively released), solo-founder-dominant commit history.
**License** — AGPL-3.0, flagged — self-hosting for internal use is unaffected; redistributing a modified version as a hosted service would trigger the network-use clause.
**Alternatives** — Native provider sync (doesn't solve the cross-provider problem); Zapier/Make calendar automations (no self-host path, no MCP); hand-rolled sync-token polling scripts.
**Why this one** — The two specific design choices called out by the author — an outliving mapping row for reliable eventual deletion, and a cleanup sweep that only ever touches events it created itself — are exactly the two failure modes that are easiest to get silently destructive in any calendar-sync tool, and the engine is AGPL specifically so that claim is checkable.
**Recommendation** — Self-host to solve a real scheduling conflict, and study the monetization model regardless of tool adoption.

## Meaningful Updates
**Enroute** — v0.3.0 → v0.4.0 (score 6.2 → 6.6); catalogued 2026-10-29. What changed: horizontal scaling for the ledger tier (previously only compute scaled; now tested to 300,000 active repositories and 20,000 pushes/sec across a cluster) with zone-aware replica placement, plus production-grade S3/Google Cloud Storage/Azure Blob Storage support, SHA-256 repository support, remote mirroring/fetch, end-to-end OpenTelemetry tracing, and a DNS-rebinding fix for remote-fetch addresses. Why it matters: closes the main maturity gap noted at first review (no production object-store support, single-node ledger only). Does this change the recommendation: no — still STUDY, as the broader CI/CD/code-review vision remains unshipped and an upgrade from 0.3.0 requires a storage-format migration, not a drop-in swap. Catalog updated: Yes.
