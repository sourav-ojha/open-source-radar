# Open Source Radar — 2026-11-23
_Rotation slot 6 — infrastructure, observability, deployment_

## Executive Summary
Today's slot surfaced two genuinely stack-relevant infrastructure tools and two more
speculative building blocks. Databasus is the standout: a single self-hosted tool that
backs up both PostgreSQL and MongoDB — the two databases actually in use here — with real
restore verification, a step most comparable tools skip entirely. Greenmask rounds out the
Postgres side with mature anonymization and database subsetting. OpenMeter and Stategraph
are both plausible but less urgent: OpenMeter is a credible usage-metering/billing building
block for a future micro-SaaS product but ships only beta releases, and Stategraph is a
solid Terraform/OpenTofu PR-automation bot in an already fairly crowded niche. One
suspicious-engagement candidate (valqore) was held off rather than catalogued.

## Today's Best Discoveries

### 1. Databasus — 8.4/10
**Decision:** USE NOW

**What it is** — Self-hosted database backup platform covering PostgreSQL (physical,
incremental, WAL-streaming PITR, HA timeline-following for Patroni/CloudNativePG), MySQL,
MariaDB and MongoDB (logical), plus managed Neon/Supabase Postgres. Performs a real restore
after every backup to verify it's actually usable, with a per-table row-count report.
**Why I should care** — It backs up both halves of a MERN/Postgres stack under one tool,
and catches the single most commonly skipped failure mode in a hand-rolled backup setup: a
backup that silently can't be restored.
**What it could replace** — A hand-rolled cron + pg_dump/mongodump + `aws s3 cp` script
with no retention logic, no restore testing, and no team access control.
**Ways I could use it** — Nightly PITR Postgres backups with HA timeline-following; logical
MongoDB backups on the same schedule; backing up a managed Neon/Supabase instance;
workspace-scoped access for an MSSP client engagement with audit logs.
**Agent opportunity** — None identified; purely operational tooling.
**Integration effort** — Low — Docker (automated script, compose, or Helm), read-only DB
user by default, built-in SSH tunnel.
**Maturity** — Mature (18 months old, 619 forks, active 11-issue tracker, frequent
releases).
**License** — Apache-2.0, no restrictions.
**Alternatives** — pgBackRest/WAL-G/Barman (Postgres-only, no UI, no MongoDB); pgbackweb
(similar web-UI tool but Postgres-only, no PITR/HA, no restore verification).
**Why this one** — It's the only tool found that covers both PostgreSQL and MongoDB with
genuine restore verification in one self-hosted package.
**Recommendation** — Install and point it at a real dev or staging database first.

### 2. Greenmask — 7.5/10
**Decision:** PROTOTYPE

**What it is** — Single-binary CLI for PostgreSQL (MySQL in beta) logical dumping,
anonymization, synthetic data generation and restoration — a stateless drop-in replacement
for pg_dump/pg_restore with deterministic hash-based masking and referentially-intact
database subsetting.
**Why I should care** — PII masking and right-sized dev/staging subsets are recurring,
error-prone tasks, and this overlaps the data-handling care the MSSP/PTaaS side already
requires.
**What it could replace** — Hand-rolled Faker-style scripts that re-implement deterministic
masking and referential integrity by hand.
**Ways I could use it** — Subset production Postgres for local dev; mask PII before handing
a dump to staging or a contractor; generate synthetic demo data; drop into an existing
pg_dump/pg_restore backup pipeline.
**Agent opportunity** — None identified.
**Integration effort** — Low — single binary or Docker, operates on a logical dump.
**Maturity** — Mature for PostgreSQL ("production ready" per its own docs); MySQL beta.
**License** — Apache-2.0, no restrictions.
**Alternatives** — pg_dump/pg_restore (no masking); commercial platforms like Tonic.ai
(broader, not free/self-hosted at this scale).
**Why this one** — Combines subsetting, masking, and synthetic-data generation in one
Postgres-native tool rather than three separate scripts.
**Recommendation** — Prototype against one Postgres dataset needing masking or subsetting.

### 3. OpenMeter — 7.4/10
**Decision:** PROTOTYPE / STUDY

**What it is** — API-first, composable usage-metering and billing infrastructure: ingests
CloudEvents usage events, aggregates them into real-time meters, drives access-limit
enforcement, and feeds pricing/subscriptions/credits/invoicing — adoptable end-to-end or
piecemeal alongside an existing payment provider.
**Why I should care** — Directly matches this radar's own "billing" micro-SaaS building
block callout: a credible metering/enforcement layer instead of building one from scratch.
**What it could replace** — Hand-rolled event counters (Postgres/Redis) that have to stay
in sync with whatever drives billing — a common source of silent billing/limit drift.
**Ways I could use it** — Usage-based pricing for an API/AI-token feature; real-time
usage-limit enforcement sharing numbers with billing; prepaid credits; metering-only
adoption leaving invoicing to Stripe.
**Agent opportunity** — None identified.
**Integration effort** — Medium — real platform (event ingestion, aggregation, API), not a
single binary; self-hosted via Docker/Kubernetes or OpenMeter Cloud.
**Maturity** — Emerging — releases are explicitly beta (v1.0.0-beta.238) with possible
breaking changes, though the underlying metering engine is reported to predate this OSS
core in production.
**License** — Apache-2.0; self-hosted core is the full engine, not a crippled version.
**Alternatives** — Lago (10.9k stars, more complete end-to-end billing); Meteroid
(catalogued, subscription/invoicing-first); OpenMeter is metering/enforcement-first.
**Why this one** — More composable with an existing payment/tax stack than a full
billing platform, if only the metering/enforcement piece is actually missing.
**Recommendation** — Study the API shape now; prototype only once a real usage-priced
feature needs it, given the beta status.

### 4. Stategraph — 7.1/10
**Decision:** PROTOTYPE

**What it is** — Self-hosted Terraform/OpenTofu (plus Terragrunt, CDKTF, Pulumi)
pull-request automation: plans on PR, applies on comment or merge, as jobs on your own CI
runner with your own cloud credentials. Adds directory locks, OPA/Conftest and Checkov
scans, cost estimates in the PR, and scheduled drift detection.
**Why I should care** — A plan/apply-on-PR workflow for Terraform is something that
otherwise gets hand-assembled in GitHub Actions over time; this packages the operational
edges a hand-rolled version usually skips.
**What it could replace** — A hand-wired GitHub Actions pipeline for Terraform plan/apply
extended piecemeal for locking, cost estimates, and policy gating.
**Ways I could use it** — Plan-on-PR/apply-on-merge for AWS Terraform changes; directory
locks against concurrent-PR races in a monorepo; policy/security-scan gating; nightly drift
detection.
**Agent opportunity** — None — contrast with the already-catalogued Kumoss, which
generates Terraform from natural language rather than automating a human-authored PR.
**Integration effort** — Medium — self-hosted server plus GitHub/GitLab webhook and CI
runner wiring.
**Maturity** — Emerging (created 2024-10, actively developed, real company with a paid
cloud tier alongside the open-source server).
**License** — MPL-2.0 — file-level weak copyleft, no restriction on using it as-is.
**Alternatives** — Atlantis (mainstream, excluded by policy) — Stategraph adds directory
locks, built-in cost estimates and multi-engine support on top.
**Why this one** — More feature-complete than the mainstream Atlantis baseline, and a
lower-risk first step than Kumoss's AI-generates-the-Terraform approach.
**Recommendation** — Try it against one real Terraform repo's PR workflow.

## Small but High-Leverage Utility
**kwatch** — a lightweight, rule-based (no LLM) Kubernetes failure monitor: it runs inside
the cluster, traces a cascade of pod/container failures back to the one root cause, and
sends a single consolidated Slack/Discord/email message instead of fifty separate alerts.
No LLM cost, no external API dependency — a near-zero-maintenance addition to an EKS
cluster for fast first-pass triage before reaching for a heavier tool like the
already-catalogued SherlockOps. Elastic License 2.0 (source-available, not OSI-approved)
flagged: fine for internal use, but it blocks offering kwatch itself as a hosted/managed
service to third parties — relevant if ever packaged inside an MSSP offering.

## Worth Watching

  Databasus for the databases actually in the stack. Would need a 1.0 release and some

- **valqore** — An infrastructure-governance scanner (Kubernetes/Terraform/cloud) claiming

  verification of the rule claims and a clearer license before reconsidering.

  clearly distinct angle on a future pass.
