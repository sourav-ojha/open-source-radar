# Open Source Radar — 2026-09-10
_Rotation slot 2 — product infrastructure, APIs, backend components_

## Executive Summary
Today's slot pulled toward "boring glue you'd otherwise rebuild per project" rather than
flashy frameworks — a unified email-sending gateway, a permissively-licensed MinIO
alternative, a mature webhook-delivery service, a self-hosted analytics platform, and a
CRDT sync engine for SQLite. A recurring pattern across the deep-review set: three of the
five candidates (Convoy, SQLite Sync, and rejected Notifuse) turned out to carry
non-OSI, source-available licenses (Elastic License 2.0 twice, Business Source License
once) that the GitHub API's license field either mis-reported as `NOASSERTION` or left
blank — only caught by reading the raw LICENSE file directly. Given the intent to embed
things in an MSSP SaaS and PTaaS partnership, that gap between "GitHub says" and "the
actual license file says" is worth remembering as a standing verification step, not a
one-off.

## Today's Best Discoveries

### 1. Posthorn — 8.2/10
**Decision:** PROTOTYPE

**What it is** — a single Go binary/Docker container that unifies outbound email for
self-hosted apps: three ingress shapes (HTTP form, HTTP API, SMTP listener) converging on
one set of provider credentials (Postmark, Resend, Mailgun, AWS SES, or SMTP relay).
**Why I should care** — every self-hosted app that sends mail otherwise carries its own
copy of the provider API key and its own retry/rate-limit logic; Posthorn collapses that
into one deployed service.
**What it could replace** — hand-rolled per-app email integration code, and the fact
that several cloud hosts (DigitalOcean, Lightsail, Linode, Vultr) block outbound SMTP
entirely.
**Ways I could use it** — front contact forms with built-in anti-spam; route
password-reset/alert emails from cron jobs and serverless workers through the HTTP API
with idempotent retries; bridge SMTP-only tools (Gitea, Mastodon, NextCloud, Authentik)
to a modern provider; centralize SES credentials across several small projects.
**Agent opportunity** — no MCP surface, but the bearer-auth HTTP API is trivially
callable as a "send email" tool from any automation script.
**Integration effort** — Low: one Docker container, one TOML config, one provider key.
**Maturity** — Emerging (created 2026-04-27) but unusually polished: dedicated docs site
with ten written recipes, tagged v1.2.0 release, active CI, an explicit "what it is not"
scoping section.
**License** — Apache-2.0, no restrictions.
**Alternatives** — Listmonk (different scope, marketing email), Postal/Hyvor Relay (run
their own SMTP fleet rather than relaying), and a same-day wave of similar
"self-hosted-email-via-SES" projects (reloop, opensend, larasend) that were all thinner
on docs or narrower in scope.
**Why this one** — provider-agnostic three-ingress design plus documentation discipline
clearly ahead of the rest of the wave it surfaced alongside.
**Recommendation** — deploy in front of one low-stakes self-hosted app (a contact form or
cron digest) to validate the HTTP API and retry behavior before centralizing more mail
traffic through it.

### 2. RustFS — 7.9/10
**Decision:** PROTOTYPE

**What it is** — a distributed, S3-API-compatible object storage system in Rust,
explicitly positioned as the Apache-2.0 alternative to MinIO's AGPL-3.0.
**Why I should care** — MinIO's AGPL license is a real constraint for anything embedded
in or shipped with a commercial product; RustFS targets that exact gap with the same S3
API surface.
**What it could replace** — paying for AWS S3 in dev/test/staging, or MinIO where its
license blocks commercial redistribution.
**Ways I could use it** — local S3-compatible storage for CI/dev environments; backing
store for self-hosted apps needing an S3 API; drop-in MinIO swap in existing Compose
stacks.
**Agent opportunity** — none directly; it's storage infrastructure other tools sit on
top of.
**Integration effort** — Low for single-node, Medium for distributed multi-node given
replication/pool-expansion configuration.
**Maturity** — Large and very active (31,915 stars, created 2023-11-23) but still
pre-1.0 — latest tag is `1.0.0-rc.5-preview.3` from 2026-04-28, and GitHub Releases has
nothing published at all; tag history clearly lags the continuous commit activity.
**License** — Apache-2.0, confirmed via repo LICENSE file; README explicitly frames this
as a deliberate anti-AGPL choice.
**Alternatives** — MinIO (incumbent, AGPL-3.0), Kodiqa-Solutions/VaultS3 (lighter, but
also AGPL-3.0 — filed Worth Watching), Garage (different design center, not deep-reviewed).
**Why this one** — the license, not the feature set, is the differentiator that matters
here.
**Recommendation** — stand it up as a MinIO replacement in dev/CI first and specifically
test erasure-coding/healing behavior under simulated node failure before trusting it with
anything production-critical, given the pre-1.0 tagging.

### 3. Openpanel — 7.6/10
**Decision:** PROTOTYPE

**What it is** — a self-hostable, open-source product analytics platform positioned as a
Mixpanel alternative.
**Why I should care** — product analytics is a recurring SaaS cost for any product with
paying customers, including an MSSP admin-portal SaaS.
**What it could replace** — a Mixpanel/Amplitude subscription for internal or
lower-traffic products, and third-party data egress where privacy commitments matter.
**Ways I could use it** — self-host analytics for the admin-portal SaaS or PTaaS
tooling; instrument a side project without per-event billing; internal feature-adoption
dashboards.
**Agent opportunity** — none identified; pure product infrastructure.
**Integration effort** — Medium: multi-service Docker stack (dashboard, ingestion API,
worker, database), not a single binary.
**Maturity** — Mature and active — 6,909 stars, created 2024-02-29, 47 open issues
actively triaged.
**License** — **AGPL-3.0, flagged loudly.** Self-hosting internally is fine; embedding
into a closed-source hosted product needs explicit legal review first.
**Alternatives** — Mixpanel, Amplitude, PostHog; openreplay/openreplay (session replay +
analytics, 12,824 stars, mixed/fragmented license) was surfaced in the same search but is
already an established name in this space, so not independently deep-reviewed.
**Why this one** — real maturity and an active issue backlog rather than an early-stage
experiment.
**Recommendation** — self-host for internal/non-commercial-facing analytics first; get
explicit legal clarity on AGPL before using it as the analytics layer inside any paid,
closed-source product surface.

### 4. Convoy — 7.4/10
**Decision:** PROTOTYPE

**What it is** — a cloud-native webhooks gateway: accepts events and reliably delivers
them to subscriber URLs, handling retries, fanout, and delivery observability.
**Why I should care** — any product offering webhooks to its own customers needs exactly
this, and building durable retry/idempotency/dead-letter handling in-house is easy to
under-scope.
**What it could replace** — a hand-rolled retry-with-backoff queue for outbound webhook
delivery, and building delivery-status visibility from scratch.
**Ways I could use it** — power a "notify customers" webhook feature for a SaaS product;
give customers a self-service webhook-subscription UI via Convoy's own dashboard; fan
events to multiple internal services during a migration.
**Agent opportunity** — none identified; backend infrastructure.
**Integration effort** — Medium: requires Postgres + Redis, not a single binary.
**Maturity** — Established — 2,862 stars, created 2021-04-17, latest tag v26.7.6
(2026-08-27), 43 open issues, pushed yesterday.
**License** — **Elastic License 2.0, flagged loudly — not an OSI-approved open-source
license.** Confirmed by reading the raw LICENSE file after the GitHub API's license field
returned `NOASSERTION`. Explicitly prohibits reselling it as a hosted/managed service
exposing a substantial set of its features — directly relevant given the MSSP SaaS
context. Internal/embedded use appears permitted; get this read by someone with legal
context before any customer-facing deployment.
**Alternatives** — webhookx-io/webhookx (Apache-2.0, cleaner license, far less mature —
filed Worth Watching), didil/inhooks (incoming-only, different problem).
**Why this one** — the most mature, proven implementation of reliable webhook delivery
found this run, license caveat notwithstanding.
**Recommendation** — evaluate for internal/embedded use only, not as a resold hosted
service; test retry/idempotency under simulated subscriber downtime before depending on
it for customer-facing delivery guarantees.

### 5. SQLite Sync — 7.1/10
**Decision:** STUDY

**What it is** — a multi-platform SQLite extension providing CRDT-based, conflict-free
offline-first sync to SQLite Cloud, self-hosted PostgreSQL, or self-hosted Supabase, plus
a Block-Level LWW mode built for concurrent markdown editing.
**Why I should care** — "multiple processes/agents write to local SQLite and need it to
merge without conflicts" is a real problem, and it's directly relevant to the
AI-agent-memory theme that keeps surfacing on this radar.
**What it could replace** — a custom conflict-resolution/sync protocol for offline-first
apps, or ad-hoc file locking for multi-agent shared state.
**Ways I could use it** — sync a local SQLite database used by a desktop/edge tool to
self-hosted Postgres with one function call; give multiple AI-agent instances a shared,
conflict-free memory database; let multiple agents edit different sections of one
markdown file and merge cleanly via Block-Level LWW.
**Agent opportunity** — explicitly positioned by the maintainers for AI-agent memory
sync and multi-agent markdown collaboration.
**Integration effort** — Low to add sync to an app already using SQLite; Medium to stand
up a correct self-hosted Postgres sync target.
**Maturity** — Emerging (created 2025-05-13) but backed by a funded team (SQLite Cloud,
Inc.) building a family of related SQLite extensions, 558 stars, 2 open issues.
**License** — **Elastic License 2.0 (modified), flagged loudly — not OSI open source.**
Same restriction class as Convoy above: source-available, hosting it as a competing
service is restricted. Also an explicit open-core funnel toward the maker's paid SQLite
Cloud product, though the self-hosted Postgres/Supabase path is real and documented.
**Alternatives** — Yjs/Automerge (general-purpose CRDT libraries, not SQLite-specific);
the already-catalogued mex living-codebase wiki and the large "agent memory" wave
rejected 2026-09-09 solve a related but different problem (memory store vs. sync engine).
**Why this one** — the Block-Level LWW mode for multi-agent markdown editing is a
genuinely different, narrower architecture than the general-purpose memory-store tools
flooding this space.
**Recommendation** — test against a multi-agent shared-memory or offline-first prototype
to understand the architecture, but the license and open-core incentive make it premature
to standardize on beyond experimentation.

## Worth Watching
- **webhookx-io/webhookx** — Apache-2.0 webhook gateway (297 stars, pushed 2026-08-18).
  Would need more production track record and community size to compete with Convoy
  directly, but its clean license is the exact thing Convoy's Elastic License 2.0 rules
  out for resale — worth revisiting if it matures.
- **Kodiqa-Solutions/VaultS3** — lightweight S3-compatible object storage server with a
  built-in web dashboard (1,598 stars, 7 months old). Interesting for its simplicity, but
  AGPL-3.0 gives it the same license friction as MinIO, and RustFS already covers the
  permissively-licensed version of this niche.
- **AngusKit/AngusInsight** — lightweight, zero-third-party-egress self-hosted product
  analytics (GPL-3.0, 85 stars, part of a broader "AngusKit" suite). Too new and thin to
  recommend over Openpanel yet, but worth another look if it gains independent traction
  outside its parent suite.

## Rejected / Duplicate Candidates
- **R44VC0RP/opensend** — too new to evaluate: created the day before this review, 0
  issues, no license file at review time.
- **Notifuse/notifuse** — unclear/restrictive licensing: Business Source License 1.1, not

- **Webhook capture/debug/replay wave** (webhook-tester, webhook-debugger-logger, inhook,
  webhook-debugger x2, stripeek, request-catcher) — duplicate/immature; all under 150
  stars with no standout maturity, and this niche's prior entry (viewhook) was found
  archived/abandoned on 2026-08-29.

## Run Notes
GitHub search API (`api.github.com`) carried 100% of discovery this run across 9 broad
queries plus per-candidate metadata and LICENSE-file verification for the deep-review
shortlist — no rate-limit pressure (well under 200 of 8,350 requests/hour used).
`raw.githubusercontent.com` LICENSE-file reads were essential this run: three of the
five deep-reviewed/rejected candidates (Convoy, SQLite Sync, Notifuse) had a GitHub API
license field that was either `NOASSERTION` or otherwise unhelpful, and only the raw file
revealed the actual (non-OSI) license terms. `hn.algolia.com` returned zero hits on both
`self-hosted` and `API gateway` show_hn queries over 7–10 day windows — unusual (prior
runs at least surfaced low-signal posts); worth checking query construction next run
rather than concluding the source is exhausted. `WebSearch` again returned mostly
generic/stale listicle content on a Show HN roundup query, consistent with recent runs.
No sources were fully unreachable this run.
