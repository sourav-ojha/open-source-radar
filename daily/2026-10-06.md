# Open Source Radar — 2026-10-06
_Rotation slot 7 — experimental projects and hidden gems_

## Executive Summary
This run leaned into slot 7's mandate to hunt narrow, under-discussed projects rather than chase a theme. The standout is a project that affects how this radar itself runs: a proxy that claims to fix a Claude Code prompt-cache regression causing up to 20x cost spikes on resumed sessions. Alongside it, an embedded agent-memory engine that collapses vector/graph/relational storage into one SQLite file, a pre-1.0 embedded graph database with Node bindings that transparently documented and fixed a serious data-corruption bug, and an experimental Datalog-based local-first database from a credible local-first-systems pedigree. The broader search surfaced two clearly oversaturated hype waves (git-worktree managers for parallel AI coding agents, and LLM gateway/proxy products) and one repo with a strong fake-engagement signal.

## Today's Best Discoveries

### 1. CortexDB — 7.8/10
**Decision:** PROTOTYPE

**What it is** — A pure-Go embedded memory and knowledge-graph engine living in one SQLite file: vector search, relational memory, RDF/SPARQL, and Cypher graph queries in one process, no embedding model required.
**Why I should care** — Every "give my agent memory" approach wires together a vector DB + graph DB + document store, or dumps everything into a markdown file. This collapses all of it into one file, with a one-line Claude Code/Codex plugin install — directly usable in the same tool this radar runs on.
**What it could replace** — A vector-DB + graph-DB combo for lightweight agent-memory or internal-tool-memory needs.
**Ways I could use it** — Give a Claude Code session durable cross-session memory; embed as a Go library inside an internal tool needing semantic + graph + time-series memory; back a support-bot's "what do we know about this customer" lookup; share one memory store across multiple agent sessions via the gRPC mode.
**Agent opportunity** — Native Claude Code/Codex plugin, MCP server with 80+ tools, built-in self-test diagnostics.
**Integration effort** — Low: `go get`, or npm/pip/cargo client packages, or a one-line plugin install.
**Maturity** — Emerging. Created August 2025, very actively released (v2.121.1, same day as this review), 270 stars, 7 forks — effectively solo-maintained despite the release cadence.
**License** — MIT, no commercial-use restrictions.
**Alternatives** — Standing up Chroma/Qdrant + Neo4j separately; Sibyl-Memory, yantrikdb, NodeDB (similar "collapse the stack" bets with different storage engines and licenses).
**Why this one** — SQLite-file storage plus no-embedding-model-required plus first-class Claude Code/Codex plugin support is a combination the others don't all have at once.
**Recommendation** — Prototype it in a real Claude Code workflow before trusting it for anything production-critical; small community means little independent validation of recall quality yet.

### 2. claude-code-cache-fix — 7.2/10
**Decision:** PROTOTYPE (with explicit security caveats)

**What it is** — A local proxy sitting between Claude Code and Anthropic's API that rewrites `POST /v1/messages` requests to repair prompt-cache bugs: unstable request-prefix ordering, silent TTL downgrades, thinking-desync 400s, and image-retry storms — all of which turn cheap cache-read hits into expensive cache-creation spikes on long or resumed sessions.
**Why I should care** — This is directly about the tool running this radar. If the claimed cache-miss behavior is real, fixing it is a measurable cost reduction on a tool already in daily use — not a speculative future benefit.
**What it could replace** — Manually noticing and working around cache-prefix instability and TTL downgrades on long Claude Code sessions.
**Ways I could use it** — Run it locally in front of a Claude Code session and measure cache-read ratio before/after; use its diagnostics to confirm whether a given project's sessions actually hit the bug before deciding to keep it running.
**Agent opportunity** — None directly — it's infrastructure that makes an existing agent tool cheaper, not an agent tool itself.
**Integration effort** — Low to try (`npm install -g`, binds to localhost by default, idempotent if nothing needs fixing). Treat enabling anything beyond the default mode as a separate, higher-effort decision.
**Maturity** — Emerging but actively maintained. Created April 2026, latest release v4.3.0 (July 2026), 436 stars, 37 forks (including a GUI and VS Code extension built on top), 80 closed / 42 open issues.
**License** — MIT — confirmed from the raw LICENSE file and npm registry metadata. Note: GitHub's own license-detection API reports `NOASSERTION` for this repo, almost certainly because of a non-standard multi-author copyright line in the LICENSE header — the file content itself is standard MIT. Worth remembering that the API field isn't always right.
**Alternatives** — Doing nothing and eating the regression; following the underlying Claude Code bug reports directly; several much-smaller forks/wrappers (GUI, VS Code extension, a mitmproxy-based clone) with far less traction.
**Why this one** — It's the only entrant in this space with real traction, a documented security model, and a linked independent assessment.
**Recommendation** — Worth a one-week trial in default (non-TLS-terminating) mode to measure the actual cache-read-ratio effect. It intercepts and rewrites live API traffic for a tool used daily — read the Security Model section before enabling anything beyond the default local-proxy mode, and do not enable the `--remote-control` TLS-termination mode without a specific reason to need it.

### 3. SparrowDB — 6.3/10
**Decision:** WATCH

**What it is** — "The SQLite of graph databases" — an embedded, Cypher-native graph database in Rust with Python, Node.js, and Ruby bindings, no server process.
**Why I should care** — Reaching for Neo4j for a small embedded graph need (permission trees, recommendation edges, a dependency graph inside an internal tool) is usually overkill. A real embedded graph DB with a Node binding is a genuinely underserved niche.
**What it could replace** — Running a Neo4j instance (or paying for a managed one) for graph needs that are a feature inside an app, not the whole app; hand-rolled recursive-CTE graph traversal in Postgres/Mongo.
**Ways I could use it** — Embed inside a Node service for permission-graph or org-chart traversal; prototype a recommendation-graph feature before committing to a dedicated graph database; use from Python/Ruby tooling.
**Agent opportunity** — None documented specifically; usable as a general-purpose building block inside an agent's tool belt.
**Integration effort** — Low to try (`cargo add` or language bindings, no server to deploy) — but see maturity concerns before depending on it.
**Maturity** — Experimental, explicitly "pre-1.0, building in public." Created March 2026, v0.1.27 (August 2026), 79 stars, apparently single-maintainer. The README transparently documents that versions ≤0.1.26 had no lock file at all, and concurrent writers corrupted the catalog file beyond recovery in 4 of 5 test runs — fixed in 0.1.27 with a process-wide exclusive lock.
**License** — MIT, no commercial-use restrictions.
**Alternatives** — Neo4j (full server, overkill for embedded use), KuzuDB and other embedded graph databases, or modeling the graph in Postgres/Mongo directly.
**Why this one** — The SQLite-shaped embedding experience with real Cypher is a specific, compelling bet that none of the Postgres/Mongo workarounds give you — but it's the most immature of today's finds.
**Recommendation** — Watch for a few more point releases past the recent corruption-bug fix before trusting it with anything that matters; the transparency about the bug is a better signal about the project's engineering culture than the bug itself.

### 4. Dialog DB — 6.0/10
**Decision:** STUDY

**What it is** — An experimental embeddable database for local-first software, built around a Datalog-style "schema-on-read" query API rather than a fixed relational schema, targeting both WASM and native runtimes.
**Why I should care** — Local-first sync is a real architecture pattern worth understanding even without adopting this specific project. Dialog's Datalog-esque query model is a meaningfully different approach from the CRDT-document sync in Yjs/Automerge or the SQLite-replication approach in already-catalogued Evolu.
**What it could replace** — Nothing in production today — it's explicitly pre-production. The value is architectural reference.
**Ways I could use it** — Study the published design guide as a reference for schema-on-read query design in a sync context; spike a throwaway prototype to evaluate the Datalog query ergonomics in TypeScript/React.
**Agent opportunity** — None — this is a data-layer project, not an agent tool.
**Integration effort** — High right now — the README explicitly states the binary encoding and index construction are expected to break with no migration path promised.
**Maturity** — Experimental by the maintainers' own label. Created March 2025, actively pushed, but no conventional tagged releases and 73 open issues against 181 stars.
**License** — MPL-2.0 — weak, file-level copyleft. Proprietary code can be combined with it; only modifications to MPL-licensed files themselves must be shared back. Not a blocker for embedding, but re-check once the project stabilizes and any redistribution is planned.
**Alternatives** — Evolu (already catalogued, STUDY) for a more SQLite-shaped local-first sync platform; Yjs/Automerge for CRDT-document sync.
**Why this one** — The primary contributor (Gozala / Irakli Gozalishvili, currently at Tonk Labs per their GitHub profile) has a public track record in distributed/local-first systems — a useful credibility signal for a project with this little traction (181 stars, 1 watcher) otherwise.
**Recommendation** — Study the architecture; not ready for adoption, no migration guarantees on a format that's explicitly expected to change.

## Small but High-Leverage Utility
**rote** (github.com/zhh2001/rote, MIT, 364 stars) — "a cron that remembers what it did." Plain cron runs jobs and forgets them; when a backup silently stops firing at 3am there's no exit code, no timing, no output to look at. rote wraps scheduled jobs and records every run — exit code, duration, timeout status, captured stdout/stderr — with a live terminal dashboard showing which jobs are healthy and what the last failure actually printed. It's a single static binary with signed-checksum install scripts and Homebrew/deb/rpm/apk packages. Not catalogued as a full entry (the scope is narrow and the niche already has heavier options like Dagu), but it is a genuinely time-saving drop-in for anyone currently debugging silent cron failures by SSHing in and grepping logs.
