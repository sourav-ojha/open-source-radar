## Today's Best Discoveries

### 1. difit — 8.2/10
**Decision:** USE NOW

**What it is** — A CLI that spins up a local web server rendering git diffs in a GitHub-style "Files changed" UI, for single commits, branch comparisons, the working tree, or a live GitHub PR.
**Why I should care** — Removes the need to open a throwaway draft PR just to self-review a diff before pushing, and review comments can be copied out as AI-prompt-ready text.
**What it could replace** — Opening draft PRs purely for self-review; terminal `git diff` + pager workflows.
**Ways I could use it** — Pre-push self-review (`difit .`); reviewing a teammate's PR locally with imported review threads (`difit --pr <url>`); comparing a feature branch against `main` before opening a PR; piping diffs from any tool via stdin; letting a coding agent open the viewer via its official skill package.
**Agent opportunity** — Ships an official agent skill (`npx skills add yoshiko-pg/difit`) exposing `difit`/`difit-review` capabilities so a coding agent can surface a visual diff for human review instead of dumping diff text into chat.
**Integration effort** — Low: `npm install -g difit` or `npx difit`, zero config, no account.
**Maturity** — Emerging: 3,221 stars, created June 2025, actively released (v5.0.12), single maintainer.
**License** — MIT. No commercial restrictions.
**Alternatives** — `git diff`+delta, GitHub Desktop's local diff view, opening a draft PR, VS Code's diff view.
**Why this one** — Only one found combining a pixel-identical GitHub review UI, PR-thread import, and comment-to-AI-prompt export in a single zero-config CLI.
**Recommendation** — Install today; `npx difit` costs nothing to try.

### 2. whatbroke — 7.1/10
**Decision:** PROTOTYPE

**What it is** — A CLI that diffs an AI agent's *behavior* (tool calls, arguments, cost, latency, outputs) between two recorded JSONL traces, instead of diffing the text response.
**Why I should care** — Text-based evals can't see an agent silently skipping a side-effecting tool call while the reply still reads fine — whatbroke's own case studies document exactly this happening on a model downgrade, a same-size vendor swap, and a LiteLLM streaming bug that dropped every tool call while returning HTTP 200.
**What it could replace** — Manually re-testing tool-calling behavior by hand after every model/prompt/framework change; the false confidence of a passing text-quality eval.
**Ways I could use it** — CI gate (`--fail-on changed`) before merging a prompt/model change to a tool-calling agent; a "model swap checklist" step before switching to a cheaper model; debugging a proxy/gateway that may silently alter tool-call behavior; confirming a prompt edit has no tool-usage side effects.
**Agent opportunity** — Designed natively for CI: record → diff → exit-code gate, with `$GITHUB_STEP_SUMMARY`-ready markdown output; the JSONL trace format is deliberately simple to emit from any framework.
**Integration effort** — Low to adopt the CLI itself; Medium in practice because there's no ready-made trace adapter for popular agent frameworks yet — you write the instrumentation.
**Maturity** — Experimental: created July 2026, 21 stars, single maintainer, no track record yet, but documentation (README, 3 case studies, a "when to use what" comparison vs. promptfoo/LangSmith) is unusually thorough for its age.
**License** — MIT. No commercial restrictions.
**Alternatives** — promptfoo, LangSmith eval suites, manual transcript review — all score output quality rather than structured tool-call-level behavior, which is whatbroke's explicit differentiator.
**Why this one** — No other tool found doing behavioral diffing at the tool-call level with flaky-run-aware severity classification.
**Recommendation** — Worth trying instrumentation on the next model/prompt change to an agent project; too early to rely on exclusively.

### 3. Captain CLI (RWX) — 6.9/10
**Decision:** PROTOTYPE

**What it is** — An open-source Go CLI that detects and quarantines flaky tests, auto-retries failures, partitions test files for parallel CI, and generates markdown failure summaries.
**Why I should care** — Automates the two most common manual flaky-test workarounds (re-run, mentally ignore) plus hand-rolled CI sharding scripts, as a free CLI rather than a paid dashboard subscription.
**What it could replace** — Manual CI re-runs for known-flaky tests; hand-written test-partitioning/sharding scripts for parallel CI.
**Ways I could use it** — Wrap an existing CI test step for automatic retry + quarantine; partition a large suite across parallel jobs without a manually maintained shard file; pipe failure summaries into a PR comment or Slack alert.
**Agent opportunity** — The markdown failure-summary output is well suited to being consumed by a coding agent doing CI-failure triage.
**Integration effort** — Medium: wraps around existing test commands in CI, and it's unclear from the docs whether the flaky-test-history state is fully local or needs RWX backend communication — confirm before trusting it with sensitive test data.
**Maturity** — Mature as a product: company-backed (RWX), repo created 2023, actively released (v2.9.0), Discord community; modest star count (99) likely because the CLI's open-source release itself is newer than the repo.
**License** — MIT for the CLI; RWX Cloud (analytics, automatic rebalancing) is a separate proprietary paid tier — flagging the open-core split explicitly.
**Alternatives** — BuildPulse, Trunk Flaky Tests, Datadog Test Visibility — mostly paid; Captain's baseline feature set is free and open source.
**Why this one** — Only free, open-source CLI found doing all of retry + quarantine + partition + failure summaries in one tool.
**Recommendation** — Trial on a flaky CI suite to see how much value the open-source tier delivers before considering the paid Cloud.

### 4. DockFlare — 7.0/10
**Decision:** PROTOTYPE

**What it is** — Automates Cloudflare Tunnel (+ DNS + optional Zero Trust Access policy) provisioning directly from Docker Compose labels, with a web dashboard.
**Why I should care** — Collapses manual `cloudflared` config editing and Cloudflare dashboard DNS/Access setup into container labels — directly useful for exposing self-hosted admin tools or client demo environments securely without opening firewall ports.
**What it could replace** — Hand-written `cloudflared` configs per service; manually maintained DNS/Access rules in the Cloudflare dashboard; a VPN just to reach an internal dashboard.
**Ways I could use it** — Spin up a client demo environment behind an Access policy for the MSSP/PTaaS work without opening inbound ports; expose an internal admin dashboard to a small team instead of running a VPN; standardize "every self-hosted side project gets a public access-controlled URL" as a compose-file concern.
**Agent opportunity** — Not agent-facing, but a clean building block for an automated "spin up a demo environment" script or agent-driven deploy flow.
**Integration effort** — Low for anyone already on Docker Compose + Cloudflare; hard-couples the deployment model to Cloudflare specifically.
**Maturity** — Emerging but well-adopted: 2,472 stars, created April 2025, actively released (v3.1.6), only 1 open issue relative to its star count.
**License** — GPL-3.0 (GitHub's API misreports this as "NOASSERTION" — confirmed by reading `LICENSE.MD` directly). Fine to self-host; flagging loudly that embedding it in a distributed closed-source commercial product would trigger copyleft obligations.
**Alternatives** — Manual `cloudflared`, Traefik + Let's Encrypt (needs an open inbound port), Tailscale Funnel.
**Why this one** — The only one found that's fully Docker-label-driven with zero manual `cloudflared` config and a management dashboard.
**Recommendation** — Try it for the next internal tool or client demo that needs secure external access without VPN setup.

## Meaningful Updates

**LibreDB Studio** — human-facing self-hosted DB IDE → now also agent-facing. v0.17.0 added a native MCP server at `/api/mcp` (`list_connections`, `inspect_schema`, `run_read_query`), with per-connection opt-in, database-transaction-level read-only enforcement (not a SQL-text filter), role-scoped visibility, and 30-day bearer tokens. This directly extends the tool's USE NOW case from "team DB browser" to "agent-safe database access layer." Does this change the recommendation: no, still USE NOW. Catalog updated: Yes.

**Destructive Command Guard (dcg)** — v0.14.4 → v0.15.2, and this one matters: v0.15.1 had a fail-open bug where, under load (~16 concurrent hook processes), a hook that exits silently is treated as "allow" by every agent — 3-9% of destructive commands requiring the embedded-script reader (e.g. `watch 'git reset' --hard`) could bypass the guard. v0.15.2 fixes it. Anyone running dcg should upgrade immediately. Does this change the recommendation: no, still USE NOW, but flagging loudly given this is safety-critical tooling. Catalog updated: Yes.
