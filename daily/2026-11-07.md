# Open Source Radar — 2026-11-07
_Rotation slot 4 — data, search, documents, RAG_

## Executive Summary
Today's strongest finds all pivot an existing engineering discipline toward the AWS/agent context
already in scope: an AWS Labs framework that treats "which graph-RAG method" as a runtime choice
instead of an architecture decision, a dbt-alternative that adds compile-time type checking plus
an explicit approval gate for AI-agent-proposed pipeline changes, and a mature vectorless RAG
approach (reasoning over document structure instead of embedding similarity) that's worth
understanding even without adopting it wholesale. Three previously-catalogued tools also shipped
real security fixes this week, a reminder that "meaningful update" in this space increasingly
means "read the security advisories," not just "check the changelog."

## Today's Best Discoveries

### 1. Unified Knowledge Graph RAG on AWS — 8.4/10
**Decision:** PROTOTYPE

**What it is** — An AWS Labs framework running four published graph-RAG methods (Microsoft
GraphRAG, LightRAG, HippoRAG 2, opt-in RAPTOR) on one shared index, selectable per query rather
than per deployment. Hybrid retrieval fuses BM25, vector search, and Amazon Neptune graph
traversal, reranked with a Bedrock rerank model. Runs fully local (SQLite + Ollama, no AWS
account, five-minute quickstart) or AWS-native (Neptune + OpenSearch + Bedrock).
**Why I should care** — Graph-RAG is normally a commit-to-one-paper decision; this collapses four
methods behind one ingestion pipeline with a real evaluation CLI (LLM-free metrics, LLM judges,
paired confidence intervals, per-query cost) so the choice becomes measurable instead of assumed.
Built by AWS Labs directly against the Bedrock/Neptune/OpenSearch stack already in scope.
**What it could replace** — Hand-rolling GraphRAG or LightRAG from their reference repos, plus a
custom evaluation harness to decide which one is actually worth running in production.
**Ways I could use it** — Compare retrieval methods on a real corpus before committing engineering
time; a Bedrock-native cited-source Q&A tool for client-facing compliance/research documents;
prototype locally with Ollama before paying for the AWS-native deployment; merge an existing
taxonomy into an LLM-extracted graph via the seed-graph path.
**Agent opportunity** — CLI (`run-ingestion`, `run-rag`, `run-eval`) narrow enough to wrap as an
agent tool or MCP server directly; the eval CLI doubles as a CI regression check for retrieval
quality.
**Integration effort** — Medium: low for the local/evaluation path, higher once Neptune/
OpenSearch/Bedrock are involved.
**Maturity** — Emerging (created 2026-07-20, no tagged release yet, actively pushed today).
**License** — Apache-2.0, no restrictions.
**Alternatives** — Hand-rolled GraphRAG/LightRAG; Amazon Bedrock Knowledge Bases GraphRAG (the
managed path, compared directly in the project's own docs); the already-catalogued CocoIndex/
Antfly/PageIndex, none of which combine multiple graph-RAG methods behind one eval harness.
**Why this one** — The "one index, many retrieval algorithms, chosen per query" design and the
built-in evaluation CLI are the differentiators; most graph-RAG tooling hard-wires one method.
**Recommendation** — Run the local quickstart against a real document set before deciding whether
any method, or the AWS-native deployment, clears the bar for a client-facing feature.

### 2. Rocky — 7.9/10
**Decision:** PROTOTYPE

**What it is** — A dbt-alternative SQL transformation engine that type-checks an entire pipeline
before it runs: compile-time type/reference/contract errors, column-level lineage diffs showing
exactly what a change breaks downstream, named branches with replay, and a plan/apply workflow so
nothing executes without an explicit review step. Single static Rust binary with a browser UI, a
VS Code extension, a Python SDK, and a Dagster integration.
**Why I should care** — dbt pipelines typically fail at runtime against the warehouse; Rocky's
compiler catches broken references and type mismatches offline. The `[policy]` rule set —
"an AI-written plan needs an approval marker" before `apply` — is a directly reusable pattern for
letting a coding agent propose SQL pipeline changes without letting it auto-apply them.
**What it could replace** — dbt plus a bolted-on CI review process for pipeline changes.
**Ways I could use it** — Import an existing dbt project (`rocky import-dbt`) and get compile-time
checking for free; use `rocky lineage-diff` as a PR check; let an agent propose pipeline changes
gated by the approval-marker policy; develop entirely on the DuckDB playground first.
**Agent opportunity** — The AI-agent approval-marker policy is a ready-made guardrail pattern for
any agent-proposed database-affecting change, independent of whether Rocky itself is adopted.
**Integration effort** — Medium: easy to run the binary/playground; Postgres and most non-
Databricks warehouses are beta-tier.
**Maturity** — Emerging but unusually active: created 2026-04-13, already on engine release
v1.89.0 (89 releases in under 7 months), GitHub Sponsors funding.
**License** — Apache-2.0, no restrictions.
**Alternatives** — dbt (the explicit baseline, with no-lock-in import/export); the already-
catalogued pgschema (declarative Postgres *schema* migration, a different layer); Dagster/Airflow
for orchestration (Rocky integrates rather than competes).
**Why this one** — Compile-time contracts plus an agent-approval policy that most SQL
transformation tools don't have, backed by a genuinely fast release cadence.
**Recommendation** — Try the DuckDB playground, then a non-critical Postgres pipeline; hold off on
anything warehouse-critical given the beta-tier Postgres support.

### 3. FormKiQ Core — 7.8/10
**Decision:** PROTOTYPE

**What it is** — An open-source, API-first document management backend that runs entirely inside
your own AWS account (or locally via Docker), built on AWS-native managed services: S3 storage,
API Gateway REST API, Lambda/SQS/SNS/EventBridge event hooks, built-in OCR search, versioning,
retention policies, audit trails, and multi-tenant isolation.
**Why I should care** — This is a document-storage building block already shaped around the exact
AWS primitives in scope (S3, Lambda, SQS, EventBridge, IAM), with six years of continuous
development on a narrow, well-understood problem rather than a generic self-hosted app that
happens to support S3.
**What it could replace** — Hand-built S3 + Lambda glue for versioned storage, OCR search,
per-tenant isolation with signed links, and event-driven enrichment hooks.
**Ways I could use it** — Per-tenant document storage for a SaaS product with AWS-residency
requirements; an HR/legal/finance records vault with audit trails; an S3/email/API ingestion
pipeline with OCR and metadata tagging; customer/partner portals with signed access links —
directly relevant to the MSSP admin-portal context.
**Agent opportunity** — REST API plus Java/Python SDKs and an OpenAPI spec make this
straightforward to wrap as an agent tool; event hooks are a natural trigger for an agent-driven
classification step on upload.
**Integration effort** — Medium: AWS SAM CLI/CloudFormation is the intended deployment path;
Docker lowers the bar for local evaluation.
**Maturity** — Mature (active since 2020, latest release v1.19.1, 2026-10-06).
**License** — MIT, verified directly against the LICENSE file (the GitHub API misreported this as
NOASSERTION — a known API-metadata gap worth checking for on other repos too).
**Alternatives** — Hand-rolled S3+Lambda; the self-hosted-document-management wave (Paperless-ngx
and today's held-out Lemmary), aimed at personal archiving rather than multi-tenant AWS SaaS;
Nutrient/PSPDFKit's hosted Document Engine (proprietary backend, not comparable).
**Why this one** — Purpose-built for the AWS account model already in use, not a generic
self-hosted app retrofitted onto S3.
**Recommendation** — Stand it up against a real per-tenant document-storage requirement before
building the equivalent Lambda plumbing by hand.

### 4. PageIndex — 7.6/10
**Decision:** STUDY

**What it is** — A vectorless, reasoning-based RAG approach: builds a hierarchical tree from a
document's structure (like a table of contents) and has an LLM reason over node titles/summaries
to select relevant branches, instead of retrieving by embedding similarity. Local SDK (bring your
own LLM key) or PageIndex Cloud; a vision-based variant works over page images without OCR.
**Why I should care** — Vector similarity systematically misses what's relevant-but-dissimilar on
exactly the documents that matter most professionally — long financial reports, contracts,
regulatory filings. This is a genuinely different retrieval architecture worth understanding, not
another vector-DB wrapper.
**What it could replace** — The chunking-strategy and embedding-pipeline design work for
long-document RAG specifically, where chunked vector retrieval is underperforming.
**Ways I could use it** — A RAG layer for long structured documents where section structure (not
keyword similarity) determines relevance; the hosted Page Search API for cutting token cost on
document QA; the vision variant for scanned/image-only documents.
**Agent opportunity** — Local SDK usable directly as an agent tool; also ships as an MCP server
and a hosted API, with a ready-made OpenAI Agents SDK example.
**Integration effort** — Low for a document-QA proof of concept; tree-building adds real LLM cost
and 30–120s latency per the project's own documentation.
**Maturity** — Mature — 1.5 years old, 40k+ stars, 3,456 forks, actively released (v0.5.3,
2026-11-05), widely covered in RAG blogs since mid-2026. Not a hidden gem; the value here is the
architecture.
**License** — MIT, verified against the repository LICENSE file.
**Alternatives** — Standard vector-DB RAG (pgvector, Qdrant, Milvus, the already-catalogued
Antfly/Infino); GraphRAG/LightRAG/HippoRAG (today's Unified KG RAG on AWS) — a different
non-vector approach, graph- rather than tree-structured.
**Why this one** — The only catalogued project arguing, with real production usage behind it,
that vector similarity is the wrong primitive for a specific and common class of long document.
**Recommendation** — Study the architecture and test it specifically against a long-document use
case the next time chunked RAG underperforms; not a wholesale vector-DB replacement.

### 5. DB Agent — 7.3/10
**Decision:** PROTOTYPE

**What it is** — A minimal, production-oriented text-to-SQL agent: natural-language questions
become SELECT-only SQL, validated against a safety layer, executed, and returned with every
intermediate step visible. Node.js/React app runnable locally in one command, or deployable to
Databricks Apps. Includes an MCP gateway so Claude Desktop/VS Code/Claude Code share one governed
database connection with per-caller keys, budgets, and an audit log.
**Why I should care** — Built in the same stack (Node.js/React) already in use, rather than the
Python-first tooling that dominates this niche. The "ontology" feature — a knowledge file of
descriptions/synonyms/example queries, auto-drafted from the schema, with an accuracy test
scoring with/without it — is a concrete, measurable accuracy lever, not just prompt-tuning.
**What it could replace** — A hand-built safe natural-language-to-SQL layer, and the practice of
handing agents raw database credentials instead of a governed, budgeted connection.
**Ways I could use it** — A plain-English query layer over an internal Postgres/MySQL database
with a visible SQL audit trail; governed MCP access for Claude Code/Claude Desktop instead of raw
DB credentials; a reference implementation for an auditable text-to-SQL feature in an existing
Node/React admin panel.
**Agent opportunity** — The MCP gateway is the standout feature: one governed, budgeted database
connection shared across multiple coding-agent tools — directly relevant to the MSSP/PTaaS
context as a governed-agent-access pattern.
**Integration effort** — Low: Node.js/React stack match, Docker Compose for local evaluation.
**Maturity** — Emerging: no tagged release, but presented at the AAAI-25 Workshop on Open-Source
AI for Mainstream Use and an AWS User Group Toronto workshop (Nov 2026).
**License** — Apache-2.0, no restrictions.
**Alternatives** — WrenAI, schemagate (already catalogued, both Python-first); Vanna (the
mainstream baseline); a hand-rolled "LLM writes raw SQL" agent — what the safety layer and MCP
gateway specifically replace.
**Why this one** — Node/React stack match plus the cost-visibility ("two bills, both visible": LLM
tokens vs. warehouse compute) and MCP-gateway features together.
**Recommendation** — Try directly against an internal Postgres database given the stack match.

## Meaningful Updates

**schemagate** — v1.14.0 → v1.16.0; previous state: LangChain/LlamaIndex integrations plus a
deep_answer MCP tool → current state: three real security advisories fixed in rapid succession
(a hidden-query-in-string injection on PostgreSQL, a restricted-table leak via foreign-key
expansion, and unauthorized web-page control of a local Studio session), confirmed #1 on the live
BIRD Mini-Dev leaderboard across all three dialects, and a new Pydantic AI capability
(`SchemagateCapability`/`select_schema` tool). Why it matters: this is an access-control tool, so
real security fixes are the most relevant kind of update it can ship. Does this change the
recommendation: no, still PROTOTYPE — but re-confirm the current version is in use on anything
already running schemagate. Catalog updated: Yes.

**KiviDB** — v1.1.0 → v1.2.0; previous state: AGPL-3.0 multi-threaded Redis alternative, 6 days
old → current state: a security release (v1.1.3, three externally-reported vulnerabilities fixed)
landed in between, and v1.2.0 reworks durability so an append-only-file write is acknowledged
only once actually durable, not before. Why it matters: a real correctness fix for a project
explicitly positioning itself as "a better Redis." Stars grew 396 → 968 in just over two weeks.
Does this change the recommendation: no, still PROTOTYPE. Catalog updated: Yes.

**DatI** — v0.6.3 → v0.10.1 (14 releases over six weeks); previous state: governed DB-to-MCP
gateway with per-user credentials → current state: schema-scoped data access (v0.9.0) — table
access, metadata, and MCP exposure can now be managed per schema instead of per database
connection — plus classified JDBC connection-failure diagnostics (v0.10.0). Why it matters: a
materially finer-grained permission boundary, directly relevant to this project's core pitch. Does

## Small but High-Leverage Utility
**sghtmltopdf** — An HTML-to-PDF renderer in Rust aimed at invoices/receipts/reports, with no
Chromium/WebKit/Gecko dependency. Routine SaaS billing flows usually pay the Puppeteer/
headless-Chrome tax just to turn an HTML template into a PDF; this removes the browser process
entirely while staying close enough to wkhtmltopdf's CLI flags to be a near-drop-in replacement
for that abandoned tool. No native Node binding yet, but the CLI and HTTP server modes integrate
cleanly with a Node/React app via subprocess or REST call.

## Worth Watching
- **usemoss/moss** — Sub-10ms, vector-free semantic search runtime with real published benchmarks
  and genuinely broad SDK/framework coverage (Python, TS, Elixir, C, LangChain, DSPy, CrewAI).

- **geolens-io/geolens** — Self-hosted geospatial data catalog with semantic search (pgvector),
  OGC/STAC APIs, and a map builder on FastAPI/PostGIS/React/MapLibre. Solid engineering (OpenSSF
  Scorecard badge, Apache-2.0) but a narrow fit without an active GIS need; would need a concrete
  use case to justify a full entry over its niche.
- **buldezir/lemmary** — A paperless-ngx-API-compatible personal document library (Go + PocketBase
  + React) with real scanning (eSCL/AirScan), IMAP ingestion, and encryption-at-rest. Thin traction

  independent growth to differentiate from just running paperless-ngx.
