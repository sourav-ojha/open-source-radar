# Open Source Radar — 2026-10-03
_Rotation slot 4 — data, search, documents, RAG_

## Executive Summary
Today's pass surfaced a cluster of genuinely useful database/data-infrastructure tools rather than another RAG-ingestion wave: a self-hosted multi-database workspace with a built-in MCP server (WhoDB), a governed text-to-SQL engine distributed directly as an agent skill (WrenAI), and a pair of narrow, fast, npm-installable Rust document-extraction libraries (unpdf/undoc) that skip the usual Python-sidecar requirement entirely. A recurring theme: several tools this week ship their AI/agent integration as the primary interface rather than a bolted-on feature — WrenAI's main distribution path is now a Claude Code/Cursor/Codex skill, and WhoDB's MCP server is a first-class CLI subcommand, not an afterthought.

## Today's Best Discoveries

### 1. WhoDB — 8.6/10
**Decision:** USE NOW

**What it is** — A self-hosted, lightweight workspace (Apache-2.0, Go backend, React/TS frontend) covering Postgres, MySQL/MariaDB/TiDB, SQLite/DuckDB, MongoDB/FerretDB, Redis/Valkey/Dragonfly, Elasticsearch/OpenSearch, ClickHouse, CockroachDB, YugabyteDB, QuestDB, and Memcached — with a spreadsheet-style data grid, an interactive schema-relationship graph, a query scratchpad, import/export/mock-data tooling, optional bring-your-own-key AI chat, and a CLI plus official MCP server.
**Why I should care** — It's the one tool that actually matches a MERN+AWS stack's real database mix (Postgres, MongoDB, Redis) instead of running a different GUI client per engine.
**What it could replace** — TablePlus/Studio3T/Compass run side by side, and a hand-built MCP wrapper if agent DB access was the goal.
**Ways I could use it** — Daily Postgres/MongoDB inspection and editing; giving a coding agent read/write DB access via `whodb mcp serve`; onboarding a teammate onto an unfamiliar schema via the relationship graph; ad hoc English-language queries against a client's database during MSSP triage with a local Ollama model so no data leaves the machine; generating mock data while prototyping.
**Agent opportunity** — Ships `whodb mcp serve` out of the box — no custom MCP wrapper needed for agent DB access.
**Integration effort** — Low — one `docker run` command, or desktop app / CLI install.
**Maturity** — Mature (5,031 stars, created June 2024, active, latest release 0.134.0).
**License** — Apache-2.0 for WhoDB Community (this repo); a paid "WhoDB Platform" tier adds SSO/audit logs/pipelines but isn't required for this feature set.
**Alternatives** — DBeaver/TablePlus/Studio3T (no MCP server, no single self-hosted deployment); Chat2DB (28,299★, more AI polish, heavier Java footprint, no documented MCP).
**Why this one** — Breadth of database support plus a zero-setup MCP server is a combination none of the mainstream GUI clients offer.
**Recommendation** — Install today; low risk, immediate daily use.

### 2. unpdf / undoc — 8.1/10
**Decision:** PROTOTYPE

**What it is** — Sibling Rust libraries (MIT, `iyulab` org) for document-to-Markdown/JSON extraction: unpdf for PDF (CJK/RTL support, multi-column layout detection, streaming parsing, image dedup), undoc for DOCX/XLSX/PPTX — both published as native crates plus Python, .NET, and npm/WASM bindings.
**Why I should care** — Runs as a native npm dependency, including a WASM build that works fully client-side in a browser — no separate Python microservice needed to turn a document into clean Markdown for an LLM.
**What it could replace** — A hand-rolled PDF/Office parsing pipeline, or a Python extraction sidecar in an otherwise all-JS/TS stack.
**Ways I could use it** — Extract PDF/DOCX/XLSX/PPTX to Markdown directly inside a Node backend for a RAG pipeline; run the WASM build in-browser for instant, server-free document preview; handle CJK/RTL-heavy documents that many extractors mangle; bulk-convert a document archive using the streaming API to bound memory.
**Agent opportunity** — npm-installable and runs fully in-process — trivial to wrap as an MCP tool without a sidecar service.
**Integration effort** — Low — `npm install @iyulab/unpdf`.
**Maturity** — Emerging — created Dec 2025/Jan 2026, modest stars (36/58) but actively released daily across 4 package registries.
**License** — MIT, both repos.
**Alternatives** — Xberg/Kreuzberg (catalogued, broader — 107 formats, OCR, transcription — but heavier); pdf_oxide/office_oxide (similar narrow-and-fast positioning, more language bindings).
**Why this one** — Direct npm/WASM embedding with no Python dependency is the differentiator for an all-JS/TS stack specifically.
**Recommendation** — Prototype against real document samples before depending on it; too new to fully trust yet, but the registry spread and release cadence are good signs.

### 3. WrenAI (Wren Engine) — 7.8/10
**Decision:** PROTOTYPE

**What it is** — Open-source governed text-to-SQL / "GenBI" engine (Canner): a semantic layer (plain YAML/Markdown you own) sits in front of 22+ data sources and is exposed to Claude Code, Cursor, Cline, Codex, and 50+ other agents via an MCP server, CLI, and installable skill.
**Why I should care** — Extends agent leverage into the BI/analytics surface — an agent gets a governed, reviewable query path instead of raw database credentials.
**What it could replace** — A hand-built NL-to-SQL translation layer, or letting an agent write raw SQL directly against production with no guardrails.
**Ways I could use it** — Let a coding agent answer business questions against a Postgres replica without writing raw SQL; build an ask-your-database-in-English feature for an admin-portal SaaS; maintain one shared semantic layer across agents and dashboards; prototype a client-facing analytics assistant for the MSSP portal.
**Agent opportunity** — Its primary distribution path is now an agent skill/MCP server — install directly into Claude Code and query data sources conversationally.
**Integration effort** — Medium — needs a semantic-layer definition and an LLM API key or local model.
**Maturity** — Mature by scale (17,799 stars, since March 2024) but the skill/MCP-first architecture itself is a recent pivot away from the project's original Docker-based app.
**License** — Core engine (semantic layer, text-to-SQL, MCP server, CLI, connectors) is Apache-2.0; Wren AI Cloud / Enterprise Plus are separate paid tiers, not required for self-hosted use.
**Alternatives** — getnao/nao (smaller, less traction); holoviz/lumen (Python-native, smaller community); raw LLM + DB credentials (faster, no governance).
**Why this one** — The semantic-layer-as-agent-skill packaging is more concrete than anything else found today in this space.
**Recommendation** — Worth testing against a staging data source; the recent distribution-model pivot means validating before deeper reliance.

### 4. go-pq-cdc — 7.5/10
**Decision:** PROTOTYPE

**What it is** — Lightweight Go library/binary (MIT, Trendyol) for Change Data Capture on PostgreSQL via logical replication, streaming to Kafka/Elasticsearch/a custom sink, with a published benchmark against Debezium and a point-in-time snapshot feature.
**Why I should care** — A Postgres-only CDC path without a JVM/Kafka Connect deployment just to stream changes downstream.
**What it could replace** — A full Debezium + Kafka Connect + JVM stack, or a hand-rolled polling/dual-write sync job.
**Ways I could use it** — Sync a Postgres table to Elasticsearch/OpenSearch for search; feed row-level changes into a webhook/notification pipeline; point-in-time snapshot plus ongoing CDC to backfill a new replica or cache with no downtime.
**Agent opportunity** — Could back an MCP tool that notifies an agent of relevant DB changes as they happen rather than polling.
**Integration effort** — Medium — requires enabling Postgres logical replication and wiring a sink.
**Maturity** — Mature in production use at Trendyol (211 stars, active, latest release v1.11.14).
**License** — MIT.
**Alternatives** — Debezium (mainstream, far heavier JVM/Kafka Connect infra); Supabase Realtime (simpler but Supabase-specific); a hand-rolled pgoutput consumer (the DIY path this already wraps).
**Why this one** — Lighter-weight than the mainstream Debezium path for anyone already running Postgres without a Kafka Connect cluster.
**Recommendation** — Prototype against a real sync need (e.g. search-index freshness) before committing, given the smaller community than Debezium.

### 5. Data Contract CLI — 7.6/10
**Decision:** PROTOTYPE

**What it is** — Mature (since 2023) open-source CLI/library (MIT) for authoring, linting, and testing Data Contracts against the Open Data Contract Standard (ODCS) — connects to a real source (Postgres, Snowflake, BigQuery, and 15+ others), runs schema/quality checks against live data, diffs contract versions for breaking changes, and exports to SQL DDL/HTML/JSON Schema.
**Why I should care** — Turns "does this data still match what we promised" into a one-command CI check instead of a schema doc that silently drifts from reality.
**What it could replace** — Hand-written, ad hoc schema validation scattered across a codebase.
**Ways I could use it** — Enforce a schema/quality contract on a client-facing API or webhook payload, directly relevant to MSSP admin-portal client integrations; run `datacontract test` in CI against staging Postgres; generate SQL DDL or an HTML data dictionary from one YAML source; gate merges with `datacontract breaking`.
**Agent opportunity** — An agent could call `datacontract test` to self-verify a schema migration matches the documented contract before declaring a task done.
**Integration effort** — Medium — the ODCS YAML format has a learning curve.
**Maturity** — Mature (1,077 stars, since 2023, PyPI version 1.2.2).
**License** — MIT.
**Alternatives** — sodadata/soda-core (own DSL, not the open standard); Great Expectations/dbt contracts (heavier, dbt-ecosystem-specific); hand-written JSON Schema (the status quo this replaces).
**Why this one** — Standard-based (ODCS) rather than a bespoke format, and source-agnostic rather than tied to one warehouse.
**Recommendation** — Trial on one real client integration's schema before adopting broadly.

## Small but High-Leverage Utility
**SQLLineage** (reata/sqllineage, MIT, 1,677 stars, mature since 2019) — a Python library/CLI that statically parses SQL text, no live database connection required, to build table- and column-level lineage graphs. The real time-saver is answering "what breaks if I rename this column" in seconds instead of grepping a repo of migrations and reporting views by hand, and it's genuinely zero-infrastructure: no warehouse credentials, no server, just SQL text in and a dependency graph out.

## Worth Watching
- **Rocky** (rocky-data/rocky) — Apache-2.0 SQL transformation engine with compile-time type/contract checking, column-level lineage diffs for PR comments, and a notable AI-agent governance model (plans never self-apply; a policy file gates what an AI-authored change may do before it reaches the warehouse). Architecturally one of the more concrete "agent safety guardrail" patterns seen in this radar, but currently only writes to Databricks/Snowflake/BigQuery/Trino/DuckDB — no Postgres or MongoDB adapter — so it isn't directly usable against this stack yet. Would need a Postgres write adapter (the Adapter SDK is documented) to become a real candidate.
- **Sourcemeta One** — C++ self-hosted, Git-native JSON Schema registry with governance features (searchable schema catalog, "single source of truth" workflow). Held back by its license: Business Source License 1.1 for the Community edition, with a separate proprietary Enterprise edition — worth tracking how the BSL terms (conversion date, if any) are documented before deeper evaluation.
- **WrenAI's architecture pivot itself** — the shift from a Docker-based GenBI web app to an agent-skill/MCP-first distribution model (see entry #3 above) is worth watching as a pattern: several tools this quarter are choosing "install as a coding-agent skill" as their primary distribution channel rather than a standalone web app.
