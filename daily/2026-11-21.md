# Open Source Radar — 2026-11-21
_Rotation slot 4 — data, search, documents, RAG_

## Executive Summary
Today's slot surfaced a genuinely crowded field — GitHub's `topic:rag`,
`topic:knowledge-graph`, and `topic:vector-database` searches are dominated by
household names (Milvus, Qdrant, LlamaIndex, Meilisearch, Airbyte, Airflow) and by a
second wave of massively star-inflated "turn your codebase into a knowledge graph for
AI agents" repos that overlap the already-catalogued Graphify with no clear
differentiation. Past that noise, four smaller, more defensible picks stood out: a
dedicated memory/reflection layer built specifically for Claude Code, a
Tree-sitter-based multi-language code knowledge graph with real CI/quality tooling
behind it, a sub-millisecond hybrid search engine with independently verified Hacker
News traction, and a TypeScript-native embedded knowledge-graph library that avoids
standing up a separate graph database. A paperless-ngx dedup/metadata companion was
today's utility pick.

## Today's Best Discoveries

### 1. claude-self-reflect — 8.4/10
**Decision:** USE NOW

**What it is** — A persistent memory layer for Claude Code: one embedded Rust binary
(~138MB, bundled SQLite, no external database, containers, Python, or API keys) that
stores session history and exposes it back to Claude via MCP tools — a start-of-session
recap, "receipts" for completed work, periodic re-checks of old conclusions against
git history ("dreams"), and compacted evidence carried across context resets.
**Why I should care** — Directly targets the actual failure mode in long unattended or
multi-day Claude Code sessions — including this radar's own daily run — where useful
context is lost to compaction or a new session start, forcing Claude to re-derive state
it already worked out.
**What it could replace** — Manually re-reading scrollback or re-explaining prior
decisions at the start of a new session.
**Ways I could use it** — Resume a multi-day Claude Code project with a one-paragraph
recap instead of scrollback; let Claude periodically re-check old conclusions against
git history and surface contradictions; carry "receipts" across a context compaction;
audit a past session's decisions without reconstructing them from memory.
**Agent opportunity** — Purpose-built MCP tool surface for Claude Code specifically; the
"dreams" re-verification mechanic is a pattern worth copying for any long-running agent
with persisted state.
**Integration effort** — Low: npm install, no server or API key to configure.
**Maturity** — Emerging: created 2025-07-25 (~16 months), 231 stars, 29 forks, 3
subscribers, 13 open issues. Actively released — v10.1.0 published the same day as this
review.
**License** — MIT, no restrictions.
**Alternatives** — Planning with Files (already catalogued, file-based plan/task
persistence without built-in reflection/verification); generic vector-DB memory layers
(mem0, Zep) — heavier, not Claude-Code-specific, require a server/API key.
**Why this one** — Built specifically for Claude Code's session lifecycle rather than a
generic memory layer retrofitted onto agents.
**Recommendation** — Install it and run one real multi-day Claude Code session through
it before depending on it for anything that matters.

### 2. Code-Graph-RAG — 8.1/10
**Decision:** PROTOTYPE

**What it is** — Parses a multi-language codebase with Tree-sitter (plus an ast-grep
fallback tier) into a code knowledge graph, stored in an embedded SQLite file by
default — no database server required — with Memgraph/Neo4j and Qdrant available as
opt-in backends for scale. Published to PyPI as `cgr`.
**Why I should care** — A zero-dependency, embeddable way to get structural/RAG-style
queries over a multi-language monorepo (Python, TS, JS, Go, Rust, Java, C/C++, C#, PHP
and more) without running a separate graph database, backed by real engineering quality
signals (Codecov, SonarCloud, OpenSSF Scorecard/Best Practices) rather than just a
marketing README.
**What it could replace** — Many ad hoc grep/file-read round trips an agent would
otherwise need to understand codebase structure; hand-rolled recursive SQL for
relationship queries.
**Ways I could use it** — Ask structural questions about an unfamiliar repo without
many manual file reads; query/edit the graph directly inside an agent session; scale
from zero-server embedded SQLite up to Memgraph+Qdrant for a large monorepo without
changing the query interface.
**Agent opportunity** — A coding-agent-facing structural-query layer with explicit
data-flow edges, droppable into a CI job or agent sandbox with no database to
provision.
**Integration effort** — Low: `pipx`/`uv tool install` from PyPI, embedded SQLite by
default. Native extension needs CPython 3.12+ on specific platforms.
**Maturity** — Emerging but well-engineered: created 2025-06-16 (~17 months), 5,393
stars, 726 forks, 35 subscribers, 304 open issues, Trendshift-featured. Latest release
v0.7.1 (2026-11-17).
**License** — MIT. A separate paid "Enterprise Support & Services" offering exists but
does not gate open-source functionality.
**Alternatives** — Graphify (already catalogued, PROTOTYPE 8.5) — broader input scope
(docs/PDFs/screenshots via Claude vision) and ships as a Claude Code skill;
Code-Graph-RAG is code-only but has a more conventional embeddable-library/CLI shape and
data-flow edges. ripwire (already catalogued) — change-impact focused, not general RAG.
**Why this one** — A differently-shaped entrant in the same niche as Graphify: library/
CLI rather than Claude-Code-skill-only, with a published language matrix and
conventional CI/quality tooling.
**Recommendation** — Try it against one real multi-language monorepo and compare the
structural-query experience directly against Graphify before picking one.

### 3. SeekStorm — 7.9/10
**Decision:** PROTOTYPE

**What it is** — Sub-millisecond lexical, vector, and hybrid search engine in Rust.
Embeddable as an in-process library, runnable as a multi-tenant server, and exposable
to agents via MCP.
**Why I should care** — A lighter-weight self-hosted search building block than
Elasticsearch/OpenSearch for product work that needs hybrid search but not distributed
cluster scale.
**What it could replace** — Standing up Elasticsearch/OpenSearch for a workload that
doesn't need that much infrastructure; a bespoke BM25+vector fusion layer.
**Ways I could use it** — Self-hosted hybrid search behind a product feature; embed
search as an in-process library in a Rust service; give an agent fast hybrid search via
MCP; multi-tenant search for a SaaS product with per-customer indices.
**Agent opportunity** — Native MCP support for giving coding/research agents hybrid
search over a corpus.
**Integration effort** — Low: Rust crate for embedding, or a packaged Docker server.
Non-Rust consumers use the REST API or MCP server.
**Maturity** — Emerging with real independent validation: created 2024-02-27 (~21
months), 1,938 stars, 75 forks, 9 subscribers, 13 open issues, 245-point Hacker News
thread, active Discord. Latest release v5.1.0 (2026-11-15).
**License** — Apache-2.0, no restrictions.
**Alternatives** — Meilisearch/Typesense (more mainstream, heavier runtimes);
Elasticsearch/OpenSearch (far more mature, far more operational overhead).
**Why this one** — Independently vetted via Hacker News and an active Discord rather
than raw star count alone — a real, if small, community rather than a drive-by repo.
**Recommendation** — Try the REST/MCP server against one real search use case before
committing to the Rust embedding path.

### 4. TypeGraph — 7.7/10
**Decision:** PROTOTYPE

**What it is** — A TypeScript-first embedded knowledge-graph library on top of an
existing SQLite or PostgreSQL database. Nodes/edges defined with Zod schemas, queried
via a fluent type-safe API, with hybrid vector+fulltext search, runtime schema
evolution from agent-proposed JSON, and bitemporal (valid-time + recorded-time) reads.
**Why I should care** — The only entrant found today that brings graph semantics
(ontology relations, bitemporal history, typed traversal) natively into a
TypeScript/SQL stack rather than requiring a separate graph database — a direct fit for
a MERN/Postgres profile.
**What it could replace** — Hand-rolled adjacency tables and recursive SQL for
relationship-heavy domain models; a dedicated graph database service for a feature that
doesn't need one.
**Ways I could use it** — Model a knowledge graph or RAG context store inside an
existing Node/Postgres app; build auditable agent memory with bitemporal decision
replay; model identity/permissions graphs with type-checked traversal; let an agent
evolve the schema at runtime from proposed JSON.
**Agent opportunity** — Runtime schema evolution from agent-proposed JSON is explicitly
designed for agent-driven data modeling, not human migrations.
**Integration effort** — Low: npm package, embeds directly into an existing SQLite or
PostgreSQL database.
**Maturity** — Experimental: created 2026-02-08 (~9 months), 93 stars, 3 forks, 1
subscriber, 37 open issues. Actively released — v0.76.0 published the same day as this
review. No independent production-usage evidence beyond its own docs.
**License** — MIT, no restrictions.
**Alternatives** — Neo4j/Dgraph/NebulaGraph (dedicated graph databases, more capable at
scale, a separate service to run); hand-rolled adjacency tables in Postgres (what this
replaces, at the cost of writing the traversal/ontology logic by hand).
**Why this one** — Native TypeScript/SQL graph semantics with no separate database
service — nothing else found today fits this stack this directly.
**Recommendation** — Spike one real relationship-heavy feature (agent memory or a
permissions graph) with it before relying on it for anything load-bearing.

## Small but High-Leverage Utility
**Paperless-NGX Dedupe** — a companion service for the self-hosted document manager
paperless-ngx that finds near-duplicate scans via MinHash/LSH (with a discriminative
penalty to avoid false positives on boilerplate-heavy documents) and optionally
extracts metadata with an LLM, surfacing confidence scores and evidence for review
before applying. Single-container Docker, embedded SQLite, OpenTelemetry built in.
GPL-3.0, conditional on actually running paperless-ngx — removes a specific recurring
chore (manually finding and merging duplicate scans) rather than being general-purpose
infrastructure.

## Run Notes
GitHub's search/repositories API (direct from the GitHub Actions runner,
`GITHUB_TOKEN`, well under the 8,500/hr limit — roughly 60 calls across topic searches,
individual repo lookups, fork/issue inspection, and release checks) was the sole
discovery lever today; WebSearch/WebFetch were not needed. `topic:` searches on
document-processing, pdf-extraction, rag, semantic-search, vector-database,
knowledge-graph, data-pipeline, full-text-search, and etl produced the raw candidate
pool, but the vast majority were either mainstream household names (Milvus, Qdrant,
LlamaIndex, Meilisearch, Airbyte, Airflow, Weaviate) explicitly out of scope per
AGENT.md §7, or repos matching the inflated-engagement pattern already flagged in prior
runs. `raw.githubusercontent.com` was used to read full READMEs for all seven
deep-review candidates before cataloguing. Checking fork and issue authorship directly
via the GitHub API (rather than trusting star/fork counts alone) surfaced the
pyrite-wiki/pyrite sock-puppet-like pattern — a discovery technique worth reusing when a
repo's fork:star or issue:star ratio looks inverted from the norm. No sources were
unreachable.
