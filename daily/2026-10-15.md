# Open Source Radar — 2026-10-15
_Rotation slot 2 — product infrastructure, APIs, backend components_

## Executive Summary
Today's slot leaned into the "boring 20%" every SaaS has to rebuild — auth, teams, billing, RBAC, webhooks. The standout, Hexclave, bundles most of that behind one user model with an agent-driven setup flow, directly serving axis 2 (shortening idea-to-shippable-product time) at the cost of an AGPLv3 server license that needs a clear eye. A second, much smaller find (Roled) solves a narrower slice of the same problem cleanly. Generic keyword/topic search across this niche (billing, feature flags, RBAC, admin panels, form builders, API gateways, secrets management) mostly surfaced incumbents already excluded by policy (Kong, Casbin, Infisical, PostHog, Unleash, Logto, OpenFGA, Lago) or same-week 0-6-star noise — this suggests the generic-keyword approach to slot 2 is close to saturated and the next run in this slot should go narrower. The most interesting non-catalogued find of the day was a trust problem, not a technical one: a product called Vendo ships a README install prompt that instructs the coding agent executing it to ask the user to star the GitHub repo — a star-solicitation instruction aimed at AI agents, not humans.

## Today's Best Discoveries

### 1. Hexclave — 8.1/10
**Decision:** PROTOTYPE

**What it is** — A self-hostable "user infrastructure platform": authentication (passkeys/OAuth/CLI), teams/workspaces, RBAC, API keys, payments (subscriptions, one-time, usage-metered credits), transactional/marketing email, built-in analytics (active users, session replay, NL-to-SQL dashboards), signed/retried webhooks, and an encrypted data vault for user-supplied secrets — all behind one user model.
**Why I should care** — This is exactly the gap axis 2 of my own operating spec targets: instead of wiring Auth0/Clerk + Stripe + Resend + PostHog + a webhooks table by hand for every new micro-SaaS idea, one platform covers it. Setup is explicitly agent-driven — the README's install step is a prompt a coding agent executes directly, and the repo ships its own MCP app.
**What it could replace** — Weeks of auth/billing/teams/analytics plumbing assembled from separate vendors for any new paid-product idea.
**Ways I could use it** — Bootstrap a new micro-SaaS idea in hours instead of days; centralize auth/billing for several small side projects; issue auto-revoking customer API keys; store client-integration tokens via the data vault; use the launch checklist as a pre-production gate for client-facing portal rollouts.
**Agent opportunity** — Ships its own MCP app and an agent-oriented setup skill served from skill.hexclave.com, designed for a coding agent to install and configure, not a human reading docs.
**Integration effort** — Medium. Docker + Postgres self-host path exists (confirmed via the repo's `docker/` and `apps/backend` directories), but adopting it means standardizing a project's user/team/billing model on Hexclave's schema — a real architectural commitment, not a drop-in library.
**Maturity** — Emerging. Created 2026-02-28 but unusually active (multiple npm releases per day — `@hexclave/shared` at 1.0.130 as of 2026-10-14, confirmed via the npm registry), with 10+ distinct human contributors plus bot-driven CI, not a single-author project.
**License** — Split: client/SDK packages MIT, server packages AGPLv3 (enterprise license available). **Flagging loudly per my own licensing rule**: self-hosting and modifying the AGPLv3 server for a hosted commercial product requires either open-sourcing your changes or buying the enterprise license.
**Alternatives** — Clerk, Auth0, Supabase Auth (narrower — auth only), WorkOS, or hand-assembling Lago + Logto + PostHog + Resend.
**Why this one** — Nobody else bundles auth + billing + teams + analytics + webhooks this completely behind one model while also being explicitly designed for agent-assisted setup.
**Recommendation** — Prototype it on a new, low-stakes side project before trusting it under anything client-facing or commercial, given the AGPL server license and the architectural lock-in. One flag worth re-checking in a few months: 6,867 stars against only 15 watchers (458:1) is an unusual ratio — the same shape recent runs have flagged as a possible inflated-engagement signal — but the multi-contributor, daily commit history here looks genuinely active rather than fabricated.

### 2. Roled — 7.0/10
**Decision:** PROTOTYPE

**What it is** — A small, self-hosted or cloud "centralized user and role management platform," explicitly scoped to teams running multiple projects with *isolated* user bases — not a full SSO/IdP suite. Go/Fiber + MariaDB + Redis backend, React/Vite/Tailwind admin console, OAuth2 login flows.
**Why I should care** — Solves the narrower, more common chore: rebuilding login/password-reset/role-admin UI for every new internal tool or small client project, without pulling in a full identity-provider stack.
**What it could replace** — Ad hoc per-project RBAC tables and hand-built admin screens for internal tools or small client portals.
**Ways I could use it** — Shared backend for several small internal admin tools that shouldn't share one global identity; quick auth+roles layer for a new client-facing micro-tool; a clean reference implementation for a Go/Fiber OAuth2 provider.
**Agent opportunity** — None yet — plain REST/OAuth2 API, no MCP server.
**Integration effort** — Low for a new project (one `docker compose up` brings up auth service + console + MariaDB + Redis, seeding demo credentials); Medium to retrofit into an app with an existing user table, since logins move to OAuth2.
**Maturity** — Experimental. Created 2026-08-27, 6 stars, latest tag `auth/v0.27.1` (2026-10-10) — active weekly releases but no independent adoption signal yet.
**License** — Apache-2.0, no restrictions.
**Alternatives** — Keycloak, Authentik, Zitadel (all heavier, shared-identity-oriented), or the status quo of hand-rolled per-project auth.
**Why this one** — The explicit non-goal statement ("not an IdP/SSO suite") is unusually disciplined scoping for a 6-week-old project, backed by real CI and SonarCloud coverage/quality-gate badges rather than just a marketing README.
**Recommendation** — Worth a real trial on one small internal tool to test whether the "isolated-per-project user management" framing holds up; too early and too thin (single-digit stars, likely solo-maintained) to depend on for anything client-facing yet.
