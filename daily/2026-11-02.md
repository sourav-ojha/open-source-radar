# Open Source Radar — 2026-11-02
_Rotation slot 6 — infrastructure, observability, deployment_

## Executive Summary
Today's strongest find is an agent-native self-hosted PaaS (bex) that treats a coding agent's deploy call as identical to a human's rather than bolting an API onto a dashboard — a genuinely different design from the Coolify/Dokploy/CapRover wave already in the catalog. Alongside it, an alert-triage agent (SherlockOps) and Grafana's own agentic CLI (gcx) both point at the same theme: observability tooling is actively being redesigned around "an LLM with tool calls investigates this, a human reviews the output" rather than "a human opens a dashboard." Two already-catalogued MSSP/MERN-relevant tools (MongoRescue, Breeze) shipped real maturity jumps this cycle — HA and chaos-testing for MongoRescue, EDR-vendor integration depth for Breeze. Several adjacent niches searched today (infrastructure drift detection, Kubernetes cost optimization, zero-trust network access, database backup/DR, service mesh, bare-metal provisioning) turned up only a prior-rejected hype wave or thin/stale entrants — noted below rather than padded into the main list.

## Today's Best Discoveries

### 1. bex — 7.6/10
**Decision:** PROTOTYPE

**What it is** — An open-source, Apache-2.0, AI-native alternative to Render: git push to a running HTTPS service on your own infrastructure (local Docker or Hetzner), built on a self-managed Kubernetes substrate (Cluster API) with a Go operator behind it.
**Why I should care** — Dashboard, REST, GraphQL, MCP, and CLI all drive the same operator with no dashboard-only actions, so an agent's deploy is literally the same operation as a human's — not an API bolted onto a human-first tool, which is how every other self-hosted PaaS alternative is built.
**What it could replace** — A recurring Render/Railway/Heroku bill, or a bespoke internal "let an agent deploy things" API that would otherwise need to be hand-built.
**Ways I could use it** — self-hosted internal-tools PaaS on infra already owned; agent-driven deploys via the MCP `deploy` tool; managed Postgres/Valkey for small internal apps without standing up RDS/ElastiCache; studying the Cluster API + bin-packing + idle-hibernation architecture.
**Agent opportunity** — Native MCP server with a `deploy` tool that takes a repo plus a manifest and performs a real deploy in one call — "deploy-from-chat" is a first-class feature, not an afterthought.
**Integration effort** — High. Requires real Kubernetes operational knowledge (Cluster API, `kind`, `clusterctl`), not a single-binary/docker-compose deploy.
**Maturity** — Experimental. The README states explicitly: "not ready for production workloads." 2+ years old (created 2024-04-30) but effectively a 2-person project beyond bot accounts.
**License** — Apache-2.0. No commercial restrictions.
**Alternatives** — Coolify, Dokploy, CapRover (all mature, docker-compose-first, no agent-native control plane); Render/Railway/Heroku (proprietary).
**Why this one** — The agent-first control-plane design is the differentiator, not the PaaS feature list — every interface is a first-class citizen of the same operator.
**Recommendation** — Prototype against a local `kind` cluster before trusting it with anything beyond throwaway services; first surfaced on 2026-09-21 and held to Worth Watching pending this deeper review.

### 2. SherlockOps — 7.4/10
**Decision:** PROTOTYPE

**What it is** — A self-hosted, MIT, Docker-Compose alert-triage agent: receives webhooks from Alertmanager/Grafana/Zabbix/Datadog/ELK/Loki, investigates with an LLM that can call Prometheus/Loki/Kubernetes/CloudWatch/GCP/Azure/PostgreSQL/MongoDB/any MCP server, and posts root-cause analysis to Slack/Telegram/MS Teams within seconds.
**Why I should care** — It automates exactly the first-pass "is this real, what's happening" triage work that otherwise falls on a human the moment an alert fires, across the stack already in play (AWS, Prometheus/Grafana/Loki, Postgres, MongoDB) — and it supports self-hosted Ollama/vLLM for cases where alert context shouldn't leave the premises.
**What it could replace** — Manual on-call triage for the first 5-30 minutes after an alert fires; a bespoke alert-to-LLM pipeline that would otherwise need building from scratch.
**Ways I could use it** — automatic RCA posted to Slack on alert fire; on-call triage assistant checking pod/replication/CloudWatch state before a human opens a dashboard; a white-labeled triage add-on inside an MSSP admin portal; self-hosted-LLM-only configuration for client-data-sensitive triage.
**Agent opportunity** — Consumes any MCP server as a tool, so its investigation surface extends without forking the project.
**Integration effort** — Low. `docker compose up`, configure `.env`/`config.yaml`, point existing alert sources at its webhooks.
**Maturity** — Experimental. 18 stars, 1 fork, 0 subscribers, single maintainer, created 2026-04-01, last pushed 2026-10-05 — essentially unvalidated by any community.
**License** — MIT. No restrictions.
**Alternatives** — PagerDuty/Opsgenie AI triage (proprietary, per-seat), Rootly/Blameless (proprietary), manual triage (status quo).
**Why this one** — Breadth of integrated tools (12+ systems spanning every major cloud plus Postgres/MongoDB) and a credible self-hosted-LLM escape hatch, in a project small enough to actually read end-to-end before trusting it.
**Recommendation** — Trial against a non-critical alert channel first; too new and too small a community to depend on for real on-call coverage yet.

### 3. gcx (Grafana CLI) — 6.8/10
**Decision:** PROTOTYPE

**What it is** — Grafana Labs' own official, Apache-2.0, Generally Available CLI giving terminal and coding-agent access to a Grafana OSS/Enterprise/Cloud deployment's dashboards, alerts, SLOs, metrics, logs, and traces, with bundled agent skills for alert investigation and dashboard-as-code.
**Why I should care** — Grafana itself is excluded from this radar as a household name, but `gcx` is a materially new capability on top of it, turning alert investigation into a shell command or agent skill instead of requiring someone to open a dashboard — directly extends agent-driven ops if Grafana/Prometheus/Loki is already the observability stack.
**What it could replace** — Manual dashboard-opening for routine metric/log/trace checks; hand-rolled scripts against the raw Grafana HTTP API.
**Ways I could use it** — agent-driven alert root-causing from the terminal; `gcx resources pull/push` for dashboard-as-code/GitOps; SLO/alert-rule management from CI; bundled observability-setup agent skills.
**Agent opportunity** — Ships documented agent skills (alert investigation, dashboard creation, SLO management) built for any agentic coding tool, not just one vendor's.
**Integration effort** — Low, but only if Grafana is already deployed (Grafana 12+ required, most features need 13+).
**Maturity** — Mature/GA. Created 2026-03-23, already 811 stars/65 forks/7 subscribers with active weekly releases.
**License** — Apache-2.0. Some commands (SLO, Synthetic Monitoring, IRM, Assistant) require a paid Grafana Cloud tier — a Grafana Cloud billing gate, not a `gcx` license issue.
**Alternatives** — Grafana's own MCP server (complementary, MCP protocol instead of shell), Grafana Assistant (in-product, Cloud-gated).
**Why this one** — It's the first shell-native, any-agentic-tool-compatible interface to Grafana, officially maintained rather than a third-party wrapper.
**Recommendation** — Wire into an agent's toolbelt specifically if Grafana is already running; zero standalone value otherwise.

## Meaningful Updates

**MongoRescue** (YigitCittan/mongorescue) — v0.18.0 → v0.28.0 (10 releases). Previous state: 10-day-old, 6-star, single-binary MongoDB backup/DR tool with no community validation. Current state: added active-passive HA (phase 1), a nightly chaos/fault-injection test suite covering backups/restores/purges/migrations/key-rotation/PITR, privacy/erasure-request tooling, TLS connection material, and KMS-wrapped secret storage via Vault Transit, plus a CVE fix (CVE-2026-78667, net/http DoS). Does this change the recommendation: no, held at PROTOTYPE pending independent track record, but score raised 7.4 → 7.7. Catalog updated: Yes.

**Breeze** (LanternOps/breeze) — v0.121.0 → v0.125.0. Previous state: RMM+PSA platform with an AI operator, evaluated mainly for its architecture and MSSP-context fit. Current state: added client e-sign agreements, ticket merge with SLA/routing rules, Windows update rings, an expanded Trust Center, connection-health monitoring, and — most relevant here — Huntress and SentinelOne EDR deployment driven from policy plus EDR detections/response actions surfaced directly in the platform. Why it matters: deepens the MSSP/PTaaS relevance specifically on the security-operations side. Does this change the recommendation: no, held at PROTOTYPE (AGPL hosting caveat unchanged), score raised 7.0 → 7.2. Catalog updated: Yes.
