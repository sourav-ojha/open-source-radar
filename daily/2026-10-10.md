# Open Source Radar — 2026-10-10
_Rotation slot 4 — data, search, documents, RAG_

## Executive Summary
Today's slot surfaced a strong embedded-database find (LatticeDB — graph + vector + full-text in one file, Node/Python bindings) alongside a genuinely novel agent-infrastructure idea (Graft's on-demand, sandboxed API-integration synthesis). The RAG/document-intelligence space itself was mostly noise today — dozens of same-day 0-star tutorial/portfolio repos ("RAG pipeline", "document QA agent", "text-to-SQL agent") with no real differentiation — but a narrow, well-engineered security utility (schemagate) and a solid coding-agent productivity tool (CocoIndex Code) stood out from the churn. One find, MuninnDB, is architecturally interesting but carries an unusual patent-plus-BSL combination that needs flagging loudly before anyone considers building on it.

## Today's Best Discoveries

### 1. LatticeDB — 8.3/10
**Decision:** PROTOTYPE

**What it is** — Embedded, single-file property-graph database with native HNSW vector search and BM25 full-text indexing behind one Cypher-like query language. Zig core, with bindings for Python, Node.js, Go, and Java.
**Why I should care** — Most embedded databases cover one retrieval axis (graph, vector, or text); this covers all three in one file with credible published performance numbers and a Node.js binding that drops straight into a MERN-adjacent stack.
**What it could replace** — A 3-service stack (Postgres + pgvector + Elasticsearch/Meilisearch) for a single-tenant or desktop product; a hand-wired Neo4j-plus-vector-DB setup for Graph RAG prototyping.
**Ways I could use it** — Local agent-memory store; Graph RAG prototype with zero external infra; embedded knowledge graph inside a CLI or Electron app; local-first app needing relationship + semantic + text search.
**Agent opportunity** — Storage layer for an agent-memory system or local Graph RAG pipeline, opened directly in-process with no database service to run.
**Integration effort** — Low for Python/Node prototyping; Medium if packaging native bindings for distribution across platforms.
**Maturity** — Emerging, pre-1.0 (v0.15.0). Single-maintainer-dominated (494 of ~500 commits); 733 stars but only 2 watchers.
**License** — MIT. No restrictions.
**Alternatives** — Neo4j (server-based), Kuzu (no native vector+FTS fusion), SQLite+sqlite-vec (no graph model), LanceDB (no graph model).
**Why this one** — The only embedded single-file option combining all three search modes in one query layer with bindings already reaching Node and Python.
**Recommendation** — Prototype it for an internal agent-memory or Graph RAG use case; not yet a production dependency given single-maintainer risk.

### 2. CocoIndex Code (ccc) — 7.9/10
**Decision:** PROTOTYPE

**What it is** — AST-based semantic code search CLI built on the already-catalogued CocoIndex engine, packaged as a Claude Code/Grok skill plus MCP server with a claimed ~70% token reduction versus grep/full-file reads.
**Why I should care** — Incremental AST indexing for agent code search is infrastructure most teams never build; this ships it with a 1-minute setup and first-party Claude Code/Grok integration.
**What it could replace** — A hand-built embeddings index for agent-facing code search; ad-hoc grep-based exploration in long agent sessions.
**Ways I could use it** — Drop-in semantic search for a Claude Code session via `npx skills add`; keep an index fresh automatically via a bundled edit hook; expose the same search to any MCP-compatible agent.
**Agent opportunity** — Claude Code Skill + plugin marketplace entry + MCP server + Grok plugin — the most complete agent-native packaging seen in this niche.
**Integration effort** — Low — CLI install plus a skill/plugin registration.
**Maturity** — Emerging, real multi-contributor team (CocoIndex org), 2,823 stars, active release cadence.
**License** — Apache-2.0.
**Alternatives** — grep/ripgrep (no semantic ranking); already-catalogued code-search MCP servers (code-index-mcp, octocode) — this one's edge is the CocoIndex engine plus packaging, not retrieval novelty.
**Why this one** — Reuses a mature Rust indexing engine rather than reinventing AST chunking, and ships the agent integration that engine lacked on its own.
**Recommendation** — Install the skill in a real repo and measure the token-reduction claim directly.

### 3. schemagate — 7.8/10
**Decision:** PROTOTYPE

**What it is** — Row-level-security-aware schema pruning for text-to-SQL agents: filters which tables/columns a caller may see before the model ever writes SQL, across Postgres, Oracle, MySQL, SQL Server, and SQLite.
**Why I should care** — RLS alone produces a quiet failure mode — a disallowed table returns "no rows," indistinguishable from "no data." schemagate moves the access check earlier so the table never enters the prompt, with a benchmarked token reduction (~383 vs ~2,036 tokens on its demo schema) as a side benefit.
**What it could replace** — Hand-rolled, per-project role-based SELECT-list filtering in application code; the false sense of security from relying on RLS alone in a text-to-SQL agent.
**Ways I could use it** — Access-control layer in front of an internal BI/SQL chat agent; authorization layer bolted onto an existing MCP SQL server; a compliance feature for a SaaS reporting product.
**Agent opportunity** — Works with LangChain or any MCP-based SQL agent as a pre-prompt filtering step.
**Integration effort** — Low — a schema-filtering step inserted before existing prompt construction, not a new service.
**Maturity** — Emerging, solo-maintained, but unusually complete for 8 stars: CI, five PyPI releases in three weeks, OpenSSF Best Practices badge, public demo, MCP Registry listing.
**License** — Apache-2.0.
**Alternatives** — Vanna (no access-control layer, explicitly positioned against in its own docs); hand-rolled filtering; RLS alone.
**Why this one** — Directly relevant to an MSSP/security-admin-portal context, and the maturity signals (benchmarks, CI, registry listing) far outrun what 8 stars would suggest.
**Recommendation** — Worth testing against a real internal SQL agent despite the low star count.

### 4. Graft (getmodern-ai) — 7.2/10
**Decision:** STUDY

**What it is** — An MCP server that synthesizes a missing API integration on demand: an agent calls `acquire`, Graft's model reads the vendor's docs and writes a small module, proves it with reads, dry-runs writes behind a credential-injecting proxy, and promotes it into the agent's tool list.
**Why I should care** — The hard part of "let an agent call any API" isn't the HTTP call, it's doing so safely at runtime — sandboxed egress, credential isolation, dry-run-gated writes. Graft ships that safety machinery with an eval harness that scores a real run against exactly those properties.
**What it could replace** — Bespoke, one-off integration code written every time an agent needs a long-tail vendor API with no existing MCP tool.
**Ways I could use it** — Study the sandbox/proxy design as a reference architecture for any "agent writes and runs its own code" feature; self-host and test against a low-stakes vendor API.
**Agent opportunity** — `acquire`, `find_tool`, `promote`, `run_tool` and related meta-tools over MCP, with OAuth for Claude.ai/ChatGPT and bearer tokens for Hermes/OpenClaw.
**Integration effort** — Medium — Docker Compose self-host requiring Postgres and a Docker daemon; the project itself flags the Docker-socket mount as root-equivalent on the host.
**Maturity** — Experimental, v0.1.0, single maintainer, unusually candid about its own limits ("no third-party security audit has been done").
**License** — Apache-2.0 core; MIT plugins; hosted backing is proprietary.
**Alternatives** — Static MCP server catalogs/marketplaces; Composio-style hosted integration platforms.
**Why this one** — Not a variant of an existing pattern — genuinely different approach (synthesize the tool at call time vs. pre-built catalog), with a well-documented security model to match.
**Recommendation** — Study the architecture; hold off on production use given the single-maintainer, no-audit, root-equivalent-mount combination.

### 5. MuninnDB — 6.6/10
**Decision:** WATCH

**What it is** — Single-binary agent-memory server modeling memory strength as decay/reinforcement (Ebbinghaus-style decay, Hebbian-style reinforcement, Bayesian confidence) rather than flat vector similarity, over MCP/REST/gRPC.
**Why I should care** — A real architectural difference from the usual vector-store-plus-recency-filter agent memory, with a working implementation and an actual multi-contributor team, not just a research idea.
**What it could replace** — Manually re-establishing context for an agent at the start of every session; a flat-vector-similarity memory store that can't distinguish old-but-relevant from old-but-stale.
**Ways I could use it** — Persistent coding-agent memory that surfaces relevant history automatically; architecture reference for a decay/reinforcement memory model.
**Agent opportunity** — `muninn init` auto-configures Claude Desktop, Claude Code, Cursor, OpenClaw, Windsurf and others for MCP access.
**Integration effort** — Low to try (single binary, zero dependencies) — but change the shipped default admin credentials immediately.
**Maturity** — Alpha. Created February 2026, real team (924 commits from the primary author, several contributors at 7-26 commits).
**License** — **Flagged loudly:** Business Source License 1.1, converting to Apache-2.0 in 2030. Free for individuals/small orgs/internal use only; a commercial license is required beyond that. The project also states a provisional patent was filed on its core mechanism — an unusual combination that narrows reuse further than BSL alone.
**Alternatives** — Mem0, Zep, and other already-catalogued agent-memory projects (differentiator here is the explicit decay/reinforcement engine).
**Why this one** — The decay/reinforcement model is a genuine architectural idea worth tracking, independent of whether the licensing allows adoption today.
**Recommendation** — Watch only — do not build on this without explicit legal clearance given the BSL-plus-patent combination.
