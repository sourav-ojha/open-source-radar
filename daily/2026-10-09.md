## Today's Best Discoveries

### 1. pgschema — 8.7/10
**Decision:** PROTOTYPE

**What it is** — A CLI from Bytebase's pgplex suite that brings Terraform-style declarative schema migration to PostgreSQL: dump the live schema, edit the desired state as plain SQL, generate a reviewable migration plan as a diff, apply it with concurrent-change detection and lock-timeout control.
**Why I should care** — This is the Terraform plan/apply mental model applied directly to Postgres DDL, which is exactly the stack in use. It replaces the usual hand-written up/down migration file with a single source-of-truth schema file and an automatically generated, reviewable diff.
**What it could replace** — Hand-written Flyway/golang-migrate-style migration files, and the risk of an ALTER statement that doesn't match what was intended.
**Ways I could use it** — Run `pgschema plan` in CI as a required check before a schema change merges; manage RLS policies/triggers/materialized views declaratively instead of as ad hoc scripts; let a coding agent propose a schema change through a deterministic plan instead of freeform SQL; use `pgschema dump` to get a clean starting schema.sql for a new service.
**Agent opportunity** — The plan/apply output is explicitly designed to be deterministic and agent-drivable rather than freeform SQL — this is close to a native fit for "let an agent change the schema safely."
**Integration effort** — Low: single binary (Homebrew/mise/Docker/Nix), no server component, drops into an existing CI pipeline as a plan step. Windows is unsupported (WSL/Linux only).
**Maturity** — Emerging: created 2025-06-08 (not brand new), 1,056 stars, 64 forks, current release v1.13.1 (2026-09-20). Backed by Bytebase, an established open-source DB-governance company, which lowers solo-maintainer risk.
**License** — Apache-2.0, unrestricted commercial use.
**Alternatives** — Atlas (ariga/atlas, more mature/multi-dialect but heavier); golang-migrate/Flyway (the imperative status quo); reshape (fabianlindfors, zero-downtime but imperative rather than declarative).
**Why this one** — The declarative, Terraform-shaped workflow plus genuinely deep Postgres DDL coverage (documented support for RLS, constraint triggers, materialized views, custom aggregates, column-level GRANT/REVOKE) is a meaningfully different approach from the imperative-migration status quo, backed by a credible company rather than a weekend project.
**Recommendation** — Prototype on the next real schema change to a Postgres-backed service before adopting it as the default migration workflow.

### 2. Plumber — 8.0/10
**Decision:** PROTOTYPE

**What it is** — A CLI/Docker/GitHub-Action security scanner that audits GitHub Actions and GitLab CI pipelines for risky patterns (script injection, overly broad permissions, unpinned actions, secret exposure), reporting in SARIF, GitLab SAST, JSON, OCSF, and CycloneDX.
**Why I should care** — CI/CD misconfiguration is a real, easy-to-miss supply-chain weak point, and this covers both GitHub Actions and GitLab CI in one tool with native Code Scanning / MR-widget integration.
**What it could replace** — Manual workflow-YAML review for risky patterns like `pull_request_target` checking out untrusted code, unpinned third-party `uses:` refs, or over-broad `permissions:` blocks.
**Ways I could use it** — Add `plumber analyze` as a required CI check; audit a client repo's pipeline config for the MSSP/PTaaS side without cloning it (`plumber analyze github.com/owner/repo`); export SARIF to GitHub Code Scanning; export CycloneDX/OCSF into existing security tooling.
**Agent opportunity** — Structured JSON/SARIF findings are straightforward for an agent to turn into a remediation PR (pin an action to a SHA, narrow a permissions block).
**Integration effort** — Low: Homebrew/mise binary, Docker image, official GitHub Action, GitLab CI component — no account or server required for local/CI use.
**Maturity** — Emerging: created 2026-01-19, 821 stars, 36 forks, actively released (v0.6.0, pushed today). 105 open issues against a small team is a backlog worth watching.
**License** — MPL-2.0 (file-level weak copyleft on Plumber's own source; no obligations on the code it scans) — worth a quick internal OSS-policy check before MSSP/client-facing use.
**Alternatives** — zizmor (GitHub-Actions-only, no GitLab CI support); OpenSSF Scorecard (broader repo health, not pipeline-config-specific); step-security/harden-runner (runtime egress control, complementary rather than competing).
**Why this one** — Covers both major CI platforms in one tool and has real, checkable adoption (go-delve/delve 24.9k★, lightpanda-io/browser 36k★ listed and verified as adopters) rather than relying on star count alone.
**Recommendation** — Add as a CI step on one repo first; a strong candidate to extend into the MSSP/PTaaS service catalog if it holds up.

### 3. roborev — 7.5/10
**Decision:** PROTOTYPE

**What it is** — A local daemon that installs a git post-commit hook to review every commit a coding agent makes, surfacing findings in a TUI/browser UI and feeding them back into the live agent session (Claude Code, Codex, Gemini CLI, Cursor, and others) via per-agent hooks.
**Why I should care** — Most "AI code review" tools fire at PR time, after an agent has already built hours of work on top of an issue. This reviews every commit continuously and pushes findings back into the same active session while context is still fresh.
**What it could replace** — Manually re-prompting an agent to self-review its own diff, or discovering accumulated issues only at PR time.
**Ways I could use it** — `roborev init` for automatic background review of every commit on a repo; `roborev refine` before opening a PR to iterate until reviews pass; wire `roborev agent-hook install` into an active Claude Code session; use the browser UI's cost/latency/reliability analytics to see how much agent-review overhead is costing.
**Agent opportunity** — This is itself agent-loop infrastructure — the whole design point is closing the loop back into the coding agent's live session.
**Integration effort** — Low: single binary, git hook install, runs entirely locally with no hosted service; review execution is delegated to whichever agent/model is already configured.
**Maturity** — Emerging: created 2026-01-05, 1,748 stars, 165 forks (~9.4% fork:star ratio — a reasonable real-usage signal), v0.71.0, pre-1.0 and iterating fast.
**License** — MIT, unrestricted.
**Alternatives** — proval (already catalogued) — self-hosted LLM PR-review agent, reviews at PR time rather than continuously per-commit; manually re-prompting an agent (status quo).
**Why this one** — Different point in the loop than existing PR-review tools: continuous per-commit review fed straight back into the active agent session, not a separate end-of-task review pass. The standout of a crowded same-week "AI code review" wave that otherwise had no clear differentiation.
**Recommendation** — Wire into one actively agent-driven repo to see whether the per-commit signal is useful day to day or just noise.

### 4. Browser Debugger CLI (bdg) — 7.6/10
**Decision:** PROTOTYPE

**What it is** — An npm CLI that keeps a Chrome session open in the background and exposes DOM, network, console, cookies, and raw CDP as short shell commands, built for coding agents to drive and debug a browser without an MCP server, a Playwright script, or screenshots.
**Why I should care** — Removes two common costs of agent browser tooling: MCP server setup, and the token overhead of screenshot-heavy browser state. Output is compact and designed to pipe into `jq`.
**What it could replace** — Throwaway Playwright scripts written just to answer "why didn't this click work," and MCP browser servers for simple debugging tasks.
**Ways I could use it** — `bdg network getCookies` + `bdg eval` to debug a broken frontend flow; reuse an authenticated session's cookies from the shell to hit an API directly with curl; `bdg dom a11y tree` for quick accessibility inspection; script-free one-command-at-a-time automation for a one-off check.
**Agent opportunity** — Built explicitly for Claude Code, Codex, and Gemini CLI as first-class users — this is squarely agent tooling, not a general dev utility with an agent bolted on.
**Integration effort** — Low: `npm install -g browser-debugger-cli`, no MCP client/server setup.
**Maturity** — Emerging: created 2025-10-31 (~1 year old), 170 stars, 1 watcher, v0.15.0 (pushed today, npm version cross-checked against the GitHub tag). Small sample size.
**License** — MIT, unrestricted.
**Alternatives** — MCP browser servers (Playwright MCP, browser-use) — heavier setup, more tokens per call; Chrome DevTools MCP (already catalogued) — MCP-based, heavier integration.
**Why this one** — The explicit design choice to skip MCP and screenshots in favor of a plain, cheap CLI is a genuinely different tradeoff from the MCP-first browser-automation tools already catalogued.
**Recommendation** — Try it on the next frontend debugging session alongside Claude Code.

### 5. EasyPostman — 6.8/10
**Decision:** PROTOTYPE

**What it is** — An open-source Java 17 desktop app combining Postman-style API debugging with JMeter-style load testing, with Git-backed workspaces, a headless CLI for CI, and a built-in MCP server.
**Why I should care** — Most free Postman alternatives (Bruno, Hoppscotch, Insomnia) stop at the request-collection layer; this bundles load testing and an MCP server in the same local-first app.
**What it could replace** — A paid Postman Team plan for collection sharing, and a separate JMeter setup for load testing.
**Ways I could use it** — Share collections via Git workspaces instead of a Postman Team seat; run the same collection as a functional test and a load test; run collections headless in CI instead of Newman; let an AI client call a saved API request through the MCP server.
**Agent opportunity** — The built-in MCP server lets an agent run a saved, pre-authenticated request directly instead of reconstructing a curl command from scratch.
**Integration effort** — Low as an end-user tool: native installers bundle a runtime, no separate Java install needed; a cross-platform JAR exists for direct Java 17+ use.
**Maturity** — Emerging: created 2025-06-18, 722 stars, 61 forks, v6.2.4 (pushed today). Smaller community than Bruno/Hoppscotch/Insomnia.
**License** — Apache-2.0, unrestricted.
**Alternatives** — Bruno/Hoppscotch/Insomnia (no bundled load testing); Postman paid tier (the cost this removes); k6/JMeter standalone (no collections layer).
**Why this one** — The load-testing + MCP-server combination isn't covered by any existing catalogue entry, even though it's the weakest fit of today's five (Java desktop app, outside the core JS/TS stack, used only as an end-user tool rather than integrated).
**Recommendation** — Try it for the next team API-collection-sharing or load-testing need before reaching for Postman Team.

## Small but High-Leverage Utility
**hl** (pamburus/hl) — a single Rust binary that converts JSON or logfmt logs into a clear, human-readable, colorized format in the terminal. 3,303 stars, MIT, actively maintained (v0.36.3). This is the kind of tool that pays for itself the first time a CloudWatch/ECS/Lambda JSON log line needs to be read without piping it through `jq` by hand — pipe any JSON log stream through `hl` and get readable timestamps, leveled/colored fields, and a clean layout instead of a wall of `{"ts":...}`.
