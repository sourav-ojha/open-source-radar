# Open Source Radar — 2026-10-23
_Rotation slot 3 — developer utilities, debugging, testing_

## Executive Summary
Today's slot surfaced a cluster of tools aimed at a specific, recurring problem: trusting output that a coding agent produced. A non-blocking quality gate (Code Quality) checks whether an agent fixed code or just quieted its tests; a monorepo-audit skill (monorepo-doctor) checks whether an agent's refactor respected package boundaries; a self-hosted regression framework (AutotestHub) tries to give AI-agent behavior the same baseline-comparison discipline as API/browser tests. Alongside that theme, a genuinely interesting hidden gem turned up outside the AI-agent angle entirely: a multi-language mutation-testing tool from Robert C. Martin (Uncle Bob) with real TypeScript support. GitHub keyword search was also unusually noisy today with a new pattern worth flagging: a wave of same-day, templated "Best X for Y 2026" repos with inflated star counts and no real content behind the title — a content-farm signature distinct from the star:watcher-ratio fraud pattern flagged in prior runs.

## Today's Best Discoveries

### 1. Code Quality — 8.0/10
**Decision:** PROTOTYPE

**What it is** — A non-blocking quality advisor built specifically for coding agents (Claude Code, Codex, Grok, pi, omp, OpenCode): git hooks and agent-lifecycle hooks that flag test tampering, hold a CRAP-complexity bar on changed functions, check diff coverage, and scan for secrets, across 12 languages from one config file.
**Why I should care** — The specific failure mode it targets — "the agent made the tests green, did it fix the code or the tests?" — is a real and growing risk as more day-to-day coding gets delegated to an agent, and it's agent-native (hooks into the agent's lifecycle, not just a CI step) rather than a bolt-on linter.
**What it could replace** — The manual "did the agent actually fix this or just quiet the test" check that otherwise happens only at code review, plus ad hoc secrets scanning on agent commits.
**Ways I could use it** — Install as a Claude Code plugin to get a red-flag report after agent turns touching tests; catch an agent quietly raising a function's complexity while "fixing" something else; backstop against pasted secrets; catch agent-added code with no corresponding test via diff-coverage checks.
**Agent opportunity** — It is itself agent tooling: installable hooks/plugins across six agent harnesses, with a non-blocking Stop-hook pattern that reports once on the agent's next message rather than holding the turn.
**Integration effort** — Low: one-line plugin install per agent harness, Bun required, no server.
**Maturity** — Emerging: created 2026-09-21, 19 stars, 2 forks, 4 releases (latest v1.3.3), 407 passing tests, single contributor.
**License** — MIT, unrestricted commercial use.
**Alternatives** — commit-check (already catalogued, adjacent commit-policy niche); roborev (already catalogued, broader LLM-driven review); plain CI coverage gates.
**Why this one** — Deterministic-first design (LLM classifier is an optional fallback, not the core mechanism) makes it auditable in a way most "AI reviews AI" tools aren't.
**Recommendation** — Prototype against an existing Claude Code or Codex workflow.

### 2. monorepo-doctor — 7.8/10
**Decision:** PROTOTYPE

**What it is** — A read-only AI agent skill that audits npm/yarn/pnpm/bun JS/TS workspaces (deeper rules for Nx/Turborepo) across five checks — package boundaries, circular dependencies, task-cache correctness, CI test coverage, and test code leaking into production — writing an evidence-backed Markdown/JSON report, paired with a separate `monorepo-boundaries-cleanup` skill that pays down findings in small PRs.
**Why I should care** — JS/TS monorepos are exactly the shape of project most likely to accumulate the problems it checks for, and the read-only-audit-then-separate-PR-skill split keeps an agent's destructive actions behind a human checkpoint.
**What it could replace** — The ad hoc, rarely-done exercise of manually tracing import boundaries and cache-config correctness across workspace packages.
**Ways I could use it** — Baseline an existing Nx/Turborepo monorepo before a refactor; triage severity-ranked circular-dependency findings; feed the report into a PR template or CI comment; hand the baseline to the cleanup skill for incremental PRs.
**Agent opportunity** — Ships as a Claude Code-style `SKILL.md` with an `llms.txt` for agent consumption; the diagnose/cleanup split is a reusable pattern for other agent-driven refactor tooling.
**Integration effort** — Low: agent skill, no server, Node ≥ 22.5 required.
**Maturity** — Experimental: created 2026-10-10, 8 stars, 1 fork, 2 contributors, dedicated docs site.
**License** — MIT, unrestricted commercial use.
**Alternatives** — Nx `enforce-module-boundaries` / `turbo boundaries` / dependency-cruiser (the linter layer this builds on); knip; manual madge-style audits.
**Why this one** — The false-positive tuning described (e.g. skipping idiomatic lazy-ORM cycles, not flagging unused packages as boundary violations) is the detail that usually determines whether this class of linter gets left on or disabled within a week.
**Recommendation** — Run the audit once against an existing Node/React monorepo as a free baseline.

### 3. mutator — 7.5/10
**Decision:** STUDY

**What it is** — A single-binary mutation testing tool covering Clojure, Java, Go, TypeScript, Rust, and Python in one run, from Robert C. Martin (Uncle Bob, Clean Code author), with differential re-runs and a kill/survive snapshot consumed by his companion `uml-viewer`.
**Why I should care** — Mutation testing answers "would the suite notice if the logic broke," which coverage percentage doesn't, and TypeScript is a genuine first-class target here (same mutation rules as Java, spelled for TS/JS, with explicit `??`/`?.`/Express-handler handling).
**What it could replace** — The rarely-done manual audit of whether "100% coverage" tests actually assert anything meaningful; differential re-runs make this cheap enough to run per-PR instead of as a one-off.
**Ways I could use it** — Run `--changed` in CI on a PR's touched files; audit legacy code with high coverage but a regression history; use deterministic exit codes as a CI gate without the full `uml-viewer` stack; reuse existing coverage reports to skip re-instrumentation.
**Agent opportunity** — Grade a coding agent's "added tests" by mutation score instead of line coverage — much harder to game.
**Integration effort** — Medium: the mutation engine runs standalone, but full namespace/function attribution requires the sibling `crapper` repo checked out alongside it, and the CRAP-score view requires `uml-viewer` too.
**Maturity** — Experimental: created 2026-09-30, 53 stars, 6 forks, 0 tagged releases, single contributor — but the contributor is the verified Robert C. Martin (17.3k GitHub followers, cleancoder.com).
**License** — 0BSD, maximally permissive.
**Alternatives** — StrykerJS (the mature JS/TS-native incumbent, the safer default for actual adoption today); PIT (Java); cargo-mutants (Rust).
**Why this one** — Not a drop-in replacement for StrykerJS yet, but the "same mutation decisions, different syntax" multi-language architecture is worth studying, and the author's track record lowers the usual new-tool skepticism.
**Recommendation** — Study the architecture; spot-check a run against an existing TS suite before deciding whether to adopt over StrykerJS.

### 4. AutotestHub — 6.8/10
**Decision:** STUDY

**What it is** — A self-hosted regression-testing framework with a web console spanning API execution plans, browser tests (pytest + Playwright), and AI agent conversation/tool-call evaluation, built around an observe → confirm → publish → run → compare workflow with immutable case baselines.
**Why I should care** — AI-agent regression testing is a real gap: "did this change break the agent's behavior" is a different question from "did this change break an API response," and this starts from an observed agent failure rather than a hand-written test case, which matches how agent bugs actually surface.
**What it could replace** — Eyeballing agent conversation logs after a prompt/model change with no record of what "correct" was supposed to look like, and the baseline-drift failure mode where someone quietly edits the expected result instead of re-confirming it.
**Ways I could use it** — Capture a failed agent session and get automatic baseline comparison on later prompt changes; run API plans and Playwright tests from one console in shared regression batches; retrieve comparisons via CLI for a CI gate; track AI-assisted admin-portal features as prompts change.
**Agent opportunity** — AI agent evaluation is a first-class test channel (session traces, confirmed rules, judge profiles), not bolted onto a generic runner.
**Integration effort** — Medium: Docker Compose stack (Postgres, Redis, scheduler, three workers), not a single binary.
**Maturity** — Experimental: created 2026-10-09, 21 stars, 0 forks, 0 releases, single contributor.
**License** — MIT, unrestricted commercial use.
**Alternatives** — Playwright/pytest directly (what this wraps); ad hoc eval harnesses (LangSmith, custom scripts); vibecheck (already catalogued, different — an LLM-graded PR comprehension gate, not a regression framework).
**Why this one** — The immutable-baseline-after-human-confirmation design is architecturally the right call for this problem, even though the project itself is unproven.
**Recommendation** — Study the workflow pattern; the Python/Postgres/Redis footprint and lack of outside validation make it too early to stand up for real use yet.

## Small but High-Leverage Utility
**ActionRepro** (Krem24919/ActionRepro, MIT) turns a failed GitHub Actions run into a local reproducibility bundle: point it at a run URL or a saved log, and it detects the ecosystem, extracts the likely failure cause and closest repro command, and redacts secrets heuristically — no LLM, no backend, no telemetry. It's tiny (3 stars, 18 days old) but has shipped 5 releases already and ships MCP support for coding agents. The specific annoyance it kills — scrolling raw CI logs to guess what broke — is universal enough on any GitHub Actions-based workflow to be worth the five minutes to try it on the next real failure.
