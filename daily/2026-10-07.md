## Today's Best Discoveries

### 1. Planning with Files — 8.7/10
**Decision:** USE NOW

**What it is** — An Agent Skill that keeps `task_plan.md`, `findings.md`, and
`progress.md` on disk and re-injects the relevant slice via lifecycle hooks every turn,
so a coding agent's state survives `/clear`, compaction, and crashes.
**Why I should care** — This exact failure mode (losing track of a long task after
context gets wiped) is a recurring, real cost on multi-hour Claude Code sessions —
including sessions like this radar's own daily run.
**What it could replace** — Hand-rolled "write a scratch file and hope the agent reads
it" conventions, and the time cost of re-explaining state to an agent that just lost it.
**Ways I could use it** — Install as a Claude Code plugin on any multi-session project;
use `findings.md` to survive long debugging sessions across `/clear` cycles; use it as
the shared state layer between an orchestrator and subagents.
**Agent opportunity** — Ships natively as a Claude Code plugin, Codex CLI plugin, and
generic Agent Skill (`npx skills install`) — directly usable, nothing to build.
**Integration effort** — Low: skill/plugin install, no server or config required.
**Maturity** — Emerging but active: created 2026-01-03, v3.23.0, 526+ commits, 60 real
contributors, GitHub release and npm version match exactly.
**License** — MIT, no commercial restrictions.
**Alternatives** — Hand-rolled scratch-file conventions; Beads (complementary — tracks
upcoming work, not in-progress state); heavier agent-memory services (mem0, Hippo).
**Why this one** — Cross-agent standard (60+ agents) rather than a single-tool hack, with
real commit/contributor volume behind it.
**Recommendation** — Install on one real multi-session project and confirm `task_plan.md`
survives a deliberate `/clear` with useful content intact.

### 2. MoAI-ADK — 7.7/10
**Decision:** PROTOTYPE

**What it is** — A verification-driven agent orchestration harness for Claude Code: a
SPEC-driven plan/run/sync workflow with "TRUST 5" quality gates and Claude×GLM multi-LLM
cost routing, distributed as a single Go binary.
**Why I should care** — Addresses trusting an agent's own "done" claim via structural
gates, and gives a concrete lever (route cheaper tasks to GLM) on Claude Code spend.
**What it could replace** — Manual re-verification of agent output, and ad hoc per-task
judgment calls about which model to use for cost reasons.
**Ways I could use it** — Wrap one real Claude Code feature branch in the SPEC/TRUST
workflow; test the Claude×GLM routing on a bulk/low-stakes task to measure real savings;
borrow the TRUST-gate concept for a lighter custom checklist even without the full tool.
**Agent opportunity** — Sits around Claude Code sessions as a harness, not a library.
**Integration effort** — Medium: binary install is trivial, but adopting the SPEC/TRUST
folder structure and workflow is a real process change.
**Maturity** — Emerging: created 2025-09-16, 1,230 stars, CI/CodeQL/Codecov configured,
docs site + companion book. Tagged release (v3.1.2) trails the README's advertised
v3.1.3 by ~6 weeks — a release-cadence flag worth watching before pinning a version.
**License** — Apache-2.0, no commercial restrictions.
**Alternatives** — Spec Kitty, buildermethods/agent-os, GSD Pi (see Rejected, below).
**Why this one** — The only entrant in this week's spec-driven-dev wave that's
Claude-Code-specific with an explicit trust/verification framing and built-in multi-LLM
cost control, rather than a general spec-writing or codebase-standards tool.
**Recommendation** — Try it on one real feature branch specifically to evaluate TRUST
gate friction and the Claude×GLM routing's real cost savings.

### 3. AgentOS (framerslab) — 7.4/10
**Decision:** PROTOTYPE

**What it is** — A TypeScript agent framework: persistent cognitive memory, runtime tool
forging, multi-agent orchestration, optional HEXACO personality model, one dispatch
interface across 11 LLM providers. npm package, Apache-2.0.
**Why I should care** — Most agent frameworks surfaced to date are Python-first; this is
embeddable directly into a Node/React stack without a second runtime.
**What it could replace** — Custom memory persistence, multi-provider LLM dispatch, and
multi-agent coordination code that would otherwise be built from scratch.
**Ways I could use it** — Backbone for an internal tool or a commercial product feature
needing an agent with memory across sessions; study the runtime tool-forging mechanism
as a pattern; use the multi-provider dispatch to avoid single-vendor lock-in.
**Agent opportunity** — Framework-level — the layer an MCP server or CLI would be built
*on top of*, not something that exposes MCP itself.
**Integration effort** — Low-to-medium: `npm install`, but its memory/orchestration
abstractions are an architectural commitment, not a config toggle.
**Maturity** — Emerging: created 2025-10-28, 676 stars, pre-1.0, CI + Codecov configured.
NVIDIA Inception program member (a vetted credibility signal). Claims 85.6% on
LongMemEval-S, a real published benchmark — score is self-reported, not independently
reproduced here.
**License** — Apache-2.0, embeddable in a commercial product.
**Alternatives** — agentOS (Rivet, already catalogued — unrelated despite the name);
Microsoft Agent Framework; Google ADK (heavier, Python/.NET-first); Mastra/LangGraph.js
(not deep-reviewed this run).
**Why this one** — TypeScript-native and embeddable, with an unusual (worth-studying)
personality-model design rather than a typical system-prompt persona hack.
**Recommendation** — Small spike building one agent feature on it to test the memory and
tool-forging abstractions before considering it for anything commercial, given pre-1.0
maturity.
