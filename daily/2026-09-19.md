# Open Source Radar — 2026-09-19
_Rotation slot 4 — data, search, documents, RAG_

## Executive Summary
Today's run landed on a genuinely useful document/search cluster. The headline find is Xberg, the confirmed successor to Kreuzberg (whose HTML→Markdown component was already tracked here) — now a full 107-format document-intelligence engine with OCR, transcription, code intelligence, and an MCP server, spanning 15 language bindings. Alongside it, Timescale shipped a small, permissively-licensed Postgres extension that closes the BM25-ranking gap left by plain `tsvector` search, without dragging in a second datastore or an AGPL license. Two further finds sit closer to the product-opportunity axis: a permission-aware enterprise-RAG platform that treats access control as a first-class retrieval concern rather than an afterthought, and a self-hosted, drop-in-compatible replacement for paid Firecrawl/Tavily scraping API bills. The GitHub Search API surfaced heavy volume in the "AI agent memory," "AI agent gateway," and "PDF/document extraction" spaces again today — the extraction wave in particular is now large enough that Xberg's broad scope made picking a single best-in-class entry straightforward rather than requiring a hard call between near-duplicates.

## Today's Best Discoveries

### 1. Xberg — 8.8/10
**Decision:** USE NOW

**What it is** — A polyglot document-intelligence engine with a Rust core: extracts text, tables, metadata, and structured data from 107 formats, with OCR, audio/video transcription, layout/table reconstruction, code intelligence for 371 languages, embeddings, and schema-driven structured extraction, callable as a library (15 bindings), CLI, REST API, or MCP server.
**Why I should care** — One engine replaces the multi-library pipeline (PDF parser + OCR engine + table extractor + chunker) most RAG ingestion code assembles by hand, and it's natively callable from Node.js, not just Python.
**What it could replace** — A hand-rolled document-ingestion pipeline, or a paid document-intelligence API (Unstructured-style services) for a product's ingestion layer.
**Ways I could use it** — Single ingestion step for a RAG pipeline handling mixed document types; OCR + layout reconstruction for scanned uploads; code-intelligence extraction for syntax-aware RAG chunking over a codebase; schema-driven structured JSON extraction without hand-written prompts; point a coding agent at it via its built-in MCP server.
**Agent opportunity** — Ships an official MCP server out of the box; REST mode (`xberg serve`) works as a shared ingestion microservice.
**Integration effort** — Low: `pip install xberg` / `npm install @xberg-io/xberg` / Docker/Helm for a standalone service.
**Maturity** — Mature engine under a young rebrand: 9,325 stars, created Jan 2025, actively maintained (pushed today), real CI + Codecov, multi-contributor.
**License** — MIT, verified against the LICENSE file. No commercial restrictions.
**Alternatives** — yfedoseev/pdf_oxide + office_oxide (narrower but faster for pure PDF/Office extraction, more language bindings); firecrawl/pdf-inspector (Firecrawl's narrow scanned-vs-text PDF classifier); docling-project/docling (similar scope, Python-first, no first-class Node bindings); catalogued opendataloader-pdf (narrower, PDF-only).
**Why this one** — Broadest scope of anything in the extraction/intelligence space reviewed today, with a first-class MCP server and Node.js bindings that most competitors lack.
**Recommendation** — Point it at a real mixed-format document set (PDF + scanned images + a code directory) to validate the OCR and code-intelligence claims before deep production use.

### 2. pg_textsearch — 8.3/10
**Decision:** USE NOW

**What it is** — A PostgreSQL extension adding BM25 relevance-ranked full-text search via a simple `content <@> 'query'` operator, built by Timescale.
**Why I should care** — Closes the real gap between plain Postgres full-text search and a dedicated search engine — proper BM25 ranking — without adding a second datastore.
**What it could replace** — A bolted-on Algolia/Typesense integration, or standing up Elasticsearch/OpenSearch purely for ranked keyword search when the data already lives in Postgres.
**Ways I could use it** — Add ranked keyword search to an existing Postgres table; pair with pgvector/pgvectorscale in the same database for hybrid retrieval; per-tenant partitioned search indexes in a multi-tenant SaaS.
**Agent opportunity** — Natural backing store for an MCP server needing keyword search over structured records already in Postgres.
**Integration effort** — Low: prebuilt binaries for Linux amd64/arm64, or build from source; requires a `shared_preload_libraries` change and a restart to install.
**Maturity** — Emerging: pre-1.0 (v1.4.0), created July 2025, real CI + benchmark workflow + Coverity Scan badge.
**License** — PostgreSQL License (permissive, BSD/MIT-style), verified against LICENSE file.
**Alternatives** — paradedb/paradedb (broader all-in-one Postgres search+vector platform, but AGPL-3.0); Elasticsearch/OpenSearch (assumed known, much higher operational overhead for this narrow a need).
**Why this one** — Narrow, permissively-licensed, single-purpose extension rather than an AGPL all-in-one platform, from a maintainer (Timescale) with a track record in the Postgres extension space.
**Recommendation** — Install against a non-critical table first given the pre-1.0 status, then pair with pgvector for hybrid search.

### 3. PipesHub AI — 7.8/10
**Decision:** PROTOTYPE

**What it is** — An open-source platform connecting enterprise knowledge sources (drives, wikis, chat, email) to AI agents with permission-aware retrieval — results are scoped to the querying user's actual access rights, with citations back to source.
**Why I should care** — Permission-aware retrieval is the part most hand-rolled RAG setups skip until a security review forces the issue; this ships it as a first-class concern.
**What it could replace** — Hand-built per-source connectors plus a custom permission-inheritance model, a multi-week project most teams underestimate.
**Ways I could use it** — Internal "ask our docs/wiki/drive" assistant that respects real document permissions; RAG layer for a support agent where source systems have different access boundaries; baseline for a permission-aware knowledge-search feature in a B2B product.
**Agent opportunity** — Positioned explicitly as the retrieval layer AI agents call, not just a human-facing search UI.
**Integration effort** — Medium: full platform (connectors, indexing, permission engine, UI) via Docker, not a single library.
**Maturity** — Emerging: pre-1.0 (v0.8.0), created March 2025, real multi-contributor team, active Discord/roadmap.
**License** — Apache-2.0, no commercial restrictions.
**Alternatives** — onyx-dot-app/onyx (32,161★, larger and more established, similar connector model, not deep-reviewed this run); building permission-scoped retrieval by hand on pgvector/pg_textsearch.
**Why this one** — Ships permission-aware retrieval with citations as the core feature rather than an add-on, which is directly relevant given the MSSP/PTaaS-adjacent context where access-boundary correctness matters.
**Recommendation** — Worth a small real trial if a permission-scoped internal-knowledge assistant becomes a real need; audit the ACL-inheritance logic directly before trusting it with real access boundaries.

### 4. fastCRW (crw) — 7.5/10
**Decision:** PROTOTYPE

**What it is** — A self-hostable Rust web scraper/crawler/search engine exposing a Firecrawl/Tavily-compatible API as a single ~6 MB binary, turning URLs into clean Markdown or structured JSON.
**Why I should care** — Drop-in API compatibility means an existing Firecrawl/Tavily integration can point at a self-hosted binary instead of a metered API with no code changes beyond the base URL, for non-JS-heavy pages.
**What it could replace** — A recurring Firecrawl or Tavily API subscription for scrape/crawl/search calls in an agent pipeline.
**Ways I could use it** — Give a coding agent a local `crw search`/`crw scrape` tool with no per-call cost; RAG ingestion step for turning URLs into Markdown; site-mapping/crawling for a small product's content-indexing job.
**Agent opportunity** — Ships an official MCP server (crw-mcp) that auto-registers with Claude Code/Cursor/Codex/Gemini CLI/OpenCode/Windsurf on install.
**Integration effort** — Low: single binary or Docker.
**Maturity** — Emerging: created March 2026, active (pushed today), but contributors skew heavily to a single author (997 commits vs. next-highest human contributor at 4).
**License** — AGPL-3.0. **Flagged loudly**: self-hosting a modified version as a network service others query requires releasing source under AGPL or a commercial license; running it internally/locally has no such obligation.
**Alternatives** — Firecrawl and Tavily themselves (the hosted, paid services this is compatible with); browserbase/stagehand (heavier, browser-automation-first, different use case).
**Why this one** — The only self-hosted entrant found this run with genuine drop-in API compatibility with two specific paid services, backed by published head-to-head benchmarks.
**Recommendation** — Trial it for non-JS-heavy scraping/crawling to cut a Firecrawl/Tavily bill; verify the AGPL implications before any embedding into a hosted product, and keep an eye on the single-maintainer bus-factor risk.
