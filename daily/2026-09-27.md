# Open Source Radar — 2026-09-27
_Rotation slot 5 — self-hosted SaaS alternatives, productivity_

## Executive Summary
Today's discovery leaned into self-hostable replacements for paid business software: a genuinely agent-native Calendly/Cal.com alternative that ships as a single Go binary, a WHMCS alternative directly relevant to the MSSP billing side of the operator's work, and an all-in-one team workspace whose bidirectional-graph architecture is worth studying even though full adoption isn't warranted. Separately, a routine-looking version bump on an already-catalogued project turned out to be a real security release worth flagging on its own. The self-hosted "all-in-one workspace" niche is showing the same same-day-spam pattern seen previously in codebase-context and agent-memory tooling — six to eight near-identical, mostly zero-star repos surfaced today alone, none differentiated enough to catalogue.

## Today's Best Discoveries

### 1. Calnode — 8.1/10
**Decision:** PROTOTYPE

**What it is** — A Calendly/Cal.com-style scheduling engine shipped as a single Go binary with embedded pure-Go SQLite (Litestream for backups) — no Redis, no Postgres, no separate API server.
**Why I should care** — cal.com is the default self-hosted scheduler, but it's 500k+ LOC across ~100 packages needing Postgres, Redis, and a separate API server. Calnode does the same job as one static binary, and it's the most agent-native scheduling tool found so far: a Model Context Protocol server is compiled *into* the binary, exposing booking/reschedule/cancel/slot-lookup as first-class agent tools over the same code path as the REST API.
**What it could replace** — a recurring Calendly seat, or the operational overhead of self-hosting cal.com when a booking page plus an API is all that's actually needed.
**Ways I could use it** — self-hosted client-booking page for PTaaS scoping calls; an AI sales/support agent that books meetings via the built-in MCP server; webhook-driven booking automation into n8n; white-label booking-as-a-feature embedded per-tenant inside a product (cheap to run many instances of a single binary).
**Agent opportunity** — native MCP server (stdio + Streamable HTTP), with Calnode acting as its own OAuth 2.1 authorization server so a remote agent can Connect without a pre-shared key.
**Integration effort** — Low. `docker run` one container, or drop the binary on a VPS.
**Maturity** — Emerging. Created 2026-06-23 (~3 months old), pre-1.0 (v0.9.0), one dominant contributor.
**License** — Apache-2.0. No commercial-use restrictions, and notably more permissive than cal.com's AGPL-3.0.
**Alternatives** — cal.com (AGPL, far heavier to operate), Calendly (closed SaaS), asm0dey/calit (same pitch on Quarkus+Postgres — heavier JVM stack, 6 stars, earlier-stage).
**Why this one** — the combination of single-binary simplicity and MCP compiled into the core (not bolted on) is not something the mainstream alternatives offer.
**Recommendation** — prototype it for a real client-booking use case before depending on it for anything business-critical, given the pre-1.0 version and single-maintainer profile.

### 2. PNLCS (Panelica) — 7.1/10
**Decision:** PROTOTYPE

**What it is** — A self-hosted, MIT-licensed hosting billing platform and client portal — an open alternative to WHMCS covering invoicing, domain/SSL management, support tickets, and reseller hosting, with a deliberately WHMCS-familiar data model.
**Why I should care** — This lands directly on the MSSP security admin-portal SaaS side: a client billing/support portal without a recurring WHMCS license, with a Stripe gateway and a Proxmox VE module both confirmed tested in production.
**What it could replace** — a WHMCS license, or a bespoke client-invoicing/ticketing build for a services business.
**Ways I could use it** — client billing portal for MSSP retainers; reseller-hosting billing for a side VPS business using the tested Proxmox VE module; a near-zero-learning-curve WHMCS migration target for anyone who already knows WHMCS's workflows.
**Agent opportunity** — ships a documented MCP server alongside its REST API for querying client/invoice/ticket data.
**Integration effort** — Medium. Official Docker image available, but it's a full Laravel/PHP application to run as-is, not a library to fold into an existing Node/Mongo stack.
**Maturity** — Emerging. Created 2026-04-18 (~5 months old), 60 stars, small team building it alongside their main commercial product.
**License** — MIT. No restrictions on commercial use, resale, or modification — a real advantage over WHMCS's proprietary terms.
**Alternatives** — WHMCS (proprietary, the incumbent), FOSSBilling (older, GPL, slower-moving), Blesta (proprietary).
**Why this one** — modern Laravel 13 stack, MIT license, and a live production demo, against an incumbent that's paid and a spiritual predecessor (FOSSBilling) that's aging.
**Recommendation** — worth trialing for MSSP client billing given the direct fit; validate the Stripe flow and any specific registrar/gateway modules needed before relying on it for real invoicing.

### 3. Macro — 6.8/10
**Decision:** STUDY

**What it is** — An all-in-one team workspace (email, chat, docs, tasks, calls, CRM) unified over a single bidirectional graph backend, with AI agents given shared team-level memory across every object in the graph.
**Why I should care** — Not for adoption, but for the architecture: instead of Slack + Linear + Notion + HubSpot + Superhuman glued together with Zapier and MCP (the exact failure mode the maintainers describe hitting at ~20 people), every surface shares one backend and one permission system, and agents are first-class participants in that graph rather than a bolted-on chatbot.
**What it could replace** — conceptually, the "ten SaaS tools plus glue" pattern; practically, nothing here — adoption cost is too high for what it is today.
**Ways I could use it** — study the cross-object `@`-linking and unified-agent-memory pattern for a much narrower internal tool (e.g. a support-inbox-plus-CRM-plus-tasks product); read how they expose unified search (including PDF attachments parsed from email) to agents without pulling whole threads first.
**Agent opportunity** — a dedicated tools/MCP surface lets agents search and act across every workspace object (drafting email, updating CRM records from chat) with shared memory, not per-tool context.
**Integration effort** — High. 42 deployable services, 167 Rust crates, Pulumi-managed infra — self-hosting is technically supported under AGPL but is not a weekend deploy, and the project is primarily distributed as a hosted product (macro.com).
**Maturity** — Emerging as an open project (open-sourced ~10.5 months ago) but not as a product — two years of internal dogfooding by a ~15-person paid team before release, near-daily releases.
**License** — **AGPL-3.0 — flagged loudly.** Self-hosting internally is fine; offering a modified version as a hosted service to others triggers AGPL's source-disclosure requirement unless a separate commercial license is arranged.
**Alternatives** — the SaaS stack it targets replacing (Slack/Linear/Notion/HubSpot/Superhuman); partial-overlap open tools like Twenty CRM, Docmost, AFFiNE, none of which unify the whole surface.
**Why this one** — genuinely different design point (one graph, not ten tools) rather than another Notion-alternative or another Slack-alternative in isolation.
**Recommendation** — study the architecture; do not attempt adoption given the AGPL terms and the all-or-nothing migration cost.

## Meaningful Updates

**Kaneo** (already catalogued, USE NOW, 7.9/10) — v2.25.0 → v2.28.3. The intermediate release, v2.26.0 (2026-09-21), is a security release: on self-hosted instances ≤v2.25.0 that didn't explicitly set `AUTH_SECRET`, it silently fell back to a publicly-known Better Auth default, making session cookies forgeable offline — an authentication-bypass-grade bug. The same release also separates the `project:share` permission from `project:update`, defaults `TRUSTED_PROXIES` to loopback only, stops publishing the Postgres port in Compose, and requires an explicit WebSocket `Origin`/credentials. It ships several breaking changes (documented in the v2.26.0 notes) that must be read before upgrading. Recommendation unchanged (USE NOW) — this is a "patch immediately" update, not a reason to reconsider the tool, but anyone self-hosting Kaneo on 2.25.0 or earlier should upgrade now and rotate `AUTH_SECRET` if it was ever visible in a Helm/Deployment manifest. Catalog updated: Yes.
