## Today's Best Discoveries

### 1. mongo-migrate-kit — 7.6/10
**Decision:** PROTOTYPE

**What it is** — A Node.js MongoDB migration toolkit (`mmk` CLI + typed API + VS Code extension) with single-file runs, rollback by batch/step/file/redo, dry-run previews, opt-in transactions, lifecycle hooks, SHA-256 tamper detection, and MongoDB-native locking.
**Why I should care** — This is squarely a MERN-stack gap-filler: migrate-mongo, the usual default, has none of the rollback granularity, dry-run safety, or tamper detection this ships with.
**What it could replace** — migrate-mongo in any existing Node/Mongo project, or a hand-rolled wrapper around it.
**Ways I could use it** — Dry-run a migration against staging before touching prod; roll back one bad file instead of a whole batch; wrap a schema-shape change in a transaction; use the VS Code GUI to compare pending migrations across environments; detect a migration file edited after it was applied.
**Agent opportunity** — `mmk dry-run up` prints a plain-text plan a CI step or coding agent could gate on before running migrations unattended.
**Integration effort** — Low: `npm install mongo-migrate-kit`, zero required config.
**Maturity** — Emerging: created 2026-06-01, 21 stars, 1 subscriber, single maintainer, no tagged GitHub releases (npm 1.6.0 is the version source).
**License** — MIT, no restrictions.
**Alternatives** — migrate-mongo, umzug, Mongock (JVM-only).
**Why this one** — It's the only Mongo-specific migration tool found with dry-run + checksum tamper detection + native locking together, rather than one or two of those.
**Recommendation** — Prototype on a side project before trusting it against production data; the correctness story is sound but the project is young and small.

### 2. lazyjournal — 7.8/10
**Decision:** USE NOW

**What it is** — A Go TUI (lazydocker/lazygit-styled) unifying journald, auditd, filesystem, Docker/Podman, Compose, and Kubernetes pod logs behind one filterable screen, with a web mode for browser access.
**Why I should care** — Debugging across EC2/EKS infra usually means switching between journalctl, docker logs, and kubectl logs with different flags each time; this collapses all of them into one filter/search model.
**What it could replace** — Ad hoc `journalctl`/`docker logs`/`kubectl logs`/`tail -f` invocations, and the tmux gymnastics needed to watch several at once.
**Ways I could use it** — First-look incident triage on EC2/EKS boxes; live regex/fuzzy filtering instead of repeated grep piping; web mode for a remote box without a full SSH+tmux session; quick MSSP admin-portal infra checks.
**Agent opportunity** — None meaningful — built as an interactive human TUI, not a scriptable automation surface.
**Integration effort** — Low: single static Go binary, Homebrew/Docker/Conda-Forge/AUR/Debian packages, no config needed.
**Maturity** — Mature: ~2 years old, 1,440 stars, 35 forks, 8 subscribers, actively released (v0.8.7 the same day as review).
**License** — MIT, no restrictions.
**Alternatives** — lazydocker (Docker-only), lnav (no native Docker/k8s source list), stern/k9s (Kubernetes-only), Dozzle (web UI, Docker-only).
**Why this one** — The only tool found unifying journald + auditd + Docker + Podman + Compose + Kubernetes behind one lazy*-family TUI rather than a tool per source.
**Recommendation** — Install it; zero risk, immediately useful for anyone doing hands-on debugging across mixed journald/container/k8s infra.

### 3. codeburn — 7.4/10
**Decision:** USE NOW

**What it is** — A free, local-first tracker of AI coding-agent token usage and cost across 37+ tools (Claude Code, Cursor, Codex, Gemini CLI, etc.), run via `npx codeburn` or as a native desktop app.
**Why I should care** — Coding-agent spend is scattered across however many tools get used and only shows up in aggregate on a monthly provider bill; this gives a per-project, per-model breakdown immediately, with no backend to run.
**What it could replace** — Manually cross-referencing provider billing dashboards, or just not knowing which project/model is burning the budget.
**Ways I could use it** — Catch a runaway-cost session live; compare Claude Code vs Cursor vs Codex spend across side projects; a zero-setup personal equivalent of the already-catalogued team-oriented Agent Console.
**Agent opportunity** — Its local usage data files could in principle be read by a skill for self-reporting spend, though the tool itself is a human-facing dashboard.
**Integration effort** — Low: `npx codeburn`, no account, no backend.
**Maturity** — Emerging-to-mature: ~7 months old, 11,704 stars, 910 forks, 33 subscribers, active cross-platform releases, Product Hunt launch, Claude/Codex open-source grant credit.
**License** — MIT, no restrictions.
**Alternatives** — Agent Console (catalogued, team dashboard, needs deployment), ccusage (narrower, Claude-Code-only).
**Why this one** — Covers 37+ tools rather than one, ships as a real cross-platform app (Microsoft Store, Homebrew, .deb), and needs no infrastructure at all.
**Recommendation** — Try it; zero-risk and immediately informative for anyone running more than one coding-agent tool.

## Small but High-Leverage Utility
**Drydock (git fleet)** (`yetidevworks/drydock`) — a single Rust binary that renders a live TUI dashboard of uncommitted, unpushed, and unreleased work across every git repo under a configured tree of root directories, color-coded by state. For anyone with dozens of local checkouts (side projects, client repos, forks), this answers "what did I leave unfinished" in one screen instead of a shell loop over `git status`. **Name collision warning:** this is unrelated to the already-catalogued Drydock (`CodesWhat/drydock`, a self-hosted container-image-update watcher, AGPL-3.0) — same display name, different author, different purpose, different license. Catalogued under slug `drydock-git-fleet-tui` to keep them apart.
