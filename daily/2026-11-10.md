# Open Source Radar — 2026-11-10
_Rotation slot 7 — experimental projects and hidden gems_

## Executive Summary
Today's strongest theme is testing/execution infrastructure that's smaller and more credible than it looks on star count: a TypeScript-native Deterministic Simulation Testing framework (Chronos) fills a gap left by an otherwise Go/Zig-only wave of DST frameworks this week, and a mature WASI sandbox (Runno) quietly does what most of 2026's "agent sandbox" repos are still trying to build. zvec-grep is the headline discovery — a real, benchmarked hybrid search CLI built on Alibaba's zvec engine rather than another from-scratch vector store. Scott Hanselman's disposable-Windows-VM tool is a genuine hidden gem for the PTaaS/MSSP side of things, even though it doesn't fit the primary MERN/AWS stack.

## Today's Best Discoveries

### 1. zvec-grep (zg) — 8.1/10
**Decision:** USE NOW

**What it is** — A Rust CLI, distributed via npm, unifying ripgrep-equivalent exact search, BM25 keyword search, and vector/semantic search behind one local-first index, for both humans and coding agents, over source code, documents, and structured data. Built on Alibaba's zvec vector engine.
**Why I should care** — Most "agent-friendly search" tools wrap one search mode. This wraps three behind one index and publishes real cross-domain agent benchmarks (SWE-QA-Bench via Claude Code, BrowseComp-Plus via Codex) showing fewer tool calls and less token spend, rather than marketing claims.
**What it could replace** — A custom grep+embeddings glue script; an agent re-ranking raw ripgrep output itself.
**Ways I could use it** — Search a large Node/TS monorepo by meaning; give a coding agent one hybrid search tool; search mixed code+docs+config in one query; offline/local search for sensitive codebases.
**Agent opportunity** — CLI-first, already scriptable as an agent tool; `zg --install --target opencode --yes` wires it into OpenCode directly; Claude Code/Codex usage shown in published benchmarks (exact install flag for those targets unclear from available documentation).
**Integration effort** — Low: `npm install -g @zvec/zvec-grep`, index once, no server.
**Maturity** — Emerging (created July 2026, already 4,298 stars / 263 forks / 90 open issues / 14 subscribers — elevated star:subscriber ratio but paired with real fork/issue activity).
**License** — Apache-2.0, no restrictions.
**Alternatives** — ripgrep (exact-match only); already-catalogued AST-based agent code search (CocoIndex Code/ccc); Sourcegraph-style hosted code search.
**Why this one** — Real backing engine (Alibaba's zvec, not a from-scratch vector store) plus published, reproducible agent benchmarks instead of marketing copy.
**Recommendation** — Install and try it on an active Node/TS repo this week.

### 2. Runno — 7.8/10
**Decision:** PROTOTYPE

**What it is** — A WASI-based sandboxed code-execution runtime shipped as four npm packages (browser web components, a Node sandbox, an isomorphic WASI runner, and an MCP server), running Python/Ruby/QuickJS/SQLite/C inside an isolated sandbox in the browser, on a server, or via MCP.
**Why I should care** — Any product feature needing to "run this code safely" (grader, interview tool, runnable docs, an agent verifying generated code) normally means building a Docker sandbox with real security review. Runno has done that work since 2021.
**What it could replace** — A from-scratch Docker-based ephemeral sandbox; granting a coding agent raw host shell access to verify a snippet runs.
**Ways I could use it** — A "run code safely" feature in a product; grading untrusted Python/Ruby/SQL/C submissions; an MCP code-execution tool for agents; in-browser what-if code checks with no server round-trip.
**Agent opportunity** — `@runno/mcp` is a ready-made MCP server exposing sandboxed execution to any MCP client.
**Integration effort** — Medium: npm install; browser use needs COOP/COEP headers for SharedArrayBuffer.
**Maturity** — Mature relative to most 2026 agent-sandbox entrants: created 2021, 775 stars, 48 forks, 12 subscribers, actively pushed.
**License** — MIT, no restrictions.
**Alternatives** — Pyodide/WebContainers (browser-only, heavier); already-catalogued cluster-native agent sandboxes (capsulerun/runtime, OpenKruise Agents — heavier, need cluster infra); Docker-based ephemeral sandboxes.
**Why this one** — The only entrant offering the same sandbox from a browser component, a Node library, and an MCP server, with no Docker/Kubernetes dependency and a multi-year track record.
**Recommendation** — Prototype the next time a "run code safely" feature or agent tool is actually needed.

### 3. Chronos — 7.5/10
**Decision:** PROTOTYPE

**What it is** — A zero-runtime-dependency Deterministic Simulation Testing (DST) framework for TypeScript/Node.js: virtual time, a seeded PRNG driving every random draw/delay/scheduling decision, a simulated chaos network (partitions, crash/restart), and entropy guards intercepting Date.now()/Math.random()/timers — reproducing distributed race conditions bit-for-bit from one seed. Inspired by FoundationDB/TigerBeetle.
**Why I should care** — DST catches distributed race conditions before production, and every prior credible DST implementation found in this radar (detest, marionette, faultline) required Go or Zig. Chronos is the first TypeScript-native entrant.
**What it could replace** — Guessing at a flaky CI failure from a stack trace; a hand-rolled chaos-network harness.
**Ways I could use it** — Testing an SQS/BullMQ-style Node worker pipeline under simulated partitions/crashes; reproducing a "fails once in CI" bug deterministically; seed-sweeping concurrent code paths in CI; validating idempotency/retry logic.
**Agent opportunity** — A coding agent could run a seed sweep as a pre-merge check on newly-touched concurrent code, flagging a concrete failing seed+capsule instead of a vague race-condition comment.
**Integration effort** — Medium: requires writing code against Chronos's clock/network/randomness abstractions — not a drop-in for existing untouched code.
**Maturity** — Experimental: 19 stars, 0 subscribers, pre-1.0 (v0.3.0), 18 open issues vs. 2 forks — real CI and published npm packages, but unproven beyond the author.
**License** — MIT, no restrictions.
**Alternatives** — k1LoW/detest (already catalogued, Go); sb2bg/marionette (Zig); hmdsefi/faultline and lockstep (Go) — a same-week DST wave, none TypeScript-native.
**Why this one** — Only TS-native option in an otherwise Go/Zig-only niche, directly usable on a Node backend without a language switch.
**Recommendation** — Try it on one concurrency-sensitive Node module (a queue consumer, a cache-invalidation path) before deciding whether to adopt more broadly.

### 4. sandbox-mcp — 7.3/10
**Decision:** PROTOTYPE

**What it is** — A CLI (`sbx`) and optional MCP adapter, from Microsoft developer advocate Scott Hanselman, automating Windows Sandbox to boot a real, disposable, network-off Windows 11 machine, drive an app's UI via UI Automation, capture evidence, and tear it down.
**Why I should care** — Directly fits a concrete secondary use case: safely detonating a suspicious attachment or installer from a PTaaS/MSSP client engagement without touching a real machine. Nothing else found gives a disposable, network-off, real Windows machine with UI-driving and an MCP adapter in one CLI.
**What it could replace** — A manually-maintained snapshot/restore Windows VM; testing an unknown binary on a real, persistent machine.
**Ways I could use it** — Safely opening a suspicious client file; catching "works on my machine" bugs in a Windows desktop app; giving an agent a sandboxed Windows GUI to verify a build against; regression-testing installers on a genuinely clean machine.
**Agent opportunity** — MCP adapter exposes the full sandbox lifecycle (boot/deploy/drive UI/capture evidence/teardown) as agent tools with inline images.
**Integration effort** — High: Windows 11 Pro/Enterprise host with Hyper-V-capable hardware required; doesn't run from a Mac/Linux dev machine or most constrained cloud instances.
**Maturity** — Emerging: created 4 days before review, 390 stars/19 forks/4 subscribers/1 open issue — fast growth consistent with the author's high public profile, not the fake-engagement pattern flagged elsewhere.
**License** — MIT, no restrictions.
**Alternatives** — Long-lived Windows VM snapshot/restore (slower, drifts); GitHub Actions windows-latest runners (heavier, non-interactive); commercial malware sandboxes like Any.run/Joe Sandbox (hosted).
**Why this one** — Disposable + network-off + UI-automation-driven + MCP, from a credible, highly visible author, in one small CLI.
**Recommendation** — Worth a one-off trial on a Windows host the next time a client engagement needs to open something untrusted. Does not fit primary day-to-day MERN/AWS development.

## Small but High-Leverage Utility
**Address** (daimon3332/address) — A self-hosted, Dockerized Node.js 24/PostgreSQL 16 service generating realistic, real addresses (sourced from official registries and open map data, not randomly assembled strings) for 27 countries, with a bearer-authenticated API for single/batch generation. It directly fixes the recurring annoyance of Faker-style test addresses failing real-world postcode/format validation in checkout and onboarding flows — and it's built on exactly the Node/Postgres stack already in use. The elevated star:subscriber ratio (~764:1) is the one thing worth watching.
