# ZenStack

## Summary
A TypeScript data layer for Node.js/Bun apps: a schema-first ORM compatible with
Prisma's schema and API, with built-in declarative access control and data validation,
automatic CRUD API generation (with framework adapters), automatic TanStack Query hooks
for frontend CRUD, Zod schema generation, and a Kysely-based query builder as a
fully-typed escape hatch. V3 is a ground-up rewrite that replaces the Prisma engine
itself with an in-house Kysely-based engine while keeping a Prisma-compatible API.

## Why I Should Care
It removes a real, recurring source of backend bugs — per-endpoint access-control logic
written by hand — by moving authorization into the schema as declarative policy, on a
stack (TypeScript/Node, Prisma-adjacent) already in use.

## Problems It Can Remove
- Hand-written authorization checks scattered across API endpoints, a common source of
  subtle access-control bugs.
- Boilerplate CRUD API code and frontend data-fetching hooks that would otherwise be
  written by hand or generated by a separate tool.
- Falling back to Prisma's raw/typed-SQL escape hatches when the ORM isn't flexible
  enough — ZenStack's Kysely-based builder is fully typed instead.

## Practical Uses
- Add ZenStack to an existing Prisma-based Node/TypeScript backend and move
  access-control logic into the schema.
- Scaffold a new project (`npm create zenstack@latest`) to get typed CRUD APIs and
  TanStack Query hooks immediately.
- Use polymorphism and advanced modeling patterns not available in stock Prisma.

## Product Opportunities
Meaningfully cuts backend-boilerplate time on every new product's data layer,
particularly multi-tenant SaaS work where access-control policy sprawl across many
endpoints is a recurring source of both bugs and wasted engineering time.

## Agent / Automation Opportunities
Not agent-specific, but a schema that declares access control alongside data shape is a
good fit for AI-coding-agent-generated CRUD code — the agent has one place to look for
both the data model and the authorization rules instead of hunting through handlers.

## Integration
Low effort. `npx @zenstackhq/cli@latest init` on an existing project, or
`npm create zenstack@latest my-project` for a new one. Pure TypeScript (no Rust/WASM
components in V3), embeds as a library rather than requiring a separate service.

## Architecture Notes
V3 replaced the Prisma query engine with an in-house engine built on
[Kysely](https://kysely.dev) while preserving a Prisma-compatible query API — the
project's own blog post frames this as a "bold decision" trading short-term stability
risk for long-term flexibility they said they couldn't achieve while depending on
Prisma's engine internals. Worth reading before adopting V3 in anything critical.

## Maturity
Established project (created 2022, 2,945 stars, active Discord community, named
sponsors including Marblism and CodeRabbit) currently in the early stability window of a
major V3 rewrite (`v3.9.6` as of this review). Treat the V3 engine specifically as less
battle-tested than the V2 lineage that built the star base.

## Alternatives
- Plain Prisma + hand-written guards (the status quo).
- **Supabase Row-Level Security** — Postgres-specific, ties the app to Supabase's Postgres.
- **CASL / Casbin** — authorization-only, no ORM/API generation.
- **Hasura** — GraphQL-first, heavier infra footprint.

## Risks / Limitations
- V3's new engine is recent; re-test critical access-control policies after upgrading.
- Tied to Prisma-style relational schemas — doesn't help with MongoDB-native access
  patterns.
- Smaller, sponsor-funded team relative to Prisma itself; check issue-response time
  before depending on it for anything time-critical.

## Recommendation
PROTOTYPE — solid fit for a new TypeScript/Postgres backend; worth trying on a
non-critical service first given the V3 engine's youth before migrating an
access-control-sensitive production API.
