# Open Source Radar — 2026-11-09
_Rotation slot 6 — infrastructure, observability, deployment_

## Executive Summary
Today's slot surfaced four genuinely distinct infrastructure niches rather than variations on one theme: a Kubernetes UI built MCP-first from day one (directly relevant to EKS), an AI-agent-driven IaC governance platform from a real retail giant rather than a demo, a mature AWS cost-waste policy engine whose own marketing oversells one capability, and a self-hosted certificate control plane getting ahead of the industry's move to much shorter TLS cert lifetimes. The common thread: every one of them pairs a real operational pain point with an MCP or agent-facing surface, which is becoming the default expectation for new infrastructure tooling rather than a bonus feature.

## Today's Best Discoveries

### 1. Radar (Skyhook) — 8.6/10
**Decision:** USE NOW

**What it is** — An open-source Kubernetes UI distributed as a single Go binary, `kubectl` plugin, or desktop app, with an MCP server on by default exposing topology, ranked issues, event/change timeline with diffs, Helm, GitOps state, live traffic, and a 44-check audit to any MCP-aware AI coding agent.
**Why I should care** — Removes the "paste kubectl output into the agent chat" loop on EKS clusters — both a human and an agent query the same maintained, live view, with zero in-cluster footprint for local use.
**What it could replace** — Lens/K9s/Octant for visual inspection, plus the manual context-rebuilding an agent does every session when only given raw kubectl output.
**Ways I could use it** — Local EKS debugging with a ranked issue queue instead of manual correlation; handing an agent the read-only MCP endpoint for self-service diagnosis; Helm revision diffing before a rollback; the 44-check audit ahead of a client-facing MSSP review; visualizing live traffic on a cluster already running Istio/Hubble.
**Agent opportunity** — MCP server on by default, same port as the UI, no API key needed. Read-only tools cover topology/health/events/diffs/logs/Helm/audit/RBAC/cost/Prometheus; write tools (restart/scale/apply/rollback/GitOps-sync/node-drain) are explicitly marked destructive for confirmation gating. Secret values withheld and scrubbed from logs/env/Helm values, with the README noting this can't catch everything.
**Integration effort** — Low: single binary or kubectl plugin, no CRDs, no cluster install for individual/local use; Helm-based in-cluster mode exists for shared team access.
**Maturity** — Emerging but fast-moving: created 2026-01-20, 4,071 stars, 269 forks, v1.20.2 released today. YC W23 company.
**License** — Apache-2.0, no restrictions; a separate paid "Radar Cloud" hosted multi-cluster tier exists but the OSS core is presented as fully featured.
**Alternatives** — Lens, K9s, Octant, Headlamp (no MCP/agent surface); raw kubectl plus agent shell access (no persistent context).
**Why this one** — First Kubernetes UI found in this radar built MCP-first rather than bolted on, with destructive-action gating and secret-scrubbing as first-class design decisions.
**Recommendation** — Install locally against a real EKS cluster today; trivial to try, genuinely useful for agent-assisted debugging.

### 2. CloudBurn — 8.1/10
**Decision:** USE NOW

**What it is** — An open-source policy engine of 82 deterministic AWS cost-waste rules, runnable as a static `scan` (Terraform/CloudFormation, for CI/PR gating) or a live-account `discover` (via Resource Explorer). Ships as a CLI, GitHub Action, VS Code extension (preview), MCP plugin, and SDK.
**Why I should care** — Sourav's stack is AWS-heavy (EC2, Lambda, EKS, ALB, CloudFront, S3) — this is a zero-infrastructure way to catch cost-waste patterns in Terraform before they ship rather than on the monthly bill.
**What it could replace** — Manual infra-PR review for known waste patterns; a from-scratch cost-waste CI rule engine.
**Ways I could use it** — GitHub Action to fail a PR on a known waste pattern; one-time `discover` inventory against an existing AWS account; on-save VS Code flagging while writing Terraform; MCP plugin so an agent checks its own generated Terraform; SDK embedded in an internal review tool.
**Agent opportunity** — MCP plugin exposes the rule set as read-only tools; SDK allows embedding the same evaluation inside a custom agent tool.
**Integration effort** — Low: CLI (Homebrew/npm) and GitHub Action are the fastest path to value, no hosted service required.
**Maturity** — Mature: created 2021, 1,802 stars, 370 forks, 43 subscribers (healthy ≈42:1 ratio), pushed 2026-11-08.
**License** — Apache-2.0, no restrictions.
**Alternatives** — Infracost (cost estimation, complementary not overlapping); cloud-custodian, OpenCost/krr (different layer); AWS Trusted Advisor/Compute Optimizer (less transparent, AWS-coupled).
**Why this one** — Deterministic, versioned rule IDs rather than an LLM estimate, plus a 5-year track record from a known AWS consultancy.
**Recommendation** — Add the `scan` GitHub Action to an existing Terraform CI pipeline now. Flag: the README tagline claims it "remediates what's already burning," but the body only documents `discover` reporting what needs fixing — no auto-fix feature is described. Treat "remediates" as marketing language until verified hands-on.

### 3. Kumoss — 7.8/10
**Decision:** PROTOTYPE

**What it is** — An AI-agent-driven Infrastructure-as-Code platform from Inditex (Zara's parent company). A plain-language request becomes a Terraform/OpenTofu plan, gets retried until clean, has drift corrected against live state in the same PR, passes a compliance-agent review, and opens a gated pull request with cost/impact estimates — multicloud, bring-your-own LLM.
**Why I should care** — First project in this radar treating natural-language-to-infra-change as a governed pipeline (plan validation, drift correction, compliance gate) rather than just prompting a coding agent at a Terraform repo, and it's a real company's internal tool, not a demo.
**What it could replace** — Hand-written Terraform diffs for routine day-2 changes; manual `terraform import` sessions; ad hoc drift discovery.
**Ways I could use it** — Day-2 AWS changes requested in plain language; gated infra-change access for a non-infra teammate; studying the compliance-agent-review/policy-locked-session pattern for reuse in any product giving an AI agent write access to something sensitive.
**Agent opportunity** — It's itself an agent pipeline rather than a tool for an external agent to call; MCP/A2A support is explicitly roadmapped, not yet implemented. Bring-your-own LLM via LiteLLM avoids a hosted API key dependency.
**Integration effort** — High: FastAPI + React + Postgres + Redis + RustFS + SearXNG + nginx + OpenTelemetry + Arize Phoenix — a real multi-service stack, and authorization must be implemented by the adopter.
**Maturity** — Emerging: created 2026-05-06 (~6 months), 145 stars, 57 open issues, v1.0.8. OpenSSF Scorecard badge and a security disclosure program present. README explicitly states the roadmap "reflects intent, not commitment."
**License** — Apache-2.0, copyright INDITEX S.A.
**Alternatives** — Manual Terraform PRs (status quo); Atlantis, Terraform Cloud, Spacelift, env0, the catalogued Terraducktel — none of these generate the code itself from a natural-language request.
**Why this one** — The compliance-gate architecture, not the LLM call, is the hard and genuinely novel part here.
**Recommendation** — Worth a sandbox-account trial to evaluate the governance pattern, not a quick spin-up given the setup weight and unimplemented authorization.

### 4. CertMate — 7.7/10
**Decision:** PROTOTYPE

**What it is** — A self-hosted TLS certificate control plane: multi-CA issuance (Let's Encrypt, ZeroSSL, Google Trust Services, Actalis, DigiCert, Sectigo, SSL.com, or its own private CA), Certificate Transparency-log discovery, ARI-aware renewal tracking, and deploy-hook push with verification. Its own internal ACME server issues for internal names/IPs that public CAs can't cover. Web UI, REST API, CLI, and MCP server.
**Why I should care** — Cert renewal is a recurring, low-visibility task that causes real outages when forgotten, and the CA/Browser Forum's SC-081 ballot is shortening public cert lifetimes to 47 days by March 2029 — "remember to renew" is becoming "must be fully automated."
**What it could replace** — Per-service certbot cron jobs; no-visibility blind spots on certs issued outside the normal process.
**Ways I could use it** — Centralize renewal across EC2/EB/ALB/CloudFront-fronted services; run its internal ACME server for internal mTLS/service names on EKS; CT-log discovery to catch shadow-IT certs; point cert-manager at it for internal names.
**Agent opportunity** — Ships an MCP server for querying cert inventory/expiry or triggering issuance/renewal directly.
**Integration effort** — Medium: Docker Compose/installer/Helm are all straightforward, but running your own private CA is a real operational responsibility.
**Maturity** — Mature: created 2025-06-24 (~1.5 years), 1,487 stars, 121 forks, v2.55.2, frequent release cadence, CI/CodeQL/Scorecard badges, i18n docs.
**License** — MIT (core); the separate multi-tenant CertMate-ng edition is BSL-1.1 — not evaluated here, don't assume it inherits MIT terms.
**Alternatives** — certimate-go/certimate (9,426 stars — the larger, more mainstream visual ACME tool in this niche; CertMate differentiates via its internal CA, multi-CA support, CSR-only issuance, and MCP server). cert-manager (K8s-native but no private-CA-for-internal-names). mkcertWeb, pki-manager-web (narrower).
**Why this one** — The only tool found here that both covers the internal/private-name gap and is explicitly built for the shortened-lifetime era, not just automating today's 90-day Let's Encrypt cadence.
**Recommendation** — Trial in a non-critical internal environment first — cert-automation failures are high-blast-radius — then expand to production cert management.
