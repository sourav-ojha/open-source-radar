# Open Source Radar — 2026-09-21
_Rotation slot 6 — infrastructure, observability, deployment_

## Executive Summary
Slot 6's mainstream corners (OpenTelemetry, eBPF, distributed tracing, GitOps) are dominated by names already well known (Cilium, Jaeger, SigNoz, OpenObserve, ArgoCD-family tooling) or by homelab/dotfiles repos with no general applicability. The genuine finds sat one layer under that: a zero-infrastructure SSH-native log viewer (Nerdlog), a GitOps deploy tool correctly scoped to Docker Compose instead of assuming Kubernetes (doco-cd), a smaller S3-backed alternative to OpenObserve (Rootprint), and a mature cross-database schema-governance tool now positioning itself for AI-agent-proposed migrations (Bytebase) with a license worth reading closely. Also caught one meaningful update: Kingfisher's default secret-scan behavior got materially more thorough.

## Today's Best Discoveries

### 1. Nerdlog — 8.4/10
**Decision:** USE NOW

**What it is** — A fast, remote-first, multi-host TUI log viewer with an interactive timeline histogram and no central server. It opens SSH connections directly to each target host, runs the query (time range + pattern filter) remotely, and only pulls back matching lines plus histogram data — never the full log file.
**Why I should care** — It removes the setup tax entirely: no agents to install on hosts, no central server, no Compose stack to stand up just to read logs from a handful of machines, while still giving a real correlated multi-host timeline view.
**What it could replace** — Standing up ELK/Graylog/OpenObserve just to read logs from 2-5 EC2/EB instances during an incident; juggling multiple SSH tmux panes.
**Ways I could use it** — Incident triage across EC2/EB instances; visual spike detection via the histogram before full-text search; ad hoc log inspection on client MSSP/PTaaS infrastructure where installing an agent stack isn't practical.
**Agent opportunity** — None built in; it's an interactive TUI, not scriptable as-is.
**Integration effort** — Low. Local Go binary install; nothing to deploy on target hosts, it connects out over SSH.
**Maturity** — Mature for its scope. Created 2025-04-20 (~18 months old), 1,563 stars, latest release v1.11.0 (2026-09-17), monthly cadence. Single dominant contributor (467 of ~486 commits) — real bus-factor risk.
**License** — BSD-2-Clause. No restrictions.
**Alternatives** — Graylog, Kibana/ELK (mainstream, require a server stack), OpenObserve (catalogued-class, requires a running service), plain `ssh tail -f` scripts.
**Why this one** — It's the only option here with zero server-side footprint: nothing to install on the hosts being observed, nothing to run centrally.
**Recommendation** — Install locally and point it at whatever EC2/EB hosts are already in use; very low adoption risk since nothing changes on the infrastructure side.

### 2. doco-cd — 8.2/10
**Decision:** PROTOTYPE

**What it is** — A lightweight, declarative GitOps continuous-deployment tool for Docker Compose and Swarm — a minimal ArgoCD, but scoped to Compose instead of Kubernetes.
**Why I should care** — Most self-hosted GitOps tooling assumes Kubernetes. This is scoped correctly for anyone still running plain Docker Compose on a handful of VMs, which is the realistic deployment shape for most side projects, MVPs, and small client engagements.
**What it could replace** — A hand-rolled `git pull && docker compose up -d` deploy script or a GitHub Actions SSH-deploy step maintained per project.
**Ways I could use it** — Replace an existing CI/CD SSH-deploy step; give a small MSSP-portal or PTaaS-deliverable client a push-to-deploy workflow without adopting Kubernetes; multi-environment promotion by pointing separate instances at different branches.
**Agent opportunity** — None native; an agent could trigger a deploy by pushing to the watched branch, but there's no direct tool-call surface.
**Integration effort** — Low. Single distroless container; configure a Git provider webhook or enable polling.
**Maturity** — Mature. Created 2024-07-18 (2+ years old), 1,666 stars, latest release v0.119.0 (2026-09-17), active weekly releases with Renovate-bot dependency automation, CodeQL and image vulnerability scanning in its own CI.
**License** — Apache-2.0. No restrictions.
**Alternatives** — ArgoCD/Flux (Kubernetes-only, much heavier), Portainer's GitOps stacks (proprietary tiering above the free edition), Coolify/Dokploy (catalogued-class, broader PaaS scope), hand-rolled SSH-deploy scripts.
**Why this one** — Correctly scoped: it doesn't try to be a PaaS or require a cluster, it does one thing (Compose GitOps) with 2+ years of production hardening behind it.
**Recommendation** — Trial against one existing Docker Compose-deployed side project before replacing an established deploy script — it touches live deploy infrastructure, so validate on something non-critical first.

### 3. Rootprint — 7.6/10
**Decision:** PROTOTYPE

**What it is** — A self-hosted log and trace explorer that stores its indexes directly on S3-compatible object storage instead of requiring a dedicated database cluster, with OTLP ingestion, a log explorer, trace waterfalls, and a per-service health dashboard.
**Why I should care** — Same cost argument as OpenObserve (indexes live on cheap object storage, not a database cluster sized for log volume), but narrower in scope — logs + traces only, not the full logs/metrics/traces/RUM/session-replay surface — which means less to operate for a single project's telemetry, and it plugs directly into S3 which is already part of the AWS stack.
**What it could replace** — A Postgres/Elasticsearch cluster sized for log volume; a Datadog/Honeycomb trial that turns into a real bill.
**Ways I could use it** — Personal/small-team logs+traces backend; OTLP sink for a Node/Next.js service; correlating a trace waterfall with the logs from the same request in one UI.
**Agent opportunity** — None built in beyond standard OTLP ingestion.
**Integration effort** — Medium. Needs Docker, a Postgres instance for metadata, an S3-compatible bucket, and an OTel Collector/Vector/Fluent Bit in front of it.
**Maturity** — Emerging. Created 2026-03-06 (~6 months old), 401 stars, latest release v0.4.3 (2026-09-10), active near-daily pushes. One dominant contributor (660 of ~680 commits).
**License** — Apache-2.0. No restrictions.
**Alternatives** — OpenObserve (catalogued-class, more mature, broader feature set, own storage engine), Grafana Tempo + Loki (mainstream, more moving parts), SigNoz (mainstream), Honeycomb/Datadog (hosted SaaS).
**Why this one** — Deliberately smaller scope than OpenObserve for teams that only need logs+traces, not the full observability suite.
**Recommendation** — Stand it up against a side project's OTel traffic to compare real query latency and storage cost against OpenObserve before treating it as a default pick.

### 4. Bytebase — 7.6/10
**Decision:** PROTOTYPE

**What it is** — A database schema-change and governance tool: SQL review, migration workflows with approval gates, drift detection, and access control across Postgres, MySQL, MongoDB, and most major databases. Recently repositioned to also expose an MCP-style interface for AI-agent-proposed migrations.
**Why I should care** — Most migration tools (Flyway, Liquibase, Prisma Migrate, Mongoose migrations) apply schema changes; Bytebase adds the governance layer on top — review, approval, drift detection, audit trail — which is what's missing once more than one person (or agent) touches a production schema.
**What it could replace** — Applying migrations directly from CI with no review step; not having an audit trail of schema changes; manually diffing a database against what migrations claim it should look like.
**Ways I could use it** — Gate schema migrations behind review across a Postgres + MongoDB stack; give an MSSP/PTaaS client-facing project an auditable change record; detect drift between declared and actual schema.
**Agent opportunity** — Ships an MCP-style interface so an AI agent can propose schema changes that go through the same review gate as a human-authored one — worth verifying maturity of that surface versus the long-proven core workflow.
**Integration effort** — Medium. Runs as its own service with its own metadata store; not a drop-in library.
**Maturity** — Mature. Created 2021-01-27, 14,499 stars, latest release 3.22.1 (2026-09-10), large multi-contributor team with sustained daily activity.
**License** — **FLAGGED — open-core split, not a single clean license.** Code outside `enterprise`-named directories, and not controlling feature/plan/role enablement, is MIT. Code under `LICENSE.enterprise` (advanced RBAC, SSO, other plan-gated features) may be modified and tested freely, but **production use requires a paid Bytebase subscription** per its terms. Verify exactly which features are actually needed before assuming the whole product is free to self-host in production.
**Alternatives** — Liquibase/Flyway (migration-only, no review workflow or drift detection), Atlas (schema-as-code, narrower scope), manual PR-based migration review.
**Why this one** — The cross-database (not single-engine) governance layer is the real differentiator; nothing else catalogued here does review + approval + drift detection across Postgres and MongoDB in one tool.
**Recommendation** — Trial the MIT-licensed core (SQL review, basic migration workflow) against one real database before evaluating whether any enterprise-gated feature is actually needed.

## Meaningful Updates
**Kingfisher** (`mongodb/kingfisher`, catalogued USE NOW, 8.4) — v2.1.0 → v2.5.0. `scan --branch <ref>` now scans all reachable Git history by default instead of just the branch tip, surfacing secrets that were committed and later deleted (previously required an explicit flag). ## Small but High-Leverage Utility
**OpenTab** (`hamidi-dev/opentab`, MIT, 88 stars) is a terminal-and-browser tool that reads the session history your coding agents already keep locally (Claude Code, Codex, OpenCode, Copilot, and others) and turns it into a browsable spend/token report — no account, no telemetry sent anywhere, no setup beyond pointing it at existing history files. It answers "where did this month's agent spend actually go" — down to the session and the turn that filled the context window — without instrumenting anything. Given how much of the day-to-day workflow already runs through coding agents, this is a genuinely zero-cost way to see the pattern rather than guessing from a monthly bill.
