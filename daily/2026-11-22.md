# Open Source Radar — 2026-11-22
_Rotation slot 5 — self-hosted SaaS alternatives, productivity_

## Executive Summary
Today's slot overlapped a GitHub-wide wave of same-day "open source alternative to X"
repos — most 0-5 stars, generic marketing copy, no independent signal — and one
org (`just-every`) that has templated roughly 45 near-identical micro-SaaS-alternative
seeds with almost no traction on any of them. Past that noise, four genuinely
well-built, independently differentiated self-hosted platforms stood out: an onboarding
platform with native MCP authoring, a self-hosted multi-agent Claude Code workspace with
durable remote sessions, a feature-complete PagerDuty-style incident-response platform
under a source-available license, and a multiplayer AI-agent design canvas worth
studying for its architecture even without a direct fit to the current stack. A
no-API-key, 4,500-carrier parcel-tracking engine was today's utility pick.

## Today's Best Discoveries

### 1. Usertour — 8.2/10
**Decision:** PROTOTYPE

**What it is** — A self-hosted, open-source user onboarding platform: in-app product
tours, checklists, and surveys, with a built-in MCP server so an AI agent can author a
flow directly from a prompt.
**Why I should care** — Onboarding tooling (Appcues, Userflow, Userpilot) is a recurring
per-seat SaaS cost and an annoying in-house build; this gives an MIT-core self-hosted
equivalent with AI-agent authoring built in rather than bolted on.
**What it could replace** — A paid tour/checklist/survey SaaS subscription, and the
multi-week in-house build (visual editor, targeting rules, analytics) a tour tool
otherwise requires.
**Ways I could use it** — Self-host onboarding for the MSSP admin-portal SaaS; point an
agent at a feature and have it draft a matching-styled tour; run in-app feedback surveys
without a separate tool; offer "AI-authored onboarding setup" as a client add-on.
**Agent opportunity** — Native MCP server plus a Claude Code plugin (`usertour/skills`)
that wires MCP connection and authoring skills together in one install.
**Integration effort** — Low: `docker compose up -d` (app + Postgres + Redis), or a
one-click Railway deploy.
**Maturity** — Emerging but active: created 2025-01-24 (~22 months), 2,342 stars, 170
forks, 8 subscribers, 35 open issues. v0.9.9 released the same day as this review, with
an active Discord/blog/Twitter.
**License** — MIT for the core; directories tagged "enterprise"/"ee" (feature/
permission/role/plan gating) sit under a separate commercial license — check before
depending on anything in those paths.
**Alternatives** — Appcues, Userflow, Userpilot, Chameleon, UserGuiding, Frigade — all
proprietary/hosted; none offer native MCP-based authoring.
**Why this one** — The only onboarding tool found with AI-agent authoring built into the
core product rather than as a chatbot layered on top of a visual editor.
**Recommendation** — Self-host it against one real onboarding flow and try the
MCP-authoring path before committing to it for a client product.

### 2. Open Walnut — 8.0/10
**Decision:** PROTOTYPE

**What it is** — A self-hosted, local-first web app that runs multiple Claude Code (and
Codex/Gemini/OpenCode/Goose) sessions as an "org": a CEO agent oversees per-project leads
dispatching worker sessions, with durable sessions across SSH/browser disconnects,
per-session diff review, and notes/tasks/memory in one page.
**Why I should care** — Targets the exact failure modes an unattended multi-session
coding-agent workflow hits — a dropped SSH connection losing a session, no single view of
what needs a human, no durable diff review — the same category of risk this radar's own
daily Claude Code run carries.
**What it could replace** — tmux/terminal-tab juggling across agent sessions, a separate
Notion workspace for agent-related tasks/notes, manual patch review of agent diffs.
**Ways I could use it** — Monitor several Claude Code sessions side by side; keep a
session alive across a dropped SSH connection; review an agent's diff and comment back
into the same session; dispatch a lead+worker hierarchy against a multi-part project.
**Agent opportunity** — It *is* an agent-orchestration layer, with scheduled routines, a
quick-question assistant, and a plugin system for custom apps.
**Integration effort** — Low: one-line installer, Homebrew, npm, or a Mac app; no server
to provision, local-first storage under `~/.open-walnut/`.
**Maturity** — Emerging: created 2026-02-24 (~9 months), 142 stars, 11 forks, 0
subscribers, 1 open issue. v0.6.37 released 2026-11-20, two days before this review.
**License** — MIT, no restrictions.
**Alternatives** — Bernstein (already catalogued, CLI-only orchestrator); agentOS/Rivet
(already catalogued); plain tmux + Claude Code CLI.
**Why this one** — Differentiates with a full web UI, durable remote sessions over SSH,
and bundled notes/tasks/memory, versus the CLI-only shape of the already-catalogued
alternatives.
**Recommendation** — Run a real multi-day unattended agent workflow through it to test
the durable-session claim directly before relying on it for anything load-bearing. Note:
the README's "USED BY ENGINEERS AT Amazon, DoorDash" claim could not be independently
verified — treat it as unverified marketing copy, not evidence of enterprise adoption.

### 3. IncidentRelay — 7.8/10
**Decision:** PROTOTYPE

**What it is** — A self-hosted on-call, alert routing, event orchestration, and
incident-response platform: PagerDuty-style rotations, escalation policies, a service
catalog, SLI/SLO tracking, and OIDC/SAML SSO, run on your own infrastructure.
**Why I should care** — PagerDuty/Opsgenie per-seat pricing is real recurring spend for
any team running on-call, and this reaches comparable feature depth (orchestration
builder with shadow-mode/replay, blast-radius analysis) while staying self-hosted —
directly relevant to the MSSP/PTaaS secondary context as internal tooling.
**What it could replace** — A PagerDuty/Opsgenie subscription, and the ad hoc
Slack-channel incident handling teams fall back to without one.
**Ways I could use it** — Run on-call rotations/escalation for internal infra;
deduplicate alerts from Alertmanager/Datadog/Grafana/Sentry/Uptime Kuma into one incident
queue; give an MSSP ops team SSO-gated internal incident response; track service
dependencies and blast radius.
**Agent opportunity** — Generic webhook intake and a PagerDuty Events API
v2-compatible interface make it easy to wire into any existing pipeline; no native
MCP/agent surface found.
**Integration effort** — Medium: Docker Compose, Helm/Kubernetes, RPM, or systemd;
SQLite or PostgreSQL backend. Real configuration (SSO, integrations, escalation
policies) is required, not a one-command setup.
**Maturity** — Emerging but fast-moving: created 2026-04-29 (~7 months), 231 stars, 20
forks, 7 subscribers, 29 open issues, already at v2.5.1 (2026-11-15). From the roxy-wi
org (maintainers of the existing RoxyWI load-balancer admin UI), which likely explains
the unusually fast feature maturity for a ~7-month-old repo.
**License** — Elastic License 2.0 — free to self-host/modify/use internally, but may not
be offered to third parties as a hosted/managed service exposing substantially the same
functionality. Flagged loudly given the MSSP/PTaaS context: this blocks a resellable
hosted feature, not internal use.
**Alternatives** — PagerDuty, Opsgenie, Grafana OnCall, Better Stack, Cabot (abandoned).
**Why this one** — Reaches a feature depth (shadow-mode orchestration testing,
dependency-aware blast-radius analysis) that smaller self-hosted on-call tools don't
attempt.
**Recommendation** — Stand it up against one real set of internal alert sources before
relying on it for production on-call.

### 4. Doop — 7.6/10
**Decision:** STUDY

**What it is** — An open-source, self-hostable multiplayer design canvas (an
alternative to Paper.design) where humans and AI agents co-design the same canvas live
via a built-in MCP server; frames render real HTML in sandboxed iframes.
**Why I should care** — A rare real-time collaborative tool built agent-first rather
than retrofitted: agents get the same multiplayer presence, cursors, and MCP-driven edit
surface as a human collaborator — a pattern worth copying elsewhere, independent of
whether the product itself gets adopted.
**What it could replace** — Not a direct fit for current stack work; valuable as a
collaborative mockup surface and an architecture reference.
**Ways I could use it** — Let an agent sketch/self-review a UI design live instead of a
prompt-screenshot-refresh loop; run a collaborative mockup review for an admin-portal
redesign; study the WebSocket multiplayer + sandboxed-iframe + agent-as-collaborator MCP
combination for reuse elsewhere.
**Agent opportunity** — Built-in MCP server works with Claude Code, Codex, ChatGPT,
Cursor, OpenCode, or any MCP client; headless agents (n8n, Mastra, CI) connect via an
agent-key bearer header.
**Integration effort** — Low: `docker compose up` (embedded Postgres, no external
services) or `bun run dev`.
**Maturity** — Experimental: created 2026-08-22 (~3 months), 2,256 stars, 286 forks, 9
subscribers, 77 open issues. Desktop app already at v0.14.0 (2026-11-16) — fast-moving
despite its age, with CI and an active Discord.
**License** — AGPL-3.0 — flagged loudly: self-hosting internally is fine, but offering
it as a hosted/modified service to others, or embedding it in a closed-source product,
triggers copyleft obligations.
**Alternatives** — Paper.design (proprietary), Figma (proprietary, no native
agent-as-collaborator model), tldraw (open canvas, no built-in MCP/agent-presence layer).
**Why this one** — The "design memory distiller" pattern (pin exemplar frames → capture
decisions → propose durable style rules agents must follow) is a reusable idea for any
product needing an agent to stay visually consistent over time.
**Recommendation** — Study the architecture; not an obvious adoption target for current
MERN/AWS product work given its age and AGPL-3.0 terms.

## Small but High-Leverage Utility
**Universal Parcel Scraper** — a self-hosted parcel-tracking engine for 4,500+ carriers
(1,059 dedicated adapters plus 5 universal fallbacks): give it a tracking number, it
asks the carrier's own site directly and returns the same normalized JSON for every
carrier, no account or API key needed. Apache-2.0, npm package (CLI/library/HTTP
server). The project's own published benchmark on a 100-carrier European sample shows
95% coverage with all fallbacks enabled versus 73% for the best aggregator tested — a
real, measured alternative to paid tracking APIs (AfterShip, 17TRACK, EasyPost), useful
for any fulfillment or logistics feature that would otherwise need one.

## Run Notes
GitHub's search/repositories API (direct from the GitHub Actions runner, `GITHUB_TOKEN`,
roughly 45 calls across topic/keyword searches — `topic:self-hosted`,
`topic:saas-alternative`, `"open source alternative" in:description`,
`topic:productivity topic:self-hosted` — plus individual repo/release lookups and one
org-repo listing) was the primary discovery lever today; `raw.githubusercontent.com` was
used to pull README and LICENSE text for all seven deep-review candidates (including the
two rejected ones) before cataloguing or rejecting. WebSearch/WebFetch were not needed.
No sources were unreachable; rate limit stayed well under the 8,550/hr cap (under 50
calls used). The `topic:self-hosted` and `in:description "open source alternative"`
searches, sorted by most-recently-updated, were dominated by same-day, single-digit-star
repos — a reminder that "recently pushed" is a noisy discovery signal on its own and
needs pairing with star/subscriber/README inspection before anything gets taken
seriously.
