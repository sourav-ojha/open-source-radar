# Open Source Radar — 2026-09-12
_Rotation slot 4 — data, search, documents, RAG_

## Executive Summary
Today's discoveries cluster around document ingestion and structured data for agents: a mature format-agnostic document parser (Dedoc), an embedded-to-clustered vector database (LynseDB), a visual pipeline studio for Docling extraction (Docling Studio), and a graph+vector "memory layer" for AI agents (RushDB). The most notable find outside that core theme is GEO Optimizer — a genuinely new category (Answer Engine Optimization / Generative Engine Optimization) that surfaced as a saturated same-week hype wave, but with one clearly more mature entrant worth using directly against his own SaaS marketing sites. Also flagged: a self-hostable RAG platform (bigRAG) whose "self-hostable" claim doesn't survive contact with its hard dependency on the proprietary Turbopuffer vector-search service.

## Today's Best Discoveries

### 1. Dedoc — 8.0/10
**Decision:** USE NOW

**What it is** — Apache-2.0 Python library/service that parses 30+ document formats (PDF including scanned, DOCX, HTML, images) and extracts content, logical structure, tables, and metadata into one uniform structured representation.
**Why I should care** — Broader format coverage than the PDF-only tools already catalogued (OpenDataLoader PDF), and it runs as a Dockerized REST service so ingestion isn't coupled to the app's language runtime.
**What it could replace** — Hand-rolled per-format parsers and ad-hoc OCR fallback logic for scanned documents.
**Ways I could use it** — Universal document-ingestion step for a RAG pipeline; table extraction from scanned legal/financial PDFs; a generic "upload any document" import feature; standalone parsing microservice.
**Agent opportunity** — Usable as a tool call in a document-QA agent pipeline; REST API makes it easy to wrap as an MCP tool.
**Integration effort** — Low. `pip install dedoc` or run the provided Docker image; library or REST API.
**Maturity** — Mature. Created 2020, 734 stars, active (v2.7, 2026-06-25), 14 open issues.
**License** — Apache-2.0, unrestricted commercial/SaaS/embedding use.
**Alternatives** — OpenDataLoader PDF (catalogued, PDF-only), unstructured.io, Docling, Apache Tika.
**Why this one** — Widest format coverage of any document parser reviewed so far, with a 5-year track record rather than a same-week launch.
**Recommendation** — Install and try as the ingestion layer for any multi-format document project.

### 2. GEO Optimizer (GeoReady) — 7.9/10
**Decision:** USE NOW

**What it is** — MIT CLI/library/MCP-server/Astro-integration that audits a website against 47 research-backed methods for AI answer-engine visibility (ChatGPT, Perplexity, Gemini, Claude, Google AI Overviews), scoring AI-search readiness 0–100 and generating concrete fixes (llms.txt, JSON-LD, robots.txt rules).
**Why I should care** — AEO/GEO is a genuinely new SEO-adjacent discipline in 2026; this gives an auditable score instead of vague advice, directly applicable to his MSSP admin-portal SaaS and PTaaS partnership pages.
**What it could replace** — Manual guesswork about what makes AI answer engines cite a page.
**Ways I could use it** — One-off audit of a marketing site; CI check for AI-visibility regressions; auto-generate llms.txt/JSON-LD for a new launch; run as an MCP tool during site development.
**Agent opportunity** — Ships an MCP server out of the box — usable directly by a coding agent as a self-check tool.
**Integration effort** — Low. `uvx --from geo-optimizer-skill geo audit --url <site>`, zero install.
**Maturity** — Mature for its age. ~7 months old, 792 stars, 1,720+ tests, CI, academic citations (KDD 2024, ICLR 2026).
**License** — MIT for the CLI/library/MCP server; the vendor sells a hosted monitoring tier (GeoReady.dev) on the same engine — open-core, no restriction on the OSS part.
**Alternatives** — getcito (413★), eGEOagents (183★), aeo.js (134★), elmo (321★) — all part of a same-week AEO/GEO wave.
**Why this one** — Most mature test suite and broadest integration surface (CLI + library + MCP + Astro) of the wave, with actual research citations behind the scoring methodology rather than marketing copy.
**Recommendation** — Run it once against his live marketing sites; the open-core architecture is also worth studying as a micro-SaaS pattern.

### 3. LynseDB — 7.8/10
**Decision:** PROTOTYPE

**What it is** — Apache-2.0 Python-first vector database with a Rust storage/search core; the same client API works embedded (local files), as a single HTTP server, or as a sharded cluster.
**Why I should care** — Most embedded vector DBs force a rewrite when a prototype needs to scale; LynseDB's pitch is keeping one client API across all three deployment modes.
**What it could replace** — A separate vector-DB service for early-stage RAG/agent-memory features, and the migration cost of swapping vector DBs later.
**Ways I could use it** — Embedded local vector store for a prototype; hybrid dense+BM25 search in one collection API; domain-specific distance metrics (geospatial, fingerprints) beyond typical vector-DB feature sets.
**Agent opportunity** — Backend for an agent-memory MCP server; embedded mode fits a CLI tool needing semantic search with zero infra.
**Integration effort** — Low to start (`pip install lynsedb`), medium for cluster mode (Docker/Kubernetes examples provided).
**Maturity** — Emerging. Created December 2023, actively maintained (v0.9.0, 2026-08-25), but only 40 stars after ~2 years.
**License** — Apache-2.0, unrestricted.
**Alternatives** — Qdrant, Chroma, LanceDB, Milvus Lite.
**Why this one** — The embedded→server→cluster growth path without a client-API rewrite is a genuinely different value proposition than the alternatives.
**Recommendation** — Prototype it for a small RAG feature; verify cluster-mode maturity before anything production-critical given the limited community size.

### 4. RushDB — 7.4/10
**Decision:** PROTOTYPE

**What it is** — Graph + vector database and "memory layer" for AI agents, built on Neo4j. Push arbitrary JSON, get back typed, searchable, relationship-aware records with no schema or migrations.
**Why I should care** — Combines graph relationships and vector search behind one JSON-in/JSON-out API — most agent-memory stores pick one or the other.
**What it could replace** — Ad-hoc MongoDB collections plus a separate vector DB for agent-facing data.
**Ways I could use it** — Schema-less structured memory store for an AI agent; a "record explorer" admin UI without hand-writing migrations.
**Agent opportunity** — Ships an MCP server — usable directly as an agent's structured memory backend.
**Integration effort** — Medium. Docker Compose bundles Neo4j, which a MERN stack doesn't already run.
**Maturity** — Emerging. Created December 2024, 323 stars, active (MCP server v2.13.0, 2026-08-31).
**License** — **Split — flagged loudly.** `platform/core` and `platform/dashboard` (the actual engine and dashboard) are Elastic License 2.0 (source-available, not OSI-approved); docs, website, and the JS SDK are Apache-2.0. ELv2 permits self-hosting and embedding freely but forbids reselling RushDB itself as a hosted service.
**Alternatives** — Catalogued mex (different niche), Zep, Memgraph-based agent-memory stacks.
**Why this one** — The relationship-aware, schema-less JSON API is a distinct architecture worth testing, not a repackaging of an existing vector DB.
**Recommendation** — Prototype in a low-stakes project; read the ELv2 terms before any commercial deployment decision involving reselling.

### 5. Docling Studio — 7.3/10
**Decision:** PROTOTYPE

**What it is** — MIT Vue 3 + FastAPI visual studio built on IBM's Docling extraction library. Upload a PDF, configure the extraction pipeline in the browser, inspect bounding boxes per page, then chunk/embed/index into OpenSearch and mirror the document tree as a Neo4j graph.
**Why I should care** — Docling is a strong extraction engine but headless; this fills the "see what actually got extracted before you trust it" gap with a real UI.
**What it could replace** — Trial-and-error tuning of a document-extraction pipeline blind, and a custom-built ingestion admin panel.
**Ways I could use it** — Visually tune chunking strategy and token limits before writing ingestion code; debug incorrect table/formula extraction via bounding-box inspection; one-click ingest into OpenSearch + Neo4j for a RAG prototype.
**Agent opportunity** — The ingestion pipeline could be automated as a backend step for agent-facing document search; the Neo4j mirror is useful context for structure-aware retrieval.
**Integration effort** — Medium. Two services (Vue frontend + FastAPI backend); OpenSearch and Neo4j needed only for the full ingestion pipeline.
**Maturity** — Emerging. Created May 2025, 258 stars, 40 open issues, v0.7.1 (2026-08-24).
**License** — MIT, unrestricted.
**Alternatives** — Docling itself (headless), OpenDataLoader PDF (catalogued, no visual UI), LlamaParse (hosted, proprietary).
**Why this one** — The only entrant in today's research that gives a visual, bounding-box-level view into what a document-extraction pipeline is actually doing.
**Recommendation** — Try it as a pipeline-tuning tool before building a custom extraction-debugging UI.
