## Executive Summary

## Today's Best Discoveries

### 1. Velox — 8.2/10
**Decision:** PROTOTYPE

**What it is** — Self-hosted, MIT billing engine for AI and usage-heavy SaaS: multi-dimensional token metering (`model × token_type`), prepaid commits with drawdown, per-customer margin/COGS tracking, and a LiteLLM proxy integration. Stripe still executes the underlying card charge as a plain PaymentIntent, so Stripe Billing's 0.5% fee disappears.
**Why I should care** — The already-catalogued usage-billing engines (Lago, Meteroid, OpenMeter, Flexprice) are general-purpose; none treat AI tokens as a native pricing dimension or stamp provider cost onto every event for instant per-customer margin visibility.
**What it could replace** — A hand-rolled token-metering pipeline, a margin spreadsheet or warehouse query, and Stripe Billing's percentage fee.
**Ways I could use it** — Bill for LLM/agent usage inside a product; sell prepaid usage commits; wire an existing LiteLLM proxy's spend callback straight into it; use its Stripe-grade subscription primitives for non-AI billing too.
**Agent opportunity** — Drop-in billing for any LiteLLM-gateway-fronted coding-agent or LLM-usage deployment, with zero SDK work.
**Integration effort** — Low — single Go binary, Docker Compose, ~5 minutes from clone to a finalized invoice per its own demo script.
**Maturity** — Experimental/emerging. Pre-1.0 (v0.3.2), effectively single-maintainer (1,640 of ~1,649 commits), only 4 stars — but backed by reproducible failure-correctness benchmarks (leader SIGKILL at five kill points, forced 4-leader race, a documented negative control that fails hard without one specific index) that are unusually rigorous for a repo this undiscovered.
**License** — MIT, nothing gated, explicit commitment that nothing shipped will move behind a paid key.
**Alternatives** — Lago, Meteroid, OpenMeter, Flexprice (all catalogued, general-purpose); Stripe Billing (proprietary).
**Why this one** — The only one of the group with AI-token-native pricing, a LiteLLM ingestion path, and margin/COGS as a first-class free feature — plus benchmark rigor well above its star count.
**Recommendation** — Prototype it against a real AI-feature billing need before trusting it with production revenue, given the pre-1.0/single-maintainer status.

### 2. openheard — 7.0/10
**Decision:** PROTOTYPE

**What it is** — Open-source feedback board, roadmap and changelog — a Canny alternative that runs entirely on Cloudflare's free tier (one Worker, one D1 database, KV, R2), deployed in two commands with no VPS or Postgres to operate.
**Why I should care** — The already-catalogued Quackback solves the same problem but as a heavier all-in-one support suite expecting Postgres+Docker ops; openheard is the answer for a solo/two-person product where even light infra ops is a real cost.
**What it could replace** — Canny/Featurebase/UserVoice subscriptions; a self-hosted feedback board that needs its own server to babysit.
**Ways I could use it** — Self-hosted feedback/roadmap/changelog for a micro-SaaS; embed the widget in-product with one script tag; let Claude Code triage feedback via its MCP server or bundled agent skill; import an existing Canny CSV export.
**Agent opportunity** — Ships both an MCP server and a dedicated agent skill that teaches coding agents its own feedback-triage workflows, not just a generic API wrapper.
**Integration effort** — Low, but Cloudflare-specific — doesn't drop into an AWS-centric deployment without rearchitecting.
**Maturity** — Experimental. One month old, one release (v0.1.0), effectively single-maintainer (259/268 commits). No CLI or docs site yet.
**License** — **AGPL-3.0** — flagged per section 14. Fine for internal/own-product self-hosting; re-offering a modified version as a hosted service to others would trigger source-release obligations.
**Alternatives** — Quackback (catalogued, broader/heavier), Fider (older, narrower), Canny, Featurebase, UserVoice.
**Why this one** — Real architectural differentiation from Quackback by deployment footprint, not just branding — zero-server vs. a service to operate.
**Recommendation** — Worth trying for a feedback board where zero server ops is the priority; not mature enough to depend on without a fallback given the one-person maintenance.

### 3. GoCommerce — 6.3/10
**Decision:** STUDY

**What it is** — A composable commerce engine delivered as a Go library — catalog, cart, checkout, orders, payments, fulfillment and durable outbox-pattern events over a single PostgreSQL database — with Stripe/SendGrid/Meilisearch/Klaviyo/MCP integrations as plain Go packages wired in `main()`.
**Why I should care** — Not a stack fit (Go is secondary here; Medusa.js/Vendure are the natural Node/TS equivalents), but the architecture — one state machine shared by REST, webhooks, CSV import, MCP calls and admin actions, durable events instead of fire-and-forget side effects — is a clean reference for correctness-sensitive domain services generally.
**What it could replace** — A hand-rolled order/payment state machine; a plugin-registry/DI abstraction a small commerce engine doesn't need.
**Ways I could use it** — Study the outbox-event design; reference it if a future product ever needs lightweight embeddable commerce; note the MCP module as a template for agent-safe domain-tool exposure.
**Agent opportunity** — A dedicated MCP module exposes domain services (not raw SQL) as agent tools with the same audit trail and invariants the human admin panel uses.
**Integration effort** — Medium — requires Go familiarity and manual module wiring; no managed hosting.
**Maturity** — Experimental despite a claimed "1.0": 6 weeks old, 6 stars, effectively solo-plus-AI-assisted (171 commits from the author, 5 AI-attributed).
**License** — MIT, no commercial restrictions.
**Alternatives** — Medusa.js (Node/TS, more mainstream and a better stack fit), Vendure (Node/TS), Saleor (Python/GraphQL).
**Why this one** — The architecture is worth reading regardless of adoption; Medusa.js/Vendure remain the better choice if the goal is actually shipping commerce rather than studying the design.
**Recommendation** — Study the architecture; don't adopt for anything payments-critical given the unproven "1.0" claim and Go/Node stack mismatch.

## Small but High-Leverage Utility
**BYOT** (alexanderritik/BYOT) — runs an existing Playwright/k6/test-binary suite on a schedule inside Docker as a production monitor, with zero test rewrites and a consecutive-failure threshold to keep flaky tests from paging anyone. The core insight — CI tests code changes, but production breaks between deploys when a third-party API or SSL cert changes underneath unchanged code — is genuinely useful, and most teams already have an E2E suite rotting from disuse that this would put back to work. Too early to catalog (2 stars, single contributor, no releases yet, created five months ago with its first real commits only this week), but worth a look once it has a tagged release.
